## 편집 단계에서 확립된 판단 (07-29 세션)

- RSS 요약만으로 카드를 만들지 않는다 — 기사 원문을 직접 fetch해 팩트 확보 후 재작성 (`(서울=연합뉴스) …` 리드 그대로 금지)
- 같은 사건의 중복 기사는 병합 (경기 기사 + `[○○전적]` 라인스코어 기사 → 한 포스트)
- 승인 후 draft·PNG 수정 시 해시가 어긋나 발행 거부 → 재승인 필요
- 카드 수를 줄여 재렌더하면 이전 구성의 잔여 PNG가 남는다 → 삭제할 것

## 렌더링 실측 규칙 (문서에 없던 것)

- 매거진 커버(사진 있는 커버): 헤드라인 최대 3줄 + **dek 1줄(한국어 약 25자)**. dek이 2줄로 접히면 하단 프레임 이탈 — 렌더러가 에러로 잡지 않으므로 PNG 육안 검수 필수
- scoreboard `rows[].value`·stat_grid `items[].value`는 대형 글씨 우측/셀 배치 — 짧은 값만 (`18`, `.617`, `4승`), 긴 목록은 `detail`로

## 발행: "API access blocked" 사건 (07-30 ~ 08-01)

- **증상**: 모든 graph.instagram.com 요청(프로필 조회·토큰 갱신 포함)이 `"API access blocked." OAuthException code 200`. 약 2일 지속 후 아무 조치 없이 해제 — 같은 토큰이 08-01 아침부터 정상 동작
- **추정 원인(해석)**: 07-29 밤 같은 포스트를 11분 간격 2회 발행(수정 후 강제 재발행) + 연속 발행 → Meta 자동화 감지의 임시 차단. 24~72시간 자동 해제 패턴과 일치
- **판별**: code 190(토큰 만료)과 다르다. code 200 차단은 토큰 재발급으로 해결 안 됨 — 기다리거나 대시보드 확인
- **대응 절차**: 차단 중에는 승인된 PNG+캡션을 포스트별 폴더로 정리해 수동 업로드 대비(`output/<날짜>/manual-publish/` 패턴)
- **재발 방지**: `publish_articles.py`에 `--interval`(게시물 간 대기, 기본 600초) 추가(08-01). 강제 재발행은 기존 게시물 삭제 후 시간 간격을 두고

- **예약 발행** — launchd `com.instacardnews.publish`가 매일 08:00·23:00에 그날 폴더의 승인·미발행 포스트를 발행. 포스트를 발행일 폴더에 만들고 승인까지 해두면 자동으로 나간다 → 08-14 서버 systemd timer로 대체(아래 08-14 정책 변경)

## 운영 정책 변경 (2026-08-14, 사용자 결정)

- **08:00 발행** — 전날 22:15에 다음 날 게시물 1건을 준비·검수·기본 승인하고, 전날 23:00에 Slack `#instagram`으로 PNG 전 장을 보낸다. 사용자는 08:00 전까지 수정·보류 피드백을 줄 수 있다. 피드백이 없으면 검수된 기본 승인본을 08:00에 발행한다.
- **08:00 피드백 처리** — 수정 피드백을 받으면 기존 승인을 먼저 취소해 오래된 승인본이 발행되지 않게 한다. 수정→재렌더→PNG 전 장 재검수→재승인→수정본 Slack 전송 순서로 처리한다. `발행 보류` 피드백은 재승인하지 않아 08:00 발행을 막는다.
- **23:00 발행** — 21:45에 별도 게시물 1건을 자율 준비·검수·승인하고, 사용자 피드백 대기 없이 23:00에 발행한다.
- **서버 예약 방식** — 항상 켜진 Oracle 서버의 systemd timer가 08:00·23:00 발행과 23:00 다음 날 아침 미리보기를 담당한다. Mac launchd는 발행 경로로 사용하지 않는다.
- **피드백 학습** — Slack에서 받은 카드뉴스 피드백은 [[프로젝트/개인/인스타카드뉴스/Slack 피드백 기록|Slack 피드백 기록]]에 원문·해석·수정·검증 결과를 누적한다. 한 게시물에만 해당하는 의견은 기록만 하고, 반복 적용할 수 있는 선호는 이 문서와 필요 시 `DESIGN.md` 결정 로그에 반영한다. 피드백을 반영한 모든 PNG는 재검수한다.
