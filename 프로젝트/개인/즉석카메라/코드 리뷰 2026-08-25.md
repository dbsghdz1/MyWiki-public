## 0. 총평 — 관점별 판정

| 관점 | 판정 |
|---|---|
| 1. 10분 현상 타이머 | **구조는 정답.** `capturedAt` + `developSeconds`만 저장하고 진행률을 매번 계산하는 타임스탬프 방식(`Photo.swift:27-35`)이라 앱 종료·백그라운드·재부팅에서 현상이 올바르게 이어진다. 깨지는 곳은 계산이 아니라 **UI 갱신**(발견 5)과 **알림**(발견 1)이다. |
| 2. 사진 데이터 안전성 | 원자적 쓰기(`.atomic`)는 좋으나 **모든 I/O가 `try?`로 침묵**한다. 디스크 부족 시 필름만 소모되고 빈 사진이 남으며(발견 2), 인덱스 디코드 실패 시 전체 라이브러리가 덮어써질 수 있다(발견 3). |
| 3. 렌더 파이프라인 | **색 곡선은 개발 기록 설계와 일치**(아래 §3 검증). 그러나 풀해상도 CoreImage 렌더가 전부 메인 스레드에서 돌고(발견 7), **EXIF 방향 미적용으로 실기기에서 사진이 90° 돌아갈 가능성**이 높다(발견 4). |
| 4. 푸시 알림 | 스케줄 자체는 정확하나 **첫 사진의 알림이 권한 요청 전에 등록돼 유실**된다(발견 1). 권한 거부 시 크래시 없이 조용히 넘어간다(수용 가능, 발견 13). |
| 5. 일반 | 흔들기 이중 처리(발견 6), `abs(hashValue)` 이론상 크래시(발견 10) 등. |

## 1. 발견 상세

### [높음] 1. 첫 사진의 현상 완료 알림이 유실된다 — 권한 요청 전에 스케줄

- 위치: `Sources/UI/CameraScreen.swift:250-256`, `Sources/Model/PhotoStore.swift:61`, `Sources/Model/Notifications.swift:15-30`
- 내용: `shoot()`의 캡처 콜백에서 `store.add(...)`가 먼저 실행되고, `add()` 내부에서 `Notifications.scheduleDevelopFinished(for:)`가 호출된다. 그 **다음에야** `Notifications.requestAuthorizationIfNeeded()`가 실행된다. 첫 촬영 시점의 권한 상태는 `.notDetermined`이고, 이 상태에서 `UNUserNotificationCenter.add(request)`는 "notifications are not allowed" 에러로 **조용히 실패**한다(에러 핸들러도 없음, `Notifications.swift:29`). 사용자가 다이얼로그에서 허용해도 이미 실패한 요청은 되살아나지 않는다.
- 왜 치명적에 가깝나: 첫 사진이야말로 "10분 뒤에 다시 열게 만드는" 리텐션 장치의 대상인데, 정확히 그 한 장의 푸시가 안 온다. 흔들어서 `store.shake()`가 재스케줄해 주는 우연이 없는 한 첫 경험이 "알림 안 오는 앱"이 된다.
- 재현: 새 설치 → 첫 촬영 → 권한 허용 → 앱 종료 → 10분 대기 → 알림 없음.
- 수정 방향: (a) `requestAuthorizationIfNeeded`의 완료 콜백에서 granted면 `store.developing` 전체를 재스케줄하거나, (b) 첫 촬영 플로우에서 권한 요청 → 응답 후 `scheduleDevelopFinished` 순서로 바꾼다. (a)가 기존 구조를 안 건드려서 안전하다.

### [높음] 2. 저장 실패가 전부 침묵 — 디스크 부족 시 필름 소모 + 빈 사진

- 위치: `Sources/Model/PhotoStore.swift:52-63` (`add`), `:40-43` (`save`), `:29-32` (`savePack`), `:47-50` (`loadImage`)
- 내용: `add()`는 ① `pack.consume()` + `savePack()` → ② `try? imageData.write(...)` → ③ 메타데이터 추가 + `try? save()` 순서다. ②가 실패해도(디스크 부족, I/O 에러) 아무 처리 없이 진행돼서 **필름 1장이 소모되고, 이미지 없는 Photo가 인덱스에 남는다.** 이 사진은 `loadImage`가 nil을 돌려줘 영원히 크림색 빈 인화지로 표시되고, 사용자에게 어떤 통지도 없다. ③의 `save()` 실패 시에는 반대로 이미지 파일은 있는데 다음 실행에서 인덱스에 없는 고아가 된다.
- 재현: 저장 공간이 거의 찬 기기에서 촬영 → 배출 애니메이션은 정상 재생 → 흰 인화지가 10분 뒤에도 흰 채로 남음. ₩3,300 낸 사용자 입장에서는 "찍은 사진이 사라졌다".
- 수정 방향: `add()`에서 이미지 쓰기를 `do-catch`로 감싸고, 실패 시 (a) `pack` 소모를 롤백, (b) Photo를 인덱스에 넣지 않고, (c) 사용자에게 "저장 공간이 부족합니다" 안내. 쓰기 성공 후에 `consume()`하는 순서 변경만으로도 절반은 해결된다. `save()` 실패도 최소한 재시도 1회 + 로그.

### [높음] 3. 인덱스 디코드 실패 시 전체 라이브러리가 덮어써지는 마이그레이션 지뢰

- 위치: `Sources/Model/PhotoStore.swift:21-27` (`load`), `:40-43` (`save`)
- 내용: `load()`에서 `photos.json` 디코드가 실패하면 `photos = []`로 시작하고, 이후 **첫 촬영·삭제·흔들기 아무거나 한 번이면 `save()`가 빈(또는 새 사진 1장짜리) 배열로 인덱스를 덮어쓴다.** 이미지 파일들은 Documents에 남지만 다시는 연결되지 않는다. 지금 당장은 `.atomic` 쓰기 덕에 파일 손상 확률이 낮지만, **미래 버전에서 `Photo`에 non-optional 필드를 하나 추가하면**(예: 흔들기 횟수, 팩 ID) 구버전 JSON 디코드가 통째로 실패해 **업데이트 = 전체 사진 소실**이 된다. Codable 배열 디코드는 한 항목만 실패해도 전체가 실패한다는 점도 같은 지뢰다.
- 재현(시뮬레이션): `photos.json`에 필드 하나 빠진 항목 1개 삽입 → 앱 실행 → 앨범 비어 있음 → 한 장 촬영 → 기존 사진 전부 인덱스에서 소멸.
- 수정 방향: (a) 디코드 실패 시 기존 파일을 `photos.json.bak`으로 보존하고 덮어쓰기 전 1회 백업, (b) 새 필드는 반드시 optional 또는 `decodeIfPresent` + 기본값, (c) 항목 단위로 관대한 디코드(`[FailableDecodable<Photo>]` 패턴). 최소한 (b)를 팀 규칙으로 못 박아야 한다.

### [높음] 4. EXIF 방향 미적용 — 실기기에서 사진이 90° 회전될 가능성 (실기기 검증 필요)

- 위치: `Sources/UI/DevelopingPhotoView.swift:61`, `Sources/Model/PhotoExporter.swift:13`
- 내용: 캡처 데이터는 `photo.fileDataRepresentation()`(`CameraSession.swift:71`)으로, 세로 촬영 시 픽셀은 가로 방향 + EXIF orientation(보통 6)으로 저장된다. `UIImage(data:)`는 orientation을 `imageOrientation` 속성으로 읽지만, **`CIImage(image: ui)`는 `imageOrientation`을 무시하고 원본 CGImage(비회전) 픽셀을 쓴다**는 것이 잘 알려진 함정이다. 그 결과 `squareCrop` → `develop` → `render()`(`UIImage(cgImage:)`는 `.up` 고정) 경로에서 세로로 찍은 사진이 90° 돌아간 채 표시·내보내기될 가능성이 높다. 데모 모드의 번들 JPG는 orientation이 `.up`이라 시뮬레이터에서는 절대 재현되지 않고, README도 "촬영→배출→현상 전체 흐름은 실기기에서만 확인된다"고 적고 있다 — 즉 아직 아무도 이 경로를 실물로 못 봤을 확률이 크다.
- 재현: 실기기에서 세로로 촬영 → 배출된 인화지의 이미지 방향 확인.
- 수정 방향: `CIImage(image: ui)` 직후 `ci = ci.oriented(forExifOrientation: ...)`(UIImage.imageOrientation → EXIF 변환), 또는 `CIImage(contentsOf:)` + `.applyOrientationProperty` 옵션, 또는 저장 시점에 픽셀을 정방향으로 구운 뒤 저장. 저장 시 1회 정규화가 렌더 반복 비용까지 없애서 가장 낫다.

### [높음] 5. 앨범을 열어둔 채 현상이 끝나면 "현상 중" 섹션에 갇힌다 — 탭도 안 됨

- 위치: `Sources/UI/AlbumScreen.swift:22-58`, `Sources/Model/PhotoStore.swift:106-107`, `Sources/Model/Photo.swift:33`
- 내용: `developing`/`developed`는 현재 시각으로 계산되는 computed property인데, **시간 경과는 `@Published`를 건드리지 않으므로 AlbumScreen의 body가 재평가되지 않는다.** 개별 `DevelopingPhotoView`는 내부 1초 타이머로 이미지·날짜 텍스트는 완료 상태로 바꿔주지만, 섹션 이동(현상 중 → 완료 그리드)은 일어나지 않는다. 결정적으로 **"현상 중" 섹션의 사진에는 Button이 없어서**(`:27-31`), 다 된 사진인데 큰 카드 자리에 앉은 채 탭해서 열 수도, 저장·공유할 수도 없다. 탭 전환이나 촬영·흔들기 등 store 변경이 일어나야 풀린다.
- 재현: 사진 1장이 완료 30초 전일 때 앨범을 열고 그대로 관찰 → 사진에 날짜가 새겨지며 완료 상태가 되지만 "현상 중 1장" 헤더 아래 그대로 있고 탭 불가.
- 왜 정상 사용에서 치명적인가: 이 앱의 핵심 시나리오가 "앨범을 열어두고 현상을 지켜본다"이다. 관찰의 끝(완료 순간)이 바로 이 화면에서 일어난다.
- 수정 방향: AlbumScreen에 1초(또는 다음 `finishesAt` 시각 기준) 타이머를 두고 `TimelineView` 또는 `@State now`로 섹션 분류를 다시 계산하거나, PhotoStore에 다음 완료 시각에 맞춘 타이머를 두고 `objectWillChange.send()`.

### [높음] 7. 풀해상도 CoreImage 렌더가 전부 메인 스레드 — 프레임 드랍 + 메모리 압박

- 위치: `Sources/UI/DevelopingPhotoView.swift:54-65` (`refresh`), `Sources/Film/ImagePipeline.swift:75-78`
- 내용: `refresh()`는 매번 ① 디스크에서 원본 JPEG 전체 읽기(`loadImage`) → ② `CIImage` 생성 → ③ 필터 체인 → ④ `context.createCGImage`(실제 렌더) → ⑤ 풀해상도 `UIImage`를 `@State`에 보관 — 이 전 과정을 **메인 스레드에서** 수행한다. 12MP 카메라 기준 정사각 크롭 후 약 3024×3024, RGBA로 **장당 약 35–37MB**의 `rendered`가 뷰마다 상주한다.
  - 현상 중 사진: 120단계 양자화로 **약 5초마다** 이 전체 비용을 다시 치른다(사진 N장이면 N배).
  - 완료된 사진: 앨범 2열 그리드의 **셀마다** `onAppear`에서 `refresh(force: true)`로 풀해상도 렌더 → 스크롤 히치. 화면에 셀 6개면 rendered만 200MB대 → jetsam(메모리 킬) 가능권.
  - 완료 셀에도 1초 타이머가 계속 돈다(값 비교 후 skip이라 렌더는 안 하지만 wake-up 비용).
- 재현: 실기기에서 사진 10장 이상 쌓고 앨범 스크롤 → 히치; 현상 중 3–4장 + 앨범 관찰 → 5초 주기 프레임 드랍; 메모리 게이지 확인.
- 수정 방향: (a) 표시 크기(300pt × scale ≈ 900px)로 **먼저 다운스케일**(`CILanczosScaleTransform` 앞단 배치 또는 저장 시 표시용 썸네일 별도 생성), (b) 렌더를 백그라운드 큐로 옮기고 결과만 MainActor에 반영, (c) 완료 사진은 최종 룩을 1회 렌더해 파일로 캐시(현상이 끝나면 결과가 불변이므로 캐시가 정당하다), (d) 완료 셀에서는 타이머 중지.

### [중간] 6. 흔들기 1회가 2번 처리된다 — 45초가 아니라 90초 단축

- 위치: `Sources/UI/CameraScreen.swift:71, 234-239`, `Sources/UI/AlbumScreen.swift:61-66`, `Sources/UI/RootView.swift:11-18`
- 내용: `RootView`의 주석대로 TabView는 보이지 않는 탭도 미리 만들어 유지한다. `onShake`(NotificationCenter 구독)는 CameraScreen과 AlbumScreen **양쪽에 붙어 있고 둘 다 항상 살아 있으므로**, 기기를 한 번 흔들면 두 핸들러가 각각 `store.shake(photo, by: 45)`를 호출해 **총 90초**가 줄고 햅틱도 2번 겹쳐 재생된다. "최대 절반(5분)" 하한은 지켜지지만, 의도한 페이스(45초/회)의 2배로 소진돼 "스킵은 없다" 원칙의 체감이 약해진다.
- 재현: 현상 중 사진의 남은 시간 표시를 보며 1회 흔들기 → 45초가 아닌 90초 감소.
- 수정 방향: shake 처리를 한 곳(예: RootView 또는 PhotoStore 레벨)으로 올려 1개만 두거나, 핸들러에서 `isActive`/현재 탭을 확인하고 무시.

### [중간] 8. 배출 중인 인화지는 흔들어도 남은 시간이 안 바뀐다 — 스냅샷 stale

- 위치: `Sources/UI/CameraScreen.swift:99-101` (`ejecting` 사용), `:259` (스냅샷 저장), `Sources/Model/Photo.swift` (값 타입)
- 내용: `ejecting: Photo?`는 촬영 시점의 **값 복사본**이다. 배출된 인화지가 화면에 떠 있는 동안 흔들면 `store.shake`가 store 안의 사진(`photos[i]`)만 갱신하고, 화면의 `DevelopingPhotoView(photo: ejecting, ...)`는 옛 `developSeconds`로 남은 시간을 계산한다. 하필 **첫 촬영 안내문이 "기다리기 힘들면 흔드세요"라고 말하는 바로 그 순간**(`FirstDevelopNote.swift:26-29`) 사용자가 흔들어 보게 되는데, 눈앞의 카운트다운이 꿈쩍도 안 해 "흔들기가 안 먹는다"로 읽힌다(실제로는 발견 6 때문에 90초 줄었는데도).
- 재현: 촬영 → 인화지가 나와 있는 3.5초+α 동안 흔들기 → 인화지 하단 남은 시간 무변화. 앨범에 가보면 줄어 있음.
- 수정 방향: `ejecting`에 Photo 대신 `photo.id`를 저장하고 표시할 때 `store.photos`에서 조회하거나, `store.shake` 후 `ejecting`도 갱신.

### [중간] 9. 상세 화면 진입 시 풀해상도 합성이 메인 스레드에서 실행

- 위치: `Sources/UI/PhotoDetailScreen.swift:35`, `Sources/Model/PhotoExporter.swift:11-30`
- 내용: `.task { composed = PhotoExporter.compose(...) }` — `compose`가 `@MainActor`라 원본 로드 + CI 렌더 + `UIGraphicsImageRenderer` 합성 전부가 메인에서 돈다. fullScreenCover 표시 애니메이션과 겹쳐 진입 히치가 난다. 또한 같은 화면의 `DevelopingPhotoView`도 별도로 풀해상도 렌더를 한 번 더 하므로 같은 원본을 2번 디코드·렌더한다.
- 수정 방향: `compose`의 CI 부분을 nonisolated로 분리해 백그라운드에서 수행하고 결과 UIImage만 반영. (발견 7의 캐시를 도입하면 여기도 같이 해결된다.)

### [낮음] 10. `abs(photo.id.hashValue)` — 이론상 크래시 + 기울기가 실행마다 바뀜

- 위치: `Sources/UI/AlbumScreen.swift:108-114`
- 내용: ① `hashValue`가 `Int.min`이면 `abs()`가 트랩(확률은 무시 가능 수준이지만 0이 아님). ② Swift의 `hashValue`는 **실행마다 시드가 바뀌므로**, "id에서 뽑은 고정 기울기 — 스크롤해도 안 바뀐다"는 주석의 의도 중 절반만 성립한다. 세션 안에서는 고정이지만 **앱을 다시 열 때마다 모든 사진의 기울기가 재배치**된다. "실물은 절대 반듯하게 놓이지 않는다"는 물성 연출이라면, 실물은 다시 열어봐도 같은 각도로 놓여 있어야 맞다.
- 수정 방향: `photo.id.uuid` 바이트에서 직접 유도(예: 첫 바이트들의 정수화 % 41). 크래시·재현성 둘 다 해결.

### [낮음] 11. `UIWindow` extension에서의 `motionEnded` override — 비지원 패턴

- 위치: `Sources/UI/ShakeDetector.swift:6-11`
- 내용: extension에서 저장된 클래스 메서드를 `override`하는 것은 Swift가 공식적으로 지원하지 않는 패턴이다(ObjC 디스패치 덕에 현재 동작하지만 컴파일러/런타임 변경에 취약). `super.motionEnded`도 호출하지 않아 시스템 기본 동작(편집 취소 셰이크 등)이 삼켜진다 — 이 앱에는 텍스트 입력이 없어 실해는 없다.
- 수정 방향: 커스텀 `UIWindow` 서브클래스 + `UIApplicationDelegate`/`SceneDelegate` 경유, 또는 현 패턴 유지 시 `super.motionEnded(motion, with: event)` 호출 추가.

### [낮음] 12. 데모 리소스가 Release 번들에도 포함된다

- 위치: `Project.swift:30`, `Sources/App/DemoMode.swift:11`
- 내용: `resources: [..., "Resources/Demo/**"]`는 구성(configuration) 구분이 없어 **Release 빌드에도 데모 JPG 7장이 실린다.** DemoMode 주석의 "배포 빌드에는 코드도 사진도 들어가지 않는다"와 어긋난다(코드는 `#if DEBUG`라 맞고, 사진은 틀림). 62KB라 실질 피해는 없지만 문서와 실제의 불일치.
- 수정 방향: Tuist `ResourceFileElement`는 구성별 분기가 안 되므로, 데모 리소스를 별도 번들/타겟으로 빼거나 빌드 스크립트로 Release에서 제거, 혹은 주석을 사실에 맞게 수정.

### [낮음] 13. 알림 부속 이슈 묶음 — 트리거 종류·전달된 알림 정리·포그라운드·탭 랜딩

- 위치: `Sources/Model/Notifications.swift:25-30`, `Sources/Model/PhotoStore.swift:99-104`, `Sources/App/InstantCamApp.swift`
- 내용:
  - `UNTimeIntervalNotificationTrigger`는 스케줄 시점 기준 상대 시간이다. 현상 완료는 절대 시각(`finishesAt`)이 진실이므로 `UNCalendarNotificationTrigger(dateMatching: finishesAt의 성분)`이 의미상 정확하다. (펜딩 요청은 재부팅에도 유지되므로 실사용 차이는 드물지만, 시계 변경 시 화면 진행률(벽시계 기준)과 알림(경과시간 기준)이 어긋난다.)
  - `delete()`는 펜딩만 취소한다 — 이미 **전달된** 알림은 알림 센터에 남는다(`removeDeliveredNotifications` 미호출). 사진을 버렸는데 "현상이 끝났어요"가 남아 있는 상황.
  - `UNUserNotificationCenterDelegate`가 없어 ① 포그라운드에서 완료 알림이 표시되지 않고(현 컨셉상 수용 가능) ② **알림을 탭해도 카메라 탭으로 열린다** — 다 된 사진을 보러 왔는데 앨범이 아니다.
- 수정 방향: 캘린더 트리거 전환, `delete()`에 delivered 제거 추가, delegate에서 탭 시 앨범 탭으로 전환.

### [낮음] 14. 알림 권한 거부 시 무표시 (수용 가능하나 기록)

- 위치: `Sources/Model/Notifications.swift:7-13`
- 내용: 거부 시 스케줄이 조용히 실패할 뿐 크래시·오동작은 없다. 다만 앱 안 어디에도 "알림이 꺼져 있어 완료를 알 수 없다"는 표시가 없어, 거부한 사용자는 10분 타이밍을 알 방법이 앱 재방문뿐이다. 설정 유도 배너 한 줄 정도는 고려할 만하다.

### [낮음] 15. 미세 성능·품질 — DateFormatter 매 렌더 생성 등

## 3. 현상 곡선 — 개발 기록 설계와의 대조 (일치 확인)

`Sources/Film/DevelopCurve.swift`를 개발 기록의 설계(속성별 시차)와 대조했다. **불일치 없음.**

| 속성 | 설계 | 코드 | 판정 |
|---|---|---|---|
| 흰 베일 | 0 ~ 0.55 구간에서 걷힘, 가장 먼저 | `veil: 1 - ramp(t, 0.0, 0.55, 0.45)` (`:37`) | 일치. 지수 0.45(앞당김)는 주석에 근거와 함께 문서화됨(12초 윤곽/30초 형태) |
| 채도 | 0.12 ~ 0.95, 지수 1.5, 가장 늦음 | `saturation: ramp(t, 0.12, 0.95, 1.5)` (`:20`) | 일치. 전 속성 중 완료 시점(0.95)이 가장 늦다 |
| 대비 | 중반 | `0.55 + 0.45·ramp(t, 0.08, 0.80, 1.2)` (`:23`) | 정합 |
| 밝기 | 초반 과다노출에서 하강 | `0.20·(1 - ramp(t, 0, 0.65, 0.9))` (`:26`) | 정합 |
| 청록 편향 | 늦게 빠짐 | `1 - ramp(t, 0.20, 0.92, 1.4)` (`:29`) | 정합, 색조 이동 ±13%/3%/7%로 "±10% 안쪽" 원칙 근사 준수 (`ImagePipeline.swift:59-63`) |

경계 연속성도 확인: `develop()`은 `t ≥ 0.999`에서 `applyTone`만 반환하는데(`ImagePipeline.swift:44`), t=0.999에서 saturation=1, contrast=1, brightness=0, coolness=0, veil=0으로 모든 곡선이 최종 룩에 수렴하므로 **완료 순간의 점프 없음**. 스플릿 톤의 핵심 관계(B의 shadow 최고·highlight 최저)도 4개 톤 모두 유지된다(`FilmTone.swift:22-45`).
