# 마일스톤 0 — OCR 실측 결과

[[프로젝트/개인/한능검/기출 PDF 실측 2026-08-26|기출 PDF 실측]]에서 **텍스트 레이어가 회차마다 없다**는 것이 드러나, 제품의 상한을 정하는 관문이 OCR로 특정됐다. 그것만 검증했다.

## 결론 — **통과. 파이프라인이 성립한다.**

| 항목 | 결과 |
|---|---|
| **문항 번호** | **50/50** (4개 회차 전부) |
| **선지 5개 확보** | **92~96%** (후처리 포함) |
| **정답·배점** | **100%** — 답지는 전 회차 텍스트 레이어가 있어 OCR 불필요 |
| 속도 | **약 1.1초/페이지** (12페이지 13초) |
| 비용 | **0원** — macOS Vision 로컬 처리, API 키·설치 없음 |

## 무엇으로 쟀나

**엔진: macOS Vision `VNRecognizeTextRequest`** (`.accurate`, revision 3, `ko-KR`). Swift 80줄짜리 CLI로 감쌌다. 설치할 것도 결제할 것도 없다 — Swift 툴체인만 있으면 된다.

**정확도 측정은 자기 채점이 아니라 정답 대조로 했다.** 77회는 텍스트 레이어가 있으므로, **같은 페이지를 이미지로 렌더해 OCR한 뒤 원본 텍스트와 비교**했다. 완전한 ground truth가 있는 조건이다.

### 77회 정답 대조 (300dpi, 3개 페이지)

| 지표 | 값 |
|---|---|
| 줄 단위 평균 유사도 | **98.3%** |
| 완전 일치 줄 | 69% |
| 유사도 ≥95% 줄 | 87% |
| 선지 완전 일치 | 21/25 |

> [!note] 처음 잰 "문자정확도 15~59%"는 지표가 틀린 것이었다
> 전체 텍스트를 통째로 비교하면 **읽기 순서 차이**만으로 점수가 무너진다(2단 조판). 순서를 제거하고 줄 단위로 재니 **98.3%**가 나왔다. 측정 방법이 결과를 만든 사례다.

## 오류의 성격 — 대부분 사소하고, 하나는 실제 위험

77회 2페이지 불일치 21줄을 전수 분류했다.

| 유형 | 건수 | 위험도 |
|---|---|---|
| 조판 기호 차이 (`“`→`"`, 유령 문자, 마침표) | 12 | 없음 |
| **원문자 마커 누락** (`①②④`가 통째로 사라짐) | 4 | **후처리로 복원됨** |
| **한자 오독** (`義慈`→`촌`, `韓粲`→`부`, `斧壤`→`주`) | 4 | 낮음 — 괄호 병기라 한글이 옆에 있다 |
| **한글 오독** (`윤충`→`윤중`) | **1** | **실제 위험. 인명이 바뀐다** |

**한자는 0/8, 전혀 못 읽는다.** 언어 조합을 `zh-Hant`·`ja-JP`·`en-US`로 바꿔봐도 결과가 **완전히 동일**했다 — 한국어 모델이 한자를 처리하지 않는다. 다만 시험지의 한자는 전부 `의자(義慈)` 형태의 괄호 병기라 **한글이 앞에 있어 의미가 보존된다.**

## 결정적 발견 — 후처리 한 줄이 인식률을 두 배로 올린다

이미지뿐인 78회를 전체 OCR하니 선지가 195/250(78%)이었고, **5개가 온전한 문항은 17개뿐**이었다. 그런데 부족한 문항을 열어보니 원인이 갈렸다.

**41번 — 선지 4개로 잡힘:**
```
리주로(2f) it ba                          ← ① 마커가 옆 이미지 캡션과 섞여 깨짐
학술지로 진단 학보를 발행하였다.            ← 선지 텍스트는 살아있다
② 가갸날을 제정하고 기념식을 진행하였다.
③ 태극 서관을 설립하여 서적을 보급하였다.
④ 주시경, 지석영 등이 중심이 되어 활동하였다.
⑤ 영은문이 있던 자리 부근에 독립문을 건립하였다.
```

**즉 마커만 날아가고 내용은 남는다.** 선지는 항상 5개이고 연속된 줄이므로, **살아남은 마커의 번호와 위치로 5줄 구간을 역산**하면 복원된다.

**9번 — 선지 0개:**
```
9. (가) 국가의 문화유산으로 옳은 것은?
```
이건 OCR 실패가 아니다. **선지 자체가 유물 사진 5개**인 문항이라 텍스트가 애초에 없다.

### 복원 규칙 적용 결과 (4개 회차 재현)

| 회차 | 문항 인식 | 원본 5개 | + 복원 | **최종** | 미확보 |
|---|---|---|---|---|---|
| 73회 | 50/50 | 16 | +30 | **46/50 (92%)** | 6·26·45·46 |
| 74회 | 50/50 | 13 | +35 | **48/50 (96%)** | 13·19 |
| 78회 | 50/50 | 17 | +29 | **46/50 (92%)** | 9·14·23·26 |
| 79회 | 50/50 | 12 | +34 | **46/50 (92%)** | 6·11·17·33 |

**미확보 문항은 전부 사진 선지 문항이다.** OCR로 풀 수 있는 부분은 사실상 다 풀렸고, 남은 건 [[프로젝트/개인/한능검/기출 PDF 실측 2026-08-26|앞서 센]] 사진 문항과 같은 대상이다.

## 답지는 OCR이 필요 없다

문제지와 달리 **답지는 전 회차 텍스트 레이어가 살아 있다**(약 520자). 파싱하면 문항번호·정답·배점이 그대로 나온다.

```
1 ⑤ 1 | 11 ④ 2 | 21 ① 3 | 31 ④ 2 | 41 ② 2
2 ② 3 | 12 ③ 1 | 22 ④ 2 | 32 ③ 2 | 42 ① 2
```

## 그래서 무엇이 정해졌나

**① 제품의 상한이 열렸다.** 전 회차를 데이터로 만들 수 있다. 1위가 38회부터 보유한 것과 경쟁 가능한 범위다.

**② 파이프라인 구조가 확정됐다.**
```
문제지 PDF ─┬─ 텍스트 레이어 있음 → 직접 추출
            └─ 없음 → 300dpi 렌더 → Vision OCR → 선지 복원 후처리
답지 PDF ───── 텍스트 추출 (OCR 불필요) → 정답·배점
```

**③ 남은 작업은 OCR이 아니라 검수다.** 92~96%는 **자동화 상한**이지 최종 품질이 아니다. `윤충→윤중` 같은 인명 오독이 실제로 나오고, **한능검은 인명·연호가 정답을 가르는 시험**이라 그대로 내보내면 안 된다. 1위 앱이 *"해설 오류"*로 1★을 받는 지점이 정확히 여기다.
→ **검수 UI를 초기에 만든다.** OCR 결과와 원본 이미지를 나란히 놓고 빠르게 고치는 도구. 이게 실질적인 콘텐츠 생산 속도를 결정한다.

**④ 비용 구조가 유리하다.** 로컬 처리라 회차가 늘어도 비용이 0이고, 재처리도 자유롭다. 클라우드 OCR API를 쓰면 회차마다 과금되고 재처리를 망설이게 된다.

## 도구

`한능검/tools/`에 저장했다 — `ocr.swift`(Vision 래퍼), `pipe.py`(PDF→구조화), `eval2.py`(정답 대조). 빌드는 `swiftc -O -o ocr ocr.swift` 한 줄.
