# 검수 파이프라인 — 기출 PDF에서 문항 데이터까지

[[프로젝트/개인/한능검/마일스톤 0 — OCR 실측 2026-08-26|마일스톤 0]]에서 *"남은 병목은 OCR이 아니라 검수"*로 결론이 났고, 그 도구를 만들었다. **심화 7회차(73~79) 348문항이 데이터가 됐다.**

## 결과

| 회차 | 문항 | 선지 5개 | 정답 |
|---|---|---|---|
| 79 · 78 · 77 · 76 | 50씩 | 44 · 45 · 47 · 45 | 50씩 |
| 75 | 48 | 44 | 48 |
| 74 · 73 | 50씩 | 46 · 46 | 50씩 |
| **합계** | **348** | **317 (91%)** | **348 (100%)** |

75회만 48문항이다 — 2문항을 못 잡았고 검수에서 채운다.

## 구조

```
문제지 PDF ─→ 300dpi 렌더 ─→ Vision OCR(좌표 포함) ─┐
                                                    ├─→ 문항 단위 JSON + 문항별 이미지 조각
답지 PDF ───→ 텍스트 추출 ─→ 정답·배점 ─────────────┘
                                                          ↓
                                                    검수 UI (단일 HTML)
```

- `tools/ocr.swift` — Vision 래퍼. `--json`으로 **줄마다 텍스트 + 정규화 bbox + 신뢰도**를 뱉는다. 이 좌표가 문항별 이미지 조각을 만드는 근거다
- `tools/build.py` — 페이지 OCR → 문항 경계 판정 → 선지 복원 → 원본에서 문항 영역만 다시 렌더 → JSON
- `review.html` — 검수 UI. 빌드 없는 단일 파일

## 만들면서 밟은 함정 넷

**① `'①'.isdigit()`가 파이썬에서 `True`다.** 원문자를 숫자로 취급해서 답지 파서가 `int('①')`로 죽었다. `s.isascii() and s.isdigit()`로 막아야 한다. **유니코드 숫자류(원문자·전각·한자 숫자)가 전부 여기 걸린다.**

**② 답지 형식이 회차마다 다르다.** 74~79회는 정답을 원문자(`③`)로 쓰는데 **73회는 일반 숫자(`3`)로 쓴다.** 원문자만 받는 파서는 73회에서 정답 0개가 나왔다. 둘 다 받되, 전부 숫자면 (문항, 정답, 배점) 삼중 정렬이 애매해지므로 **앞머리 잡음을 건너뛰며 오프셋을 옮겨 가장 많이 매칭되는 정렬을 고른다.**

**③ 선지 복원에 off-by-one이 있었다.** 검증 스크립트는 `blk[st:en+1]`인데 빌드 코드는 `block[st:en]`이라, 같은 로직인데 인식률이 92% → 24%로 떨어졌다. **검증본과 구현본이 갈리면 이런 게 조용히 생긴다.**

**④ 문항이 50개를 넘게 잡혔다.** 배점 표기(`[1점]`)가 `1.`처럼 읽히는 등으로 같은 번호가 중복됐다. 번호별로 **(선지 수, 정답 유무, 본문 길이)** 가 가장 그럴듯한 것만 남겨 해결.

## 검수 UI 설계 — 속도가 전부다

348문항을 사람이 훑어야 하므로 **클릭 수와 이동 비용**이 도구의 가치를 결정한다.

- **왼쪽 원본 이미지 조각, 오른쪽 편집 폼.** 문항 영역만 잘라 놓아서 페이지에서 눈으로 찾을 필요가 없다
- **`⌘↵` = 검수 완료 + 다음 미검수로 점프.** 순차 이동이 아니라 **건너뛰기**라 이미 본 문항을 다시 지나지 않는다
- **`⌘1~5`로 정답 지정.** 마우스 없이 끝난다
- **「문제만」 토글** — 손볼 게 있는 미검수 문항만 순회. 91%가 이미 멀쩡하므로 나머지 9%에 시간을 쓴다
- **입력 즉시 localStorage 저장.** 저장 버튼이 없다 — 누르는 걸 잊는 사고가 구조적으로 안 생긴다
- **플래그로 의심 지점을 미리 지목한다**: 선지 부족(빨강) · 선지 복원됨 · 한자 포함 · 신뢰도 낮음 · 정답 없음

> [!tip] 플래그가 검수의 핵심이다
> OCR이 91% 맞다는 건 **9%를 사람이 찾아야 한다**는 뜻인데, 348문항을 눈으로 훑어 찾는 건 비현실적이다. **어디가 의심스러운지 기계가 먼저 지목**해야 검수가 성립한다.
> 특히 `선지 복원됨`은 인식률을 두 배로 올린 후처리가 만든 것이라 **틀렸을 때 조용히 틀린다** — 순서가 한 칸 밀려도 문장은 멀쩡해 보인다. 그래서 복원된 문항은 전부 플래그를 단다.

## 사진 선지 문항이 눈으로 확인됐다

79회 11번(`(가) 국가의 문화유산으로 옳은 것은?`)의 이미지 조각을 열어 보니 **선지 5개가 전부 유물 사진**이었다. [[프로젝트/개인/한능검/기출 PDF 실측 2026-08-26|앞서 육안으로 센]] 사진 문항과 정확히 같은 대상이고, 검수 UI가 `선지 0/5 · 사진 선지 가능` 플래그로 자동 지목한다.

**이 문항들의 처리 방침은 아직 미정이다** — v1에서 제외할지, 이미지를 공공누리 1유형으로 조달할지. 검수를 돌리면서 실제 개수를 확인하고 정한다.

## 정정 — 검수를 사람이 하는 설계가 틀렸다 (2026-08-26 같은 날)

홍이 **"검수를 내가 해야 하는 거야?"**라고 물었고, 맞는 지적이었다. **348문항을 손으로 훑는 도구를 먼저 만든 게 순서 착오다.**

### 실제로 모델이 할 수 있다 — 검증했다

OCR이 선지를 **0개** 잡은 79회 24번의 페이지 이미지를 열어 보니 선지 5개가 명확히 읽혔다.

> ① 업무 일지인 내각일력을 작성하였다. ② 을묘왜변을 계기로 상설 기구화되었다.
> ③ **은대(銀臺), 후원(喉院)**이라고도 불렸다. ④ 대제학을 수장으로 하였으며 경연을 주관하였다.
> ⑤ 5품 이하의 관리 임명에 대한 서경권을 행사하였다.

**OCR이 전혀 못 읽는 한자(`銀臺`·`喉院`)까지 나온다.** 답지의 정답이 ③(승정원)과도 맞는다.

### 그리고 crop 설계도 이것 때문에 바뀐다

문항별로 자른 이미지는 **사람 검수용**이었다. 실제로 24·40번처럼 **문항이 컬럼 경계를 넘으면 잘린다** — 구조적 한계다. 그런데 모델에게는 **페이지를 통째로 주면 되고, 그러면 잘림 문제가 아예 없다.**

> [!note] crop 버그는 별개로 고쳤다
> 같은 문항이 중복 검출될 때 **같은 파일명으로 서로 덮어써서** 1페이지 문항들이 51~93px로 잘려 있었다. 중복 제거를 끝낸 뒤에 렌더하도록 바꿔 **잘림 의심이 12개 → 3개**로 줄었고, 남은 3개는 전부 사진 선지 문항이다.

### 자동 검수 파이프라인 (`tools/verify.py`)

페이지 이미지(150dpi) + 그 페이지의 OCR 결과를 함께 주고, **이미지를 정답으로 삼아** 교정된 문항 데이터를 구조화 출력(`output_config.format`)으로 받는다. **Batch API**라 표준가의 50%다.

프롬프트에 OCR이 실제로 틀리는 지점을 명시했다 — 선지 원문자 누락으로 인한 **순서 밀림**, 한자 미인식, **인명 한 글자 오독**(`윤충`→`윤중`), 삽화 글자 혼입. 특히 *"한국사는 인명이 정답을 가른다"*를 근거로 준다.

| 모델 | 표준 | **Batch (50%)** |
|---|---|---|
| Claude Opus 5 | $5.50 | **$2.75** |
| Claude Sonnet 5 | $2.20 | $1.10 |

**348문항 전체 검수가 약 4천원이다.** 사람이 몇 시간 쓰는 것과 비교가 안 된다.

### 검수 UI의 역할이 바뀌었다

전수 검수 도구 → **모델이 고친 것만 확인하는 도구**. `verified`·`corrections`·`choicesAreImages`가 붙으면 UI가 그것만 띄운다.

사람이 볼 것은 셋뿐이다 — ① **모델이 고쳤다고 표시한 문항** ② **선지가 사진인 문항** ③ **정답이 빈 문항**. 모델이 "이상 없음"이라 한 건 건너뛴다.

> [!tip] 도구를 만들기 전에 물었어야 했다
> *"이 일을 사람이 해야 하나?"* 를 안 물어서 전수 검수 UI를 먼저 만들었다. 검수 UI 자체는 버려지지 않았지만(역할이 좁아졌을 뿐) **순서가 틀렸다** — 자동화 가능성을 먼저 따지고, 남는 것에만 도구를 붙였어야 한다.
