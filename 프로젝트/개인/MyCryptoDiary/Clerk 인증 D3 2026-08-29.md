## 결정

- **`proxy.ts`** — Next 16에서 `middleware.ts`가 개명됐다. matcher는 정적 확장자·`_next`를 부정 look-ahead로 빼고, `/(api|trpc)(.*)`와 `/__clerk/:path*`는 반대로 포함시킨다.
- **`ClerkProvider`는 `app/layout.tsx`**, 로그인 UI는 **`widgets/header`**. 헤더가 전 페이지에 나오므로 layout에 UI를 두지 않았다.
- **`app/sign-{in,up}/[[...]]/page.tsx`는 `_pages` 슬라이스를 만들지 않고 `app/`에만** 뒀다. 내용이 우리 것이 아니라 Clerk 컴포넌트 하나라 옮겨봐야 한 줄 파일만 늘어난다. D1의 라우트 스텁 6개와 같은 판단.
- **`entities/account`** — 계좌는 명사이고 DB(바깥 저장소)에서 가져오므로 `entities/<name>/api/`. `entities/coin`이 업비트에서 가져오는 구조와 같다.
- **계좌 lazy create** — 트랜잭션 안에서 `users` → `accounts`를 FK 순서로 `ON CONFLICT DO NOTHING` 삽입한 뒤 계좌를 조회한다. 별도 "존재 확인 → 삽입"은 동시 요청 사이에 틈이 생기지만, PK 충돌을 DB에 맡기면 같은 사용자의 계좌가 둘 생기지 않는다. 기존 계좌를 update하지 않아 재호출이 잔액을 1,000만원으로 초기화하지 않는다.
- **보호 경계는 `(protected)` Route Group의 공통 layout**에 뒀다. 설치된 Clerk v7 타입에서 `createRouteMatcher`가 deprecated라 경로 문자열 목록을 proxy에 중복하지 않았다. 괄호 폴더는 URL에 나타나지 않아 `/market` 같은 주소는 유지된다. 공개 범위는 홈·로그인·회원가입·공개 시세 API다.
- **표시명 `CoinPilot`** — `app/layout.tsx` metadata의 이름을 그대로 채택했다. 저장소·위키 폴더를 일괄 변경하는 비용은 제품 표시명 결정과 분리했다.

## 밟은 지뢰

**Clerk v7(Core 3)에서 `SignedIn`/`SignedOut`/`Protect`가 제거됐다.** `removedControlComponents`에서 export되지만 쓰면 런타임 에러를 던진다 — 이름 자체가 안내판이다. 대체는 **`<Show when="signed-in" fallback={...}>`**. 조건이 맞으면 children, 틀리면 fallback.

> 중요한 점: 이 에러는 **`tsc`와 `npm run dev`를 통과하고 `npm run build`에서만** 났다. 타입은 살아 있고 런타임에만 던지기 때문이다.

**`matcher: []`는 미들웨어를 한 번도 실행시키지 않는다.** 파일이 있고 문법이 맞고 빌드가 통과하고 화면도 정상이라 "잘 된다"고 판단했지만 아무 일도 하지 않고 있었다. 확인법은 `npm run build` 출력의 **`ƒ Proxy (Middleware)`** 줄 — 비어 있으면 이 줄이 없다.

**`useAuth`(훅)와 `auth()`(서버 함수)의 갈림길.** `index.d.ts` 맨 아래 `export declare const auth: never`가 안내판이고, 주석에 `@clerk/nextjs/server`에서 가져오라고 diff까지 적혀 있다. 결정 기준은 단순하다 — `getDB()`가 `import 'server-only'`라 클라이언트 컴포넌트에 들어갈 수 없으므로 이 함수는 서버여야 하고, 서버에선 훅을 못 쓴다.

**타입 파일 하나와 패키지 export 목록은 다르다.** `auth`에 Cmd+클릭하면 `auth.d.ts`만 열려 `currentUser`가 안 보였지만, `@clerk/nextjs/server`의 `index.d.ts`는 둘을 함께 재수출한다. 같은 import에 `currentUser`를 추가하고 다시 Cmd+클릭해 `Promise<User | null>`을 확인했다.

**TypeScript는 Next의 파일 규약을 모른다.** 보호 layout을 named export로 작성해도 `tsc`는 통과했다. Next가 layout으로 읽으려면 default export여야 한다는 것은 `next build`와 실제 라우팅으로 검증해야 한다.

## 검증

- `tsc` / `eslint`(경고 0) / `steiger` 위반 0 / `next build` 통과
- 실제 가입 → 로그인 → 아바타 표시 확인. Clerk 관리 API 조회로 유저 1명 확인
- **번들 실측**: 빌드 후 `.next/static`에서 publishable key는 **1개 파일에서 발견**, secret key는 **0개**. `NEXT_PUBLIC_`이 "허가"가 아니라 "번들에 박으라는 명령"임을 눈으로 확인했다
- Neon Studio에서 Clerk 사용자와 1,000만원 계좌가 같은 ID로 생성됨을 확인했다. 홈 재호출 뒤에도 행 수·잔액이 변하지 않았다.
- 로그아웃 홈 접근, 로그아웃 `/market`·`/settings` 로그인 이동, 로그인 후 보호 화면 접근을 확인했다.
- 최종 `tsc`·ESLint·Steiger·Next production build 통과. 빌드 출력에 `ƒ Proxy (Middleware)`와 보호 라우트의 동적 렌더링이 표시됐다.
