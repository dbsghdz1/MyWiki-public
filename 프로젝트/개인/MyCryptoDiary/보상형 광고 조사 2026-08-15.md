# MyCryptoDiary 보상형 광고(rewarded ads) 조사

"광고를 보면 가상 원화를 충전해준다"를 실제 광고로 구현할 수 있는지 조사했다. 모든 정책 인용은 Google 공식 도움말·개발자 문서에서 직접 확인했고, **2026-08-15 기준**이다. 출처: Claude 대화, 2026-08-15.

## 결론

- **일반 AdSense 광고에 보상을 붙이면 계정이 정지된다.** 정식 경로는 신청제인 H5 Games Ads뿐인데, 승인된 AdSense 계정이 선행 조건이고 사실상 게임 전용이라 이 프로젝트가 통과할지 불확실하다.
- **트래픽 0인 지금 승인받을 수 있는 웹 보상형 네트워크는 사실상 없다.** 진짜 보상형 영상을 주는 곳은 전부 DAU·신청·포털 배포 중 하나로 막혀 있다.
- **따라서 지금은 mock provider로 흐름만 구현한다.** 실제 네트워크 연동은 후순위이며, 포트폴리오 가치는 광고 태그가 아니라 provider 추상화 + 서버 소유 잔액 설계에서 나온다.

## AdSense 정책: 2단계 구조

일반 디스플레이 광고는 인센티브가 **전면 금지**다.

> "Publishers are not permitted to encourage users to click on Google ads in any way."
> "Offering compensation or any incentive for clicks on ads is strictly prohibited."
> — [광고 게재위치 정책](https://support.google.com/adsense/answer/1346295)

"클릭"뿐 아니라 **"시청"도 명시적으로 포함**되고, 제재 수위는 계정 폐쇄다.

> "Publishers may not ask others to refresh or click their ads. This includes asking for users to support your site, YouTube channel, or app, **offering rewards to users for viewing or clicking on ads**…"
> — [계정 폐쇄로 이어지는 위반](https://support.google.com/adsense/answer/2660562)

반면 **승인된 보상형 광고 유닛**에는 별도 정책이 있고, 여기서는 가상 재화가 허용된다.

> "Direct monetary items may not be offered as rewards under any circumstance."
> "Indirect or non-monetary items may be offered as rewards, provided that: The reward is only redeemable and usable for an item or service within the publisher's platform, website or app; The reward is non-transferable…"
> — [Policies for ad units that offer rewards](https://support.google.com/adsense/answer/9121589) (Ad Manager 동일본: [admanager/answer/7496282](https://support.google.com/admanager/answer/7496282))

같은 정책이 요구하는 것: 사전 고지, **명시적 옵트인**("affirmatively and unambiguously opts in"), 건너뛰기 가능, 완료 시 보상 지급 보장.

**해석**: 현금화·양도 불가한 앱 내부 전용 가상 원화는 "indirect or non-monetary item"에 해당해 정책상 문제없다. **단 승인된 보상형 포맷을 거칠 때만** 그렇다. 이 정책은 특정 제품에 붙는 권한이지 일반 유닛을 인센티브화해도 된다는 허가가 아니며, 일반 AdSense for content에는 그냥 켤 수 있는 보상형 포맷이 없다.

## 제품별 가능 여부

| 제품 | 웹 보상형 | 진입 조건 | 판정 |
|---|---|---|---|
| AdSense 일반 유닛 | 없음 | — | 인센티브 금지, 계정 폐쇄 위험 |
| [H5 Games Ads / Ad Placement API](https://developers.google.com/ad-placement/docs/signup) | 있음 | 승인된 AdSense 계정 + 신청 승인, 사실상 게임 전용 | 정식 경로지만 승인 불확실 |
| [Ad Manager 보상형 (GPT)](https://support.google.com/admanager/answer/9116812) | 있음, 게임 제한 없음 | AdSense 계정 필수 + 사실상 대형 게시자 대상 | 현재 불가 |
| [AdSense Offerwall](https://support.google.com/adsense/answer/13865318) | 있음 | 별도 신청 불필요 | **보상이 "콘텐츠 접근권"으로 고정** — 가상화폐 대체 불가 |

**H5 Games Ads는 2026-06-18 문서 갱신 기준 여전히 살아 있다**(종료 공지 없음). API 형태는 `adConfig()` + `adBreak({type:'reward', beforeReward, adViewed, adDismissed, ...})`이고, `beforeReward`가 넘겨주는 `showAdFn`을 사용자 제스처에서만 호출하게 해 옵트인을 기술적으로 강제한다 — [예제 구현](https://developers.google.com/ad-placement/docs/example).

> [!warning] 미해결 — 이 프로젝트가 "H5 게임"인가
> 모의투자 시뮬레이터가 H5 Games Ads의 게임 요건에 해당하는지 확정적 근거를 찾지 못했다. 브라우저 기반 비-현금 시뮬레이션이라 게임적 요소는 있으나 통상적 의미의 게임은 아니고, 승인은 Google 재량("Google reserves the right to approve or deny any publisher's participation")이다. AdSense 커뮤니티에는 두 승인이 서로 어긋난 사례가 양방향으로 존재한다. 어차피 AdSense 승인 전에는 신청 불가이므로 후순위.

## AdSense 승인 요건

- 만 18세 이상, "content must be high-quality, original, and **attract an audience**" — [eligibility](https://support.google.com/adsense/answer/9724)
- **최소 트래픽 기준은 공개된 것이 없다.** 실질 기준은 양이 아니라 콘텐츠 품질이다.
- 심사 기간: "usually takes a few days, but in some cases can take 2-4 weeks" — [사이트 추가](https://support.google.com/adsense/answer/12169212)
- 사이트는 실제 배포되어 공개 접근 가능해야 하고 검증 스니펫이 서빙 HTML에 있어야 한다.

### vercel.app 서브도메인 — 통념이 틀렸다

[사이트 관리 문서](https://support.google.com/adsense/answer/12170421)는 등록 가능한 사이트를 이렇게 규정한다.

> "Going forward, you'll only be able to add the following as 'sites' in AdSense:
> - Domains (e.g., website.com, website.net)
> - **Subdomains on platforms that are already part of the public suffix list** (e.g., site.appspot.com).
> - Sites that are managed by AdSense platform partners (e.g., site.blogspot.com)"

Public Suffix List 원본을 직접 받아 확인한 결과 `vercel.app`은 **등재되어 있다**(`github.io` 13783행, `netlify.app` 14808행, `vercel.app` 16172행). 즉 `myapp.vercel.app`은 그 자체가 루트 도메인으로 취급되어 구조적으로 등록 가능하고, `ads.txt`도 `myapp.vercel.app/ads.txt`가 올바른 위치다.

> [!warning] 근거 충돌 — vercel.app 승인 가능 여부
> - 주장 A: 구조적 이유로 거절된다 — DEV Community "Why Google AdSense will not approve a *.vercel.app site"
> - 주장 B: PSL 등재 서브도메인은 등록 가능하다 — Google 공식 [adsense/answer/12170421](https://support.google.com/adsense/answer/12170421) + PSL 원본 확인
> - 현재 판단: **B가 근거가 더 강함.** A는 PSL 서브도메인 케이스와 "남의 비-PSL 도메인의 서브도메인"(막힘)을 혼동한 것으로 보인다. 다만 무료 플랫폼 서브도메인은 심사자에게 저품질 신호로 읽히므로, 커스텀 도메인이 가장 저렴한 리스크 제거 수단이다
> - 검토일: 2026-08-15

### 금융 콘텐츠 리스크

- **도박 규정은 해당 없음.** [Publisher Restrictions](https://support.google.com/publisherpolicies/answer/10437795)는 "real-money gambling"만 제한한다. 실제 돈을 걸지도 따지도 않으므로 무관.
- **진짜 위험은 "low value content" + YMYL이다.** 금융은 YMYL 범주라 더 높은 E-E-A-T 기준으로 평가된다. UI만 있고 읽을거리가 없는 시뮬레이터는 전형적 거절 사유. 대응: 시뮬레이션임을 명시, About·개인정보처리방침·이용약관·문의 페이지, 그리고 실제 오리지널 콘텐츠(매매일지 기능 활용).

## 비-Google 대안 (승인 난이도 순)

- **AppLixir** — 웹 보상형 영상 특화, 게임 전용 아님, 공유 시크릿 MD5 서명 서버 콜백 보유. **하지만 최소 5,000 DAU 요구.** 아키텍처 참고용으로는 최고.
- **Monetag** — 트래픽 최소 없음, 승인 빠름, `ymid`로 프론트↔백엔드를 잇는 **실제 S2S 포스트백** 제공. 단 보상형 SDK 문서가 전부 "for TMA"(텔레그램 미니앱)로 표기 — 일반 웹사이트 공식 지원 여부 불명, 문의 필요.
- **Adsterra** — 승인 쉬움. 그러나 popunder·배너 위주로 **진정한 보상형 영상 상품이 없다.**
- **GameDistribution / GameMonetize** — 장벽 낮으나 자기 포털에 게임 배포하는 모델이고 HTML5 게임 전용. 보상 지급이 **전적으로 클라이언트 사이드, 서버 검증 없음.**
- **AdinPlay(Venatus)** — 기성 게임 포털 대상. 현실성 없음.

## 핵심 발견 — 웹에는 SSV가 없다

Ad Manager 문서 원문:

> "**Server-side verification is an app only feature and it is unavailable for web use.**"
> — [admanager/answer/9116812](https://support.google.com/admanager/answer/9116812)

H5 Games Ads / Ad Placement API 문서 어디에도 서버 검증 언급이 없다. `adViewed`는 서명 없는 순수 브라우저 콜백이다. GameDistribution도 클라이언트 전용.

**즉 웹에서 Google 제품을 쓰면 보상 획득을 암호학적으로 증명할 수 없다.** 조사한 네트워크 중 웹 보상 검증을 실제로 제공하는 곳은 AppLixir(서명 웹훅)와 Monetag(S2S 포스트백)뿐이다. "Google이 정석"이라는 통념이 뒤집히는 지점.

참고로 앱(AdMob) SSV의 정본 흐름 — 우리가 흉내 낼 형태다:
표시 전 클라이언트가 `custom_data`/`user_id`를 붙이고 → 완료 시 **Google 서버가** 콜백 URL로 GET(`reward_amount`, `reward_item`, `transaction_id`, `signature`, `key_id` 등) → 서버가 `gstatic.com/admob/reward/verifier-keys.json`의 ECDSA 공개키로 서명 검증(24시간 이하 캐시) → `transaction_id`로 멱등 처리. Google 권장 패턴은 **"클라이언트 콜백으로 즉시 보상 표시, 서버 콜백 수신 시 검증"** — 낙관적 UI, 권위는 서버. [admob/android/ssv](https://developers.google.com/admob/android/ssv)

## 결정 — 지금 무엇을 만드는가

**provider 인터페이스 + mock 구현으로 간다.** 차선책이 아니라 올바른 선택인 이유:

1. 오늘 어디서도 승인받을 수 없다.
2. 후보들의 API 형태가 전부 다르다(`adBreak` vs GPT 슬롯 이벤트 vs `show_XXX().then()` vs AppLixir 상태 콜백) — 어차피 seam이 필요하다.
3. 실제 연동 후에도 로컬 개발·CI·데모용 mock이 필요하다. 보상형 광고는 localhost에서 fill되지 않는다.
4. 포트폴리오로서 붙여넣은 광고 태그보다 교체 가능한 추상화가 설계 역량을 보여준다.

### 인터페이스에 반드시 넣을 것 (실제 제공자들의 합집합)

- `isAvailable()` / 로드 단계 — 실제 네트워크는 **보여줄 광고가 없는 경우가 흔하다.** 가장 많이 빠뜨리는 케이스. GPT는 조건 미충족 시 `defineOutOfPageSlot()`이 `null`을 반환하고 Offerwall도 수요 부족 시 "won't render"다. mock도 no-fill을 반환할 수 있어야 한다.
- **사용자 제스처에서만 호출 가능한** `show()` — 취향이 아니라 정책 요구사항.
- 구분된 종료 상태: **완료 / 사용자 취소 / 오류 / no-fill.** 취소를 오류로 뭉개지 않는다(정책상 취소는 불이익 없어야 함).
- 넣고 되돌려받는 **불투명 상관관계 토큰** — `custom_data`/`ymid`가 들어갈 자리를 지금 시그니처에 만들어 둔다.
- 빈도·쿨다운은 provider가 아니라 **도메인 레이어**에.

### mock이 진짜로 지켜야 할 것

현재 저장소는 클라이언트 전용(API route·DB 없음)이라 잔액이 클라이언트에 있다. → 08-18 갱신: Route Handler(`app/api/upbit/ticker`) 도입, DB는 D2(Neon+Drizzle) 진행 중. **잔액이 클라이언트에 있는 한 보상은 이미 위조 가능하고 SSV 논의는 무의미하다.**

1. **잔액을 서버로 이동.** 클라이언트는 잔액을 설정할 수 없고 적립을 요청만 한다.
2. **서버 발급 nonce 2단계.** 광고 전 `POST /api/reward/session` → 사용자에 묶인 단기·1회용 토큰 발급(`pending`). 그 토큰을 `show()`의 상관관계 ID로 전달. 완료 시 `POST /api/reward/claim`에 실어 보내고 서버가 미등록·만료·사용됨·사용자 불일치를 거부.
3. **transaction ID 기반 멱등성** — 사용된 토큰을 고유 키로 저장해 재전송 시 적립 0.
4. **서버 측 rate limit + 일일 한도** — 오늘 웹에서 남용을 막는 사실상 유일한 방어. 광고가 가짜여도 이 부분은 진짜여야 한다.
5. **세션 발급~claim 최소 경과 시간 강제** — "광고가 실제로 재생됐다"의 정직한 대응물.
6. **mock이 궂은 경로를 시뮬레이션** — no-fill, 3초 취소, 네트워크 오류, 성공. 네 가지 모두 처리하는 UI를 만든다.
7. **`verifyCallback` seam** — `/api/reward/ssv` 핸들러를 빈 채로 남겨둔다. 제공자 교체 시 `claim`이 낙관적 UI 전용이 되고 포스트백이 pending을 `granted`로 뒤집는다.

이렇게 하면 mock → 실제 provider 교체가 파일 하나 + route handler 하나로 끝나고, 보안 모델은 처음부터 계속 올바르다.

## 진행 순서

1. **지금**: provider 인터페이스 + mock + 서버 소유 잔액 + nonce/멱등성/rate limit. UI에 데모임을 명시.
2. **병행(저비용)**: 커스텀 도메인 + About·개인정보처리방침·이용약관 페이지. 어느 경로든 필요하고 vercel.app 의문을 없앤다.
3. **콘텐츠·트래픽 생긴 뒤**: 일반 AdSense 신청. 첫 시도 "low value content" 거절은 정상.
4. **AdSense 승인 후에만**: H5 Games Ads 신청. 안 되면 Monetag가 현실적 대안(검증은 오히려 더 낫다).
5. **절대 금지**: "보면 1000만원" 버튼 뒤에 일반 AdSense 유닛. 계정 정지는 프로젝트가 아니라 **본인 신원**에 묶인다.

**3~5번에 포트폴리오를 묶지 않는다.** 모의투자 거래소 2주 계획이 우선이고(실시간은 Phase 2), 이 기능은 mock 단계에서 이미 완결된 산출물이다.

## 재사용 가능한 부분 (허브 승격 후보)

다른 웹 프로젝트(예: [[프로젝트/개인/math-sprint/README|math-sprint]])에서 같은 주제가 또 나오면 아래를 `_wiki/` 허브로 뽑는다.

- AdSense 인센티브 금지 ↔ 보상형 유닛 예외의 2단계 구조
