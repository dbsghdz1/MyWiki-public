# D4 회고 — 왜 어려웠나 (2026-09-04)

D4(매수 엔진)를 마친 뒤 본인 요청으로 쓴 회고다. *"내가 어려워하는 이유와 이런 것들을 종합해서 수정을 하고 넘어가야 할 것 같아."*

## 실측

| 일차 | 계획 | 실제 | 배율 |
|---|---|---|---|
| D1 FSD + 업비트 | 6.5h | 4 작업일 | ~4x |
| D2 Neon + Drizzle | 6h | 3 작업일 | ~3x |
| D3 Clerk 인증 | 6h | 2 작업일 | ~2x |
| **D4 매수 엔진** | **6h** | **3 작업일**(9/2~9/4) | **~3x** |

배율이 D1 4배 → D3 2배로 내려갔다가 D4에서 3배로 올랐다. **기초 비용이 끝나서 내려간 것이 아니라, 일차마다 새 개념이 몇 개 들어오느냐에 따라 오르내린다.** D3는 Clerk가 대부분을 해줘서 낮았고, D4는 새 개념이 많아 다시 올랐다.

D4는 12블록으로 쪼개 진행했다(반올림 규칙 → 수수료 → 입력 방식 → `price` bigint화 → 주문금액 → 소수 문자열 변환 → Server Action 껍데기 → 가격 재조회 → 계산·잔고 검증 → 평균단가 → 트랜잭션 → 입력 검증·폼). 커밋 9개.

## 왜 어려웠나 — 네 가지

### ① 새 개념이 한 일차에 너무 많이 들어왔다

D4 하나에 처음 보는 것이 이만큼 있었다.

| 개념 | 어디서 |
|---|---|
| 고정소수점 (단위를 쪼개 정수로) | 수량 스케일링 |
| `bigint`와 `number`의 비혼합 | 전 구간 |
| 올림 나눗셈 | 수수료·주문금액·평균단가 |
| Server Action / `'use server'` | 매수 액션 |
| 신뢰 경계 (클라이언트를 안 믿는다) | 서버 가격 재조회 |
| DB 트랜잭션 | 저장 |
| upsert / 복합 PK | 보유 갱신 |
| SQL 식으로 차감 (`sql` 태그) | 현금 차감 |
| FSD `features` 계층 | 슬라이스 배치 |
| 정규식 입력 검증 | 폼 방어 |

**열 개다.** 계획서가 D4에 6시간을 잡은 것은 이 개념들을 이미 안다는 전제였다. 몰랐으므로 3배가 걸린 것이지 느려서가 아니다 — D1에서 이미 같은 결론을 냈고 D4에서 반복 확인됐다.

### ② 세 축이 겹쳐 보였다 (가장 큰 원인)

본인 말: *"자꾸 bigint number 어떤 건 소수 뭐 이런 게 헷갈리네."*

독립적인 축 셋이 대화에서 섞여 나왔다.

| 축 | 갈림 |
|---|---|
| JS 타입 | `number` / `bigint` |
| 값의 성격 | 정수 / 소수 |
| 쓰임 | 돈을 깎는다 / 화면에 그린다 |

특히 **"소수인데 `bigint`"**(수량을 10⁸ 곱해 정수화)가 낯선 지점이었다. 소수를 다루는 방법이 "`number`로 그냥 쓴다"와 "단위를 쪼개 정수로 만든다" 둘인데, 후자를 처음 만났다.

여기서 하루에 네 번 막혔고, 결국 [[학습/공부/CS/컴퓨터의 수 표현|공부 노트]]로 정리했다. **개념을 글로 정리한 뒤에는 같은 자리에서 막히지 않았다.**

### ③ 라이브러리 어휘를 모르는 것을 문법을 모르는 것으로 착각했다

본인이 스스로 짚은 지점: *"내가 트랜잭션을 할 때 `holdings.`을 해서 어떤 걸 선택해야 하는지 모르겠어서 그러네. **TS가 아니라서** 그러네."*

이게 정확한 진단이다. 막힌 것은 TypeScript가 아니라 **Drizzle의 어휘**였다. 그리고 결정적으로 **찾는 자리를 잘못 알고 있었다** — `holdings.`에는 컬럼만 있고 쿼리 메서드는 `db`/`tx`에 달려 있다. 동사가 먼저 오고 테이블은 인자다.

```
holdings.select()          ✗  이런 건 없다
tx.select().from(holdings) ✓
```

**이 착각이 있으면 자동완성도 도움이 안 된다.** 잘못된 곳에서 찾고 있으니 아무것도 안 나오고, 그러면 "내가 문법을 모르나" 쪽으로 생각이 간다.

### ④ 검증이 세 번 거짓말했다

이 프로젝트에서 반복된 패턴이다. **`tsc` 통과가 정답을 뜻하지 않는다.**

| 무엇 | `tsc` | 실제 |
|---|---|---|
| `calculateFee` 세 버전 | 통과 | 100만원에 20원 / 항상 +1 / 올림 안 됨 |
| `formatTradeVolume` | 통과 | 15억이 `"150000000억"` |
| 업비트 응답 타입 | 통과 | 타입은 `bigint`, 런타임 값은 `number` |
| `matcher: []` (D3) | 통과 | 미들웨어가 한 번도 실행 안 됨 |
| `db:seed` (D2) | 통과 | 바뀐 드라이버 코드를 아예 안 지나감 |

**타입 검사는 형태를 보고, 숫자와 실행 여부는 안 본다.** 확인 방법을 매번 새로 찾아야 했고, 그게 시간을 먹었다.

## 잘 된 것

- **블록 쪼개기가 효과 있었다.** D4를 12조각으로 나눴고, 막힌 지점이 매번 한 조각 안에 갇혔다. D2에서 테이블 6개를 한 번에 던졌을 때와 비교하면 회복이 빨랐다.
- **모든 계산 함수를 손계산으로 검증했다.** 수수료 10케이스, 주문금액 6, 평균단가 4, 변환 함수 각 7~9. **이 기댓값들이 그대로 D5 테스트가 된다** — 계획서의 "기댓값은 손으로 먼저 계산" 순서를 지켰다.
- **일부러 부수는 검증이 자리잡았다.** 잔고 부족·미로그인·입력 공격 12종을 실제로 발생시켜 확인했다. 트랜잭션은 롤백까지 확인했다.
- **본인이 리팩터링을 요구했다.** "if문이 편해, 보기에 직관적이라" — 트릭 한 줄 대신 읽히는 코드를 고른 판단이었고, 그 트릭에 실제로 버그가 둘 있었다.

## 고칠 것

### 1. 일차 시작 전에 "새 개념 목록"을 먼저 만든다

D4는 새 개념이 열 개였는데 들어가기 전에 그걸 몰랐다. 일차를 시작할 때 **이번에 처음 나오는 것이 몇 개인지 세어보면** 배율을 예측할 수 있고, 많으면 미리 쪼갤 수 있다.

계획서의 「📚」 줄이 그 역할을 하려 했지만 너무 압축돼 있다(D4는 "Server Actions, DB 트랜잭션, 신뢰 경계, 입력 검증" 넷으로 적혀 있었는데 실제로는 열이었다).

### 2. 막혔을 때 "무엇을 모르는지" 먼저 분류한다

D4에서 확인된 세 종류다. **종류가 다르면 해결법도 다르다.**

| 막힌 종류 | 예 | 해결 |
|---|---|---|
| **개념** | 왜 소수를 정수로 바꾸나 | 설명 → 공부 노트 |
| **어휘** | Drizzle에서 update를 어떻게 쓰나 | 찾는 자리를 알려주기 (`tx.` / 우리 코드 선례) |
| **오타·실수** | 괄호 누락, `[0]` 위치 | `tsc`·eslint가 잡는다 |

세 번째에 시간을 쓰지 않도록 **저장할 때마다 `tsc`를 돌리는 습관**이 유효했다.

### 3. 검증 명령을 블록마다 미리 정한다

"통과했다"가 아니라 **"무엇이 통과했다"**를 매번 물어야 한다. D4에서 실제로 쓴 것들:

| 확인할 것 | 명령 |
|---|---|
| 계산이 맞나 | 손계산 기댓값으로 케이스 표 돌리기 |
| 미들웨어가 도나 | `npm run build` 출력의 `ƒ Proxy (Middleware)` |
| 서버 함수가 불리나 | 터미널 로그(브라우저 콘솔 아님) |
| DB에 실제로 쓰이나 | 트랜잭션 안에서 읽고 `throw`로 롤백 |
| 값이 새는가 | 빌드 산출물에서 키 검색 |

### 4. 에이전트 쪽 — 블록 크기 기준을 매 턴 적용한다

[[프로젝트/개인/MyCryptoDiary/학습 계획 2026-08-28|학습 계획]]에 "결정 2개 이상 / 파일 2개 이상 / 화면 하나 초과면 쪼갠다"는 검사를 세워뒀는데, D4에서도 몇 번 어겼다(블록 5를 "결정 + 함수"로 묶어 던졌다가 중단됨). **기준을 적어두는 것과 매 턴 적용하는 것은 다른 일이다.**

## 측정 (학습 계획의 지표 4개)

| 지표 | D4 결과 |
|---|---|
| 블록 실행 횟수 | 9/2~9/4 3일에 12블록. 습관 트리거는 아직 미설정 |
| 예측 적중·누락 | **예측 단계를 거의 건너뛰었다** — 블록 루프 4번이 실행되지 않았다 |
| 에너지 1~10 | 기록 안 함 |
| 실측 배율 | 3x (D1 4 → D2 3 → D3 2 → D4 3) |

**넷 중 둘이 비어 있다.** 특히 예측은 학습 계획에서 "난이도 다이얼이자 계기판"이라고 정해둔 것인데 실제로 쓰이지 않았다. 다음 일차에서 이걸 실제로 돌릴지, 아니면 지표에서 뺄지 정해야 한다 — **적어두고 안 쓰는 지표는 없는 것과 같다.**

## 다음 (D5) 전에 정할 것

2. **습관 트리거 고정 시각** — 학습 계획의 미확정 1번이 아직 비어 있다
