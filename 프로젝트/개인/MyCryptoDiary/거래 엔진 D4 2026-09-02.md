# D4 — 거래 엔진 ① 매수 (진행 중)

브랜치 `feat/clerk-auth` 이어서. 계획서의 D4는 서버측 가격 재조회 → 잔고 검증 → 트랜잭션(현금↓·보유↑·주문기록)이고, 학습 포인트는 Server Actions·DB 트랜잭션·신뢰 경계·입력 검증이다.

## 결정

### 반올림 (2026-08-30)

README 「반올림 규칙」 절로 분리했다 — 유저가 내는 건 올림, 받는 건 내림. 최소 수수료 1원은 올림에서 자동으로 따라온다.

### 매수 입력은 **수량 기준**(A) (2026-09-02)

유저가 "0.001 BTC"처럼 **수량**을 입력하고 주문금액을 계산한다. 금액 기준(B, "10만원어치")도 실제로 쓰이지만 — 호가창·차트 거래 화면은 대개 수량 입력, 간편매수가 금액 입력 — 하나만 먼저 한다.

| | 수량 기준 (선택) | 금액 기준 |
|---|---|---|
| 계산 | 주문금액 = 가격 × 수량 | 수량 = 주문금액 ÷ 가격 |
| 정확한 쪽 | 받는 수량 | 내는 돈 |
| 자릿수 문제 | 소수 × 소수 → 자릿수 증가 | 나눗셈 결과를 8자리로 내림 |

### 가격은 **원화 정수만** 먼저 (2026-09-02)

`Coin.price`가 `number`(부동소수점)인 것을 `bigint`로 바꾼다. **D1 리뷰가 예고한 시점이 여기다** — *"`Coin.price`가 float인 것은 표시 전용이라 지금은 허용하되, D4에서 체결가로 넘기면 「float 절대 금지」 위반이 되므로 경계를 명시할 것"*. 화면에 그리는 데는 float이어도 되지만 잔고를 깎는 순간 안 된다.

업비트 원화 마켓은 BTC·ETH급이 정수 가격이고 **소수 가격은 저가 코인에만** 붙는다(도지코인 99.4원 등). 그래서 정수 가격 코인만 먼저 지원하고, 소수는 나중에 얹는다.

## 나중에 할 것 — 소수 가격 지원

**본인 결정(2026-09-02): 정수로 먼저 가고 소수는 나중에 추가한다. 좋은 경험이 될 작업이라 별도로 남긴다.**

소수 가격을 받으려면 **고정소수점 산술**이 필요하다. 실수를 "정수 + 정해진 배율"로 표현하는 방식이고, 금융 시스템이 float 대신 쓰는 표준 방법이다.

- 소수 문자열(`"99.4"`)을 배율 맞춘 정수로 파싱 (`994n`, scale 1 → 통일하려면 scale 8로 `9940000000n`)
- **곱셈은 배율이 곱해지고 나눗셈은 나뉜다** — 가격(scale 8) × 수량(scale 8) = 결과 scale 16. 원 단위로 되돌리려면 10^16으로 나누며 올림
- 파싱 엣지 케이스: 소수점 없음, 8자리 초과, 앞자리 0, 음수 거부
- 이때 `Coin.price`는 `bigint` 하나가 아니라 **값 + 배율** 쌍이거나, 전부 scale 8로 통일한 `bigint`가 된다

착수 시점: 매수·매도가 정수 가격으로 완주한 뒤. 저가 코인을 목록에 넣고 싶어지는 순간이 신호다.

### 타입 경계를 어디에 둘지 (2026-09-02, 블록 4)

`Coin.price`·`changePrice`는 `bigint`(돈을 깎는 값), **`tradeValue24h`는 `number`**(표시 전용)로 갈랐다. 기준은 "이 값으로 돈을 깎는가, 화면에 그리기만 하는가"다.

실제 업비트 응답을 넣어보고 정했다 — `acc_trade_price_24h`는 **5종 전부 소수**였다(체결마다 `가격 × 수량`이라 구조적으로 그렇다). 반면 가격은 BTC·ETH·XRP·DOGE·SOL이 전부 정수였고 **SHIB(0.00712원)만 소수**여서, "정수 가격 코인만 먼저"가 실제로 성립하는 것을 확인했다.

**변환은 `toCoin` 한 곳에서만.** 중간에 `shared/api/upbit/types.ts`의 응답 타입을 `bigint`로 바꿔 `tsc`를 통과시킨 적이 있는데, 업비트가 주는 건 JSON 숫자라 **런타임 값은 여전히 `number`**였다 — 컴파일러를 속인 상태였고 D4 계산에서 런타임 에러로 터졌을 것이다. D1에서 정한 경계("외부 응답 타입은 준 그대로, 변환 함수에서 우리 모델로")가 그래서 있었다.

**남은 것**: 가격이 소수인 코인이 목록에 들어오면 `BigInt()`가 `RangeError`를 던진다. 지금 목록엔 없지만 **시세가 변하면 생길 수 있다**(DOGE가 114원 → 99.4원이 되는 식). 거르든 그 카드만 죽이든 처리가 필요하다.

### 발견한 구멍 — 입력 검증이 아예 없다 (2026-09-04)

`buy`가 수량 문자열을 그대로 믿는다. `"0"`이 들어오면:

```
"0" → toScaleBigInt → 0n → 주문금액 0 → 수수료 0
    → 잔고 검증 통과(0원이니까)
    → calculateAvgBuyPrice에서 RangeError: Division by zero
```

`bigint`는 0으로 나누면 던진다. 그 밖에 음수·`"abc"`·`"1.2.3"`·소수점 8자리 초과도 막는 곳이 없다. 계획서 D4 학습 포인트에 **입력 검증**이 있는데 미착수 상태다.

**블록 8에서 폼과 함께 잡는다** — 지금 넣으면 조각이 커지고, 어차피 폼을 붙일 때 같은 검증을 화면 쪽에도 걸어야 한다.

### 평균단가 (2026-09-04, 블록 6d-1)

`entities/holding/model/avgBuyPrice.ts`. 배치 기준은 **"이 값이 어느 테이블에 저장되나"** — `avgBuyPrice`는 `holdings`의 컬럼이지 `orders`에 없다.

```
newAvg = (heldQty × heldAvg + buyQty × buyPrice) / (heldQty + buyQty)
```

수량의 10⁸ 스케일이 분자·분모에 함께 있어 **나누며 상쇄**되므로 별도 보정이 필요 없다. **나머지는 올림** — 평균단가가 높을수록 나중 실현손익이 작게 잡혀 「유저가 내는 건 올림」 원칙과 같은 방향이다.

검산 4건 통과. 특히 보유 0.001@1억 + 매수 0.003@2억 → **175,000,000**(단순 평균 150,000,000이 아니라 많이 산 쪽으로 끌린다).
