# 메인 스레드를 막는 것들

Fadeo 실기기 검증에서 "셔터를 누르면 걸린다 → 고쳤는데 또 걸린다 → 콜드 스타트도 걸린다"를 세 라운드에 걸쳐 잡으며 확인한 목록. **전부 API 이름만 봐서는 비싼 줄 모르는 것들이다.**

## 실측으로 확인된 블로커

| API | 비용 | 함정 |
|---|---|---|
| `AVAudioSession.setActive(true)` | 수십~수백 ms (미디어 서버와 **동기 IPC**) | 재생 함수 안에 넣으면 소리 낼 때마다 낸다. **세션은 시작 때 한 번만, 전용 큐에서** 활성화. `AVAudioPlayer`는 메인을 요구하지 않는다 |
| `CHHapticEngine.start()` | 동기 | `isAutoShutdownEnabled = true`면 쉬던 엔진을 **재생 때마다 다시 깨운다** — 절전 옵션이 매번의 블록으로 돌아온다. 패턴 생성·시작을 전용 큐로 |
| `Data.write(options: .atomic)` | 1~2MB에 수십 ms | 셔터 콜백처럼 "즉시 반응해야 하는 자리" 바로 뒤에 오면 체감상 버튼이 걸린 것으로 읽힌다. 인코딩(메모리)과 쓰기(IO 큐)를 나눈다 |
| `AVCaptureSession` 구성 (`beginConfiguration`~`commit`) | **100~300ms** (렌즈 탐색+포맷 선택 포함) | 콜드 스타트 최대범. Apple 권고대로 **세션 전용 큐**에서 구성하고 `@Published`만 메인에서 갱신 |
| `CIContext(mtlDevice:)` 생성 | 수십 ms | 첫 프리뷰가 붙는 순간 청구된다. `static let`으로 묶어 **앱 시작 때 백그라운드에서 선생성** (static let 초기화는 스레드 안전) |
| lazy 초기화 전반 (텍스처 생성 등) | 각각은 작아도 합산 | "미리 데우기"를 메인 `.task`에서 하면 **데우기가 콜드 스타트를 늘린다.** `Task.detached`로 — 단 스레드 안전한 것만 |

## 순서 있는 파일 쓰기는 직렬 IO 큐 하나로

`DispatchQueue(label:, qos: .utility)` 직렬 큐면 쓰기 순서가 호출 순서 그대로 보존된다. 인덱스 저장처럼 "마지막 쓰기가 이기면 되는" 것에 정확히 맞는다.

## 블록을 없애면 드러나는 2차 버그 ★

**메인이 한가해지면 타이밍에 기대던 코드가 깨진다.** Fadeo에서는 화면 삽입 직후 `.task`의 `withAnimation`이 삽입과 같은 트랜잭션에 합쳐지며 애니메이션이 통째로 사라졌다 — 전에 움직였던 것은 오디오 블록이 두 트랜잭션 사이에 시간을 벌어준 **우연**이었다. 해법은 [[작업노트/Apple/SwiftUI|SwiftUI]] 2026-08-27 항목(시계 기반 이동).

**규칙: 성능을 고치면 "그동안 우연히 되던 것"이 무엇이었는지 의심하라.**

## 네 번째 라운드는 계측으로 끝났다 — 범인이 메인이 아니었다 ★★

2026-09-02, Fadeo 출시 후 "콜드 스타트에 화면이 멈춰 있다, 진짜 메인 블록 같다"는 보고.
아래 `## 진단 요령`에 *"다음엔 추측 대신 계측"*이라 적어 둔 그 상황이 다시 왔고, 이번엔 그대로 했다.
**계측이 가설을 뒤집었다. 메인은 막혀 있지 않았다.**

### 두 가지만 찍으면 된다

1. **프로세스 exec 시각 기준 경과 ms** — `sysctl(CTL_KERN, KERN_PROC, KERN_PROC_PID)`의 `kp_proc.p_starttime`.
   dyld·정적 초기화까지 포함돼서 **"앱 코드가 늦는지, 그 앞이 늦는지"**가 갈린다. `main()` 안에서 잡은 기준점으로는 안 보이는 구간이다.
2. **메인이 실제로 막힌 구간** — 백그라운드 스레드에서 `DispatchQueue.main.sync {}`를 반복하고 **그 호출이 돌아오는 데 걸린 시간**을 잰다.
   어느 함수인지는 모르지만 "언제 얼마나"는 정확하고, 마크와 대조하면 구간이 좁혀진다. 샘플링 프로파일러 없이 CLI만으로 된다.

**Debug 빌드로 재면 안 된다.** 같은 구간이 Debug 200ms / Release 98~149ms로 두 배 차이 났다 — SwiftUI body 평가가 최적화에 크게 좌우된다.
`xcodebuild -configuration Release SWIFT_ACTIVE_COMPILATION_CONDITIONS="DEBUG"`로 **최적화는 켜고 계측 코드만 살린다.**

### 실측 (iPhone 16, Release)

```
    9~42ms   dyld + 정적 초기화 끝
   29~70ms   PhotoStore.load()      ← 0.4ms, 무죄
      78ms   화면이 붙는다 (UI는 여기서 이미 떠 있다)
  83~135ms   configure()            ← 카메라 큐, 메인 아님
     135ms   startRunning()
     327ms   ★ 첫 프레임
```

| 항목 | 실측 | 판정 |
|---|---|---|
| `AVCaptureSession.startRunning()` | **200ms** | 센서를 켜는 값. **줄일 수 없다** |
| `device.activeFormat` 직접 지정 | — | **무죄.** 껐다 켜고 3회씩 A/B → 182~237 대 168~220ms로 겹침 |
| `AVCaptureDevice.default(_:for:position: .front)` | **43.6ms** | 셀카 버튼 하나 때문에 첫 프레임을 그만큼 늦추고 있었다 |

**줄일 수 있는 건 시작 시각뿐이었다.** 촬영 화면의 `.task`는 첫 렌더가 **끝난 뒤** 도는지라 화면은 107ms에 떠 있는데 뷰파인더만 327ms까지 새까맸다. `App.init`에서 켜니 327 → **253~283ms**.

⚠️ **`Task { @MainActor in }`으로 앞당기려 하면 안 된다** — 메인 액터 큐에 실리므로 첫 렌더 **뒤로** 밀린다. `nonisolated` 함수에서 전용 큐로 곧장 넣어야 병렬이 된다.

## "멈춘 것 같다"의 절반은 블록이 아니라 **침묵**이다 ★

메인은 78ms에 자유로워지는데도 사용자는 "멈췄다"고 느꼈다. 화면에 변화가 **하나도 없어서**다 —
런치 스크린(`UILaunchScreen: [:]` = 빈 검정)도 검정, 조작부도 검정, 아직 프레임이 안 온 뷰파인더도 검정.
탭한 순간부터 첫 프레임까지 검은 화면이 끊김 없이 이어진다.

고친 방법은 시간을 더 깎은 게 아니라 **기다림을 읽히게 만든 것**이다.
- 빈 뷰파인더 자리에 아주 옅은 온기(`RadialGradient`)를 깐다 — 같은 어둠인데 "불이 켜져 있는 방"으로 보인다.
- 첫 프레임을 0.3초 페이드로 띄운다. 툭 켜지면 앞의 정적이 고장으로 읽히는데, 페이드가 붙으면 같은 시간이 **연출**이 된다.

**규칙: 남은 지연이 200ms대면 더 깎기 전에, 그 시간 동안 화면이 무슨 말을 하고 있는지 먼저 봐라.**

## 직렬 큐 **바깥**의 가드는 가드가 아니다

```swift
// ❌ 두 경로가 겹치면 둘 다 통과한 뒤 입력을 두 번 붙인다
guard session.inputs.isEmpty else { return }
await withCheckedContinuation { _ in queue.async { session.addInput(...) } }

// ✅ 검사를 직렬 큐 안으로 — 중복 호출이 저절로 무해해진다
queue.async { if session.inputs.isEmpty { ... } }
```

예열(`App.init`)과 권한 요청 후 구성(`.task`), 두 진입점이 생기면서 드러났다. **`await` 지점이 있으면 "검사 → 실행" 사이가 벌어진다.**

## 진단 요령

증상별 용의자: **특정 버튼 순간** → 그 핸들러의 동기 호출(오디오·햅틱·디스크). **첫 실행** → 세션·컨텍스트 생성과 lazy. **화면 전환 순간** → 새 화면의 초기화. 재현이 실기기뿐이면 추측 반복 대신 Instruments Time Profiler로 가는 편이 빠르다 — Fadeo는 세 라운드 추측으로 잡았지만 운이 좋았다.
