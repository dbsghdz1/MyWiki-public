# 온디바이스 음성 인식과 번역

macOS 26의 `SpeechAnalyzer`(음성→텍스트)와 `Translation`(번역)을 실제로 붙여 보고 알게 된 것. **둘 다 온디바이스·무료지만 모델을 내려받는 방식이 서로 다르고, 그 차이가 앱 구조를 결정한다.**

## 핵심 정리

### SpeechAnalyzer — 모듈을 붙이는 분석기

`SpeechAnalyzer`(actor)에 `SpeechTranscriber` 같은 모듈을 물리고, `AsyncStream<AnalyzerInput>`으로 오디오 버퍼를 밀어 넣으면 `transcriber.results`에서 결과가 흘러나온다.

- `ReportingOption`은 `.volatileResults`(확정 전 텍스트를 계속 갈아끼움) · `.alternativeTranscriptions` · `.fastResults` 셋. **실시간 자막에서 지연의 핵심 손잡이는 `.fastResults`다.**
- 결과의 확정 여부는 `SpeechModuleResult`의 **`isFinal`** — 프로토콜 본체가 아니라 **extension에 있는 계산 속성**이라 인터페이스를 훑으면 눈에 잘 안 띈다.
- 입력 포맷은 `SpeechAnalyzer.bestAvailableAudioFormat(compatibleWith:)`가 알려준다. 실측 결과 **16kHz / 1ch / interleaved**.
- 모델 자산은 `AssetInventory.status(forModules:)`로 확인하고 `assetInstallationRequest(supporting:)` → `downloadAndInstall()`로 **앱이 직접 내려받을 수 있다.** 설치 후 `AssetInventory.reserve(locale:)`로 붙잡아 둔다(`maximumReservedLocales` 상한 있음).
- 실측: 영어 모델 다운로드 약 11초, 이후 **확정 자막까지 +0.85 ~ +1.03초**.

### iOS 시뮬레이터에서는 음성 인식이 통째로 안 된다 ★ (2026-09-01)

**iOS 26.5 시뮬레이터(Xcode 26.6)에서 `SpeechAnalyzer`도 `SFSpeechRecognizer`도 동작하지 않는다.** 코드 문제로 오진하기 쉬우니 증상을 그대로 적는다.

- `SpeechTranscriber.supportedLocales`가 **빈 배열**, `AssetInventory.status(forModules:)`는 `unsupported`. 같은 코드가 macOS 호스트에선 30개 로케일(ko_KR 포함)을 돌려준다.
- `AssetInventory.assetInstallationRequest(supporting:)` → `SFSpeechErrorDomain Code=1 "Cannot check the download status, com.hong.wristnote is not subscribed to transcription.ko"`. **`AssetInventory.reserve(locale:)`를 먼저 호출해도** 시뮬레이터에선 같은 에러 (reserve는 `true`를 돌려주는데도). 실기기에서 reserve 선행이 필요한지는 미확인.
- `SFSpeechRecognizer` 폴백: `supportsOnDeviceRecognition`이 **`true`인데** `requiresOnDeviceRecognition = true`로 돌리면 `kLSRErrorDomain Code=300 "Failed to initialize recognizer"`. `false`로 서버 경로를 타도 **같은 에러**. 영어(en-US)로 바꿔도 동일 → 로케일 문제가 아니라 시뮬레이터 스택 문제.
- 시뮬레이터 `SFSpeechRecognizer` 권한 프롬프트는 `simctl privacy`가 `speech-recognition`을 모른다(`Operation not permitted`). TCC.db에 직접 넣으면 통과: `sqlite3 <sim>/data/Library/TCC/TCC.db "INSERT OR REPLACE INTO access (service, client, client_type, auth_value, auth_reason, auth_version, flags) VALUES ('kTCCServiceSpeechRecognition','<bundle id>',0,2,2,1,0);"`
- 결론: **전사는 실기기에서만 검증 가능.** 시뮬레이터로 요약·UI를 보려면 전사 결과를 env로 주입하는 훅을 앱에 둔다 (WristNote `WRISTNOTE_TRANSCRIPT`).

반면 **`FoundationModels`(온디바이스 LLM)는 시뮬레이터에서 된다** — `SystemLanguageModel.default.availability == .available`, `@Generable` 구조체로 한국어 회의 요약이 정상 생성됐다.

### SpeechAnalyzer 한국어 품질 — 합성 음성 기준 실측 (2026-09-01)

macOS 26 호스트에서 ko_KR 모델(이미 설치, 다운로드 0.09초)로 34초 TTS 회의 음성을 **0.35초**에 전사. 그러나 **핵심 명사가 무너진다**: "회의"→"매일/메일/메리", "안건"→"하면/화 편", "신규 앱의 출시"→"싱U M의 소시", "예산"→"예상", "담당"→"나무". 숫자·이름·요일("15일", "300만 원", "민수", "지현", "금요일 오후 두시")은 정확. 보이스 3종(Flo·Eddy·Grandma) 모두 비슷. **합성 음성이라 실제 육성보다 불리할 수 있다** — 실제 회의 녹음으로 재측정 전엔 일반화 금지.

**그리고 요약 모델은 오염된 전사를 보정하지 못한다.** "인식 오류를 문맥으로 보정하라"는 instructions를 줘도 FoundationModels는 "싱U M의 소시 일정", "마케팅 예상"을 그대로 요약에 실었다. 전사 품질이 곧 제품 품질이다.

### Translation — 앱이 모델을 못 내려받는다 ★

여기가 함정이다. **두 API가 능력이 다르다.**

| 얻는 방법 | 가용 | 모델 다운로드 |
|---|---|---|
| `TranslationSession(installedSource:target:)` | macOS 26.0+ | **불가** — 이름 그대로 *이미 설치된* 언어만 |
| SwiftUI `.translationTask(configuration)` | macOS 15.0+ | 가능 (`canRequestDownloads`) |

→ **번역 엔진을 헤드리스로 만들 수 없다.** 백그라운드 상주 앱이라도 온보딩 어딘가에서 **SwiftUI 뷰를 띄워 `.translationTask`를 한 번 태워야** 모델이 깔린다.

미설치 상태에서 `installedSource:` 세션에 `prepareTranslation()`을 호출하면 **`Unable to Translate`로 실패한다.** 사전 확인은 `LanguageAvailability().status(from:to:)` — 반환값이 `.installed`가 아니라 `.supported`면 "지원하지만 안 깔림"이다. 이걸 설치로 오독하면 런타임에 가서야 깨진다.

**`prepareTranslation()`은 요청만 걸고 즉시 반환한다.** 실제 설치는 비동기라 `LanguageAvailability` 상태를 폴링해야 한다 — 호출 직후 앱을 종료시키면 다운로드가 시작도 못 한다.

### macOS 26.4의 지연/정확도 손잡이

`TranslationSession.Strategy`에 **`.lowLatency`와 `.highFidelity`**가 있고 `init(installedSource:target:preferredStrategy:)`로 고른다. 실시간 자막이면 `.lowLatency`. 26.0에는 없고 **26.4부터**다.

### ScreenCaptureKit으로 시스템 오디오 받기

- `SCStreamConfiguration.capturesAudio = true`, `sampleRate`(기본 48000), `channelCount`, **`excludesCurrentProcessAudio`**(자기 소리 되먹임 방지 — 자막 앱에 필수).
- **macOS 26에서는 오디오 전용 스트림이 성립한다.** `.audio` 출력만 붙이고 `startCapture()`가 통과한다. 예전엔 `.screen` 출력을 반드시 붙여야 했다는 보고가 많은데 **실측으로 더 이상 아니다** — 더미 비디오의 CPU·배터리 비용을 낼 필요가 없다.
- `CMSampleBuffer` → `AVAudioPCMBuffer`는 **콜백 안에서 복사**해야 한다. `withAudioBufferList`가 주는 포인터는 콜백이 끝나면 무효다.
- 무음 함정: 오류 없이 조용히 0만 흐르는 경우가 있어 **버퍼 피크를 명시적으로 재는 로그**를 넣어두는 편이 낫다.

### TCC 권한과 코드 서명 — 개발 중에 가장 시간을 먹는 곳 ★

- **ad-hoc 서명(`codesign --sign -`)은 빌드마다 cdhash가 달라져 TCC 권한이 매번 초기화된다.** 실제 인증서(Apple Development)로 서명하면 designated requirement가 팀ID+번들ID로 고정돼 **재빌드해도 권한이 유지된다.**
- **바이너리를 터미널에서 직접 실행하면 권한이 '터미널'에 귀속된다.** LaunchServices를 거쳐야(`open Foo.app`) 그 앱에 붙는다.
- `CGPreflightScreenCaptureAccess()`는 **확인만 하고 프롬프트를 안 띄운다.** 시스템 설정 목록에 앱이 나타나지도 않는다. 요청은 `CGRequestScreenCaptureAccess()`.
- 첫 호출은 `false`를 반환하고 사용자가 시스템 설정에서 켠 뒤 재실행해야 한다. 등록 여부는 `sqlite3 "/Library/Application Support/com.apple.TCC/TCC.db"`에서 `service='kTCCServiceScreenCapture'`로 확인 가능(`auth_value` 0=꺼짐, 2=허용).

## 기법 — API 가용성은 웹 검색 말고 SDK를 읽는다

이번에 웹 검색은 `TranslationSession` 직접 생성의 가용 버전을 **틀리게** 알려줬다. 확실한 소스는 로컬 SDK의 `.swiftinterface`다.

```bash
SDK=$(xcrun --sdk macosx --show-sdk-path)
F="$SDK/System/Library/Frameworks/Translation.framework/Versions/A/Modules/Translation.swiftmodule/arm64e-apple-macos.swiftinterface"
grep -nE "public (init|func|var)|@available" "$F"
```

`@available(macOS 26.4, *)` 같은 주석이 선언마다 붙어 있어 **버전·시그니처를 그 자리에서 확정할 수 있다.** 새 OS의 신규 API처럼 웹 정보가 부정확하거나 얇은 영역에서 특히 유효하다. `.swiftinterface`가 없는 Objective-C 프레임워크(ScreenCaptureKit 등)는 `Headers/` 아래 헤더를 같은 방식으로 읽는다.
