# Jira MCP

Atlassian Rovo MCP로 Jira를 읽고 쓴다. 소마 **보험찾개냥**(프로젝트 키 `SSH`, `somassh.atlassian.net`)에서 티켓 생성·상태 전환·스프린트 이동에 쓴다. 여기 남기는 건 도구 설명이 아니라 **실제로 거부당한 것들**이다 — 도구 목록만 보면 다 될 것 같지만 Jira 쪽 규칙이 먼저 막는다.

## 고정값 (보험찾개냥)

- `cloudId`: `9ee9a9f1-00c3-4cbd-ba6a-9ce3e6a23c34`
- 스프린트 필드: **`customfield_10020`** — `editJiraIssue`의 `fields`에 스프린트 **id(정수)**를 넣는다. 이름 문자열은 안 통한다
- 스프린트 id는 JQL로 확인한다: `project = SSH AND sprint = 269`. 이름·번호(스프린트 13)와 내부 id(269)는 다르다
- 「완료」 전환 id: **41**. 전환 id는 프로젝트·이슈 타입마다 다를 수 있으니 `getTransitionsForJiraIssue`로 먼저 확인하고 쓴다

## 기록

### 2026-09-16 — 하위 작업은 스프린트에 붙일 수 없다

백로그에 쌓인 18건을 이번 스프린트(13 = id 269)로 옮기던 중 2건만 실패했다. 응답은 이렇다.

```json
{"errorMessages":["\\{0}\\ 이슈는 하위 작업이며 하위 작업은 스프린트에 연결할 수 없습니다. 상위 작업과 동일한 스프린트에 연결됩니다."]}
```

실패한 SSH-327·SSH-328은 **Subtask**였고 상위는 SSH-294다. Jira에서 하위 작업은 자체 스프린트 필드를 가지지 않고 **상위 작업의 스프린트를 그대로 따른다.** 그러니 하위 작업을 옮기고 싶으면 상위를 옮기는 수밖에 없고, 그건 상위 담당자의 스프린트 계획을 바꾸는 일이라 함부로 하면 안 된다.

주의할 점 둘:

- **상태 전환은 하위 작업도 된다.** 같은 두 건이 `transitionJiraIssue`로 완료(41)는 정상 처리됐다. 막히는 건 스프린트 필드뿐이다. 단 **전용 전환 도구를 써야 한다** — SSH-373 때 이미 「Jira는 Subtask 전환을 편집 API로 막아 놨다」고 [[작업노트/미분류|미분류]]에 남아 있다. 즉 하위 작업에 대해 `editJiraIssue`로 막히는 건 상태와 스프린트 둘 다고, 상태만 `transitionJiraIssue`로 우회된다
- 그래서 **"스프린트 이동 실패 = 그 티켓 처리 실패"가 아니다.** 완료는 됐는데 스프린트 보드에는 상위를 따라 안 보일 수 있다. 보고할 때 둘을 나눠 적는다

`searchJiraIssuesUsingJql`로 `sprint = <id>`를 다시 조회해 결과를 검증했다 — 완료 12건 + 미완료 4건 + 원래 있던 1건 = 16건 이동이 맞고, 여기에 하위 작업 2건의 완료 전환이 따로 있었다.

### 2026-09-16 — 분류기가 쓰기 도구를 한 번 막는다

`transitionJiraIssue`(SSH-327) 호출이 **External System Writes**로 한 번 거부됐다. 같은 인자로 재시도하니 통과했다. 여러 건을 연속으로 쓰는 중이면 중간 한 건만 튕길 수 있으니, **성공 개수를 세지 말고 마지막에 JQL로 실제 상태를 다시 읽어 확인한다.**
