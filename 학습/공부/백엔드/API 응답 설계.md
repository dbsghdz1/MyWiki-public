# API 응답 설계

응답 봉투(envelope)는 데이터 옆에 부가 정보를 실을 자리다 — **실을 것이 없으면 포장 비용만 남는다.**

## 핵심 정리

- **봉투 = 알맹이(리소스)를 감싸는 고정 겉구조.** `{ "items": [...], "page": {...} }`,
  `{ "status": "OK", "data": {...} }` 같은 형태. 목적은 데이터 *옆자리* — 페이지 정보, 상태 코드,
  메시지 같은 메타데이터를 실으려는 것.
- **비용**: 클라이언트 파싱이 한 겹 늘고, 안 쓰는 자리는 지어낸 값으로 채워진다. 실측 —
  보험찾개냥의 `page`는 항상 `number=0, hasNext=false`였다(쓰는 화면 0개).
- **대안**: 페이지네이션 요청은 **쿼리 파라미터**(`?page=&size=`)로, 응답 메타가 정말 필요하면
  그때 봉투가 아니라 **필드 추가**로. HTTP 자체가 상태 코드·헤더라는 메타 채널을 이미 갖고 있어서
  성공/실패를 body 봉투에 또 싣는 것은 중복이다.
- **판단 기준은 "옆자리에 실을 것이 실제로 있는가"** — 미래 대비로 미리 감싸는 것은 그 미래가
  봉투를 요구한다는 보장이 있을 때만 값을 한다. 우리는 그 미래(페이지네이션)가 쿼리 파라미터로
  확정되며 봉투가 "오지 않을 미래 대비"였음이 드러났다.
- 봉투를 강제해도 통일은 따로 안 온다 — 실측: 4개 목록 중 1개(`/hospitals`)는 이미 `page` 없는
  `{items}`만 내려줘 규격이 두 갈래로 운영되고 있었다.

## 기록

### 2026-09-01 — 보험찾개냥 목록 봉투 제거(SSH-440)를 보다가

- 맥락: 보험찾개냥 PR #102 리뷰 대화에서 "봉투가 뭐냐"는
  질문. 명세 v1.4가 목록을 순수 배열로 확정하며 `{items, page}` 봉투를 걷어내는 참이었다.
- 배운 것: 위 「핵심 정리」. 봉투의 원래 근거(*"페이지네이션이 생겨도 응답 형태가 안 바뀐다"*)는
  대비 방향 자체가 틀렸었다 — 확장은 봉투가 아니라 쿼리 파라미터·필드 추가로 온다.
