## 전략 (2026-10-17 정리)

홍이 「우리의 전략은 뭐야, 개인이 PR 날려도 되는 거지」라고 물어 한 자리에 적는다. 근거는 아래 날짜별 확인 절이다.

- **목표**: 당근 코드베이스에 머지된 PR 1~2건을 이력서 근거로 만든다. 「기여 실적」이 아니라 「지원 회사 코드베이스를 읽고 그 규칙대로 PR을 냈고 리뷰를 받았다」 수준이다(08-20 기대치 조정). 제출, 머지, 릴리스는 구분해서 적는다.
- **개인 PR은 된다.** CONTRIBUTING이 문서 보완과 버그 픽스는 바로 PR이라고 적었고 CLA가 없으며 Apache-2.0 5조로 기여 조건을 갈음한다. 선례도 있다. 2026년 8월에 외부 계정의 문서 수정 PR 두 건(#1917, #2030)이 각각 7일, 2일 만에 메인테이너의 「thank you」 한 줄로 머지됐다. 당근의 다른 저장소 `daangn/stackflow`는 최근 PR 300건 중 외부 PR 30건에서 17건을 머지했다(2026-10-17 확인).
- **위험은 거절이 아니라 무응답이다.** 같은 8월에 올라온 외부 PR 네 건(#1930, #2070, #2096, #2097)은 봇 댓글만 달린 채 두 달째 메인테이너 반응이 없다. 머지된 둘은 파일 하나짜리 문서 수정이었고, 멈춘 넷은 코드 변경이거나 파일이 여러 개다. 외부 이슈 #2482와 #2095에도 메인테이너 댓글이 없다.
- **그래서 순서**: ① 파일 한두 개짜리 문서 PR로 첫 머지를 만든다(지금: lynx-react와 lynx-css README). ② 머지되면 리뷰와 봇 흐름을 「기록」에 적고, 보험찾개냥 Lynx 앱에 `@seed-design/lynx-react`를 실제로 넣어 컴포넌트를 쓴다. ③ 쓰다가 걸린 문서 공백이나 재현되는 버그를 두 번째 PR로 낸다. 컴포넌트 추가나 공개 API 변경은 CONTRIBUTING대로 이슈 먼저다. ④ 범위는 Lynx 쪽(SEED Lynx 패키지, lynx-console, lynx-stack)으로 유지하고 슬롯은 화, 토 16:00~18:00이다.
- **PR은 작게, 근거는 본문에.** 머지된 선례의 모양을 따른다. 영어 Conventional Commits 제목, 왜 필요한지 한 문단(npm README 부재, 루트 README 링크, #2473 선례), 확인 방법 한 줄. 문서 PR이라 changeset-bot의 「No Changeset found」 댓글은 정상이고, CodeRabbit 자동 리뷰는 읽고 맞는 지적만 반영한다.
- **무응답 대응(에이전트 제안, 홍 확정 전)**: 2주 지나면 PR에 정중히 한 번 리마인드한다. 그래도 없으면 다음 재료로 넘어가고 이력서에는 「제출」 상태로 PR 링크를 쓴다. 머지 여부와 무관하게 PR 자체가 코드베이스를 읽은 증거다.

**외부 PR 가능 여부:** 세 저장소 모두 기여 안내를 제공한다. SEED는 문서 보완·버그 수정을 바로 PR로 받고 새 컴포넌트·공개 API 변경·새 패키지·외부 의존성 추가는 이슈로 먼저 논의하도록 안내한다. Lynx Stack은 크고 작은 기여를 환영하고, Stackflow는 빌드·데모 검증 방법을 안내한다. PR 제출과 머지는 구분하며, 구체적인 첫 이슈·담당 가능 여부·최근 외부 PR의 리뷰 속도는 아직 확인하지 않았다(2026-10-02). 근거: 위 표의 각 기여 가이드.

### 첫 실습과 PR 후보 확인

1. [Lynx Quick Start](https://lynxjs.org/guide/start/quick-start)의 프로젝트 생성·Explorer 준비·개발 서버 실행 절만 따라 기본 앱을 띄운다. 시뮬레이터에서는 번들 URL을 Explorer의 입력칸에 넣어 미리 볼 수 있다(2026-10-02 공식 문서 확인).
2. 제목과 버튼 하나가 있는 작은 화면을 직접 만든다. 버튼을 누르면 글자 하나가 바뀌게 하며 JSX·이벤트·상태를 배운다. 첫 완료 기준은 실행 화면과 코드의 동작을 자기 말로 설명하기다.
3. 같은 화면의 버튼을 SEED Action Button으로 바꾸고 props·스타일·동작을 문서와 비교한다. 설치와 컴포넌트 API는 [SEED Lynx 문서](https://seed-design.io/lynx)를 확인한다.
4. 문제를 발견하면 기존 이슈·PR을 검색해 중복과 작업 중인 사람이 있는지 확인한다. 열린 이슈에 담당자·연결 PR이 없다고 자동으로 맡을 수 있다고 판단하지 않는다.
5. 최소 재현을 만들고 관련 코드·테스트를 찾는다. 변경 방향이 불명확하면 이슈에 재현 결과와 수정안을 먼저 적는다. fork → 브랜치 → 수정·검증 → 원본 저장소 PR → 리뷰 대응 순으로 진행한다.
6. 취업 자료에는 실제 수행 범위·검증·리뷰 대응과 PR 링크를 남긴다. 제출·머지·릴리스 상태를 구분한다. 문서 기여도 실제 사용 중 발견한 문제와 해결을 설명할 수 있으면 기록한다.


이 절은 기존 날짜별 계획보다 현재 실행 순서를 우선한다. 예전 사전 조사와 계획은 당시 기록으로 보존하며, 셋업·문서 파일명·스킬명은 실제 기여 전에 현재 저장소의 안내로 다시 확인한다.

**SEED에서 「바로 PR」 종류로 보이는 것**
- `@seed-design/lynx-react`·`@seed-design/lynx-css` 패키지 폴더에 README.md가 없어 npm 페이지가 비어 있다(`npm view @seed-design/lynx-react readme` → "No README data found", 2026-10-03). 문서 보완은 CONTRIBUTING이 바로 PR을 받는 종류다 — 설치 방법과 문서 사이트 링크만 담은 README 한 장이 **첫 PR 후보**

**SEED Lynx 컴포넌트 공백** — 문서 기준 React 56개 vs Lynx 42개. Lynx에 없는 것: avatar, snackbar, toggle-button, popover, pagination, table-pagination, date-picker, time-picker, wheel-picker, pull-to-refresh, side-panel, aspect-ratio, image-frame, content-placeholder, article, help-bubble-tooltip, field-button(Lynx에는 input-button이 있다). 새 컴포넌트는 CONTRIBUTING이 **이슈 먼저**다 — 실습 화면에서 실제로 필요해진 것 하나를 골라 이슈로 제안하는 것이 자연스러운 경로다.

### 2026-10-17 시작: fork, 빌드, 첫 PR 범위

**홍의 요청(2026-10-17 새벽):** 「당근 오픈소스 기여, 이거를 진짜 시작해보자」. 10-03 이후 실제로 한 것이 없었음을 먼저 확인했다. 홍 계정에 fork가 하나도 없었고, 보험찾개냥 Lynx 앱의 의존성은 `@lynx-js/*`뿐이라 SEED를 아직 쓰지 않는다. 즉 「쓰다가 발견한 문제」 경로는 SEED를 그 앱에 넣기 전까지 열리지 않는다.

**10-17에 한 것(에이전트):** `daangn/seed-design`을 홍 계정으로 fork하고 `dev`(커밋 `0684acaa7`, PR #2487)를 클론했다. 원격은 `origin`이 fork, `upstream`이 원본이다. 로컬 툴체인은 저장소 요구와 같다(Bun 1.4.2는 `.bun-version`, Node 24는 `.nvmrc`와 일치). 빌드는 CONTRIBUTING 순서(`bun install` → `bun ecosystem:build` → `bun install` → `bun generate:all` → `bun packages:build`)대로 한 번에 성공했다. 합계 약 76초(설치 17초, 생성 22초, 패키지 빌드 31초)이고 빌드 뒤 작업 트리에 생성물 드리프트가 없었다. 막힌 지점이 없어 셋업에서 나오는 문서 PR 후보는 없다. `npm pack --dry-run`은 README가 있는 `packages/react`에서 `README.md` 줄을 보여 주고 `packages/lynx-react`에서는 보여 주지 않는 것을 확인했다.

**첫 PR 범위: `@seed-design/lynx-react`와 `@seed-design/lynx-css`의 README.** 10-03 후보를 다시 확인하니 그대로 비어 있고 근거가 더 생겼다(모두 2026-10-17 확인).

**분담:** README 본문은 홍이 직접 쓴다. 이력서 근거가 되는 PR이고 코드 읽기가 곧 1단계이기 때문이다. 읽는 순서는 `CONTRIBUTING.md` → `packages/react/README.md` → #2473의 README 하나(`packages/lynx-react-headless/action-button/README.md`) → `packages/lynx-react/package.json`의 `peerDependencies` → `docs/content/lynx/getting-started/installation.mdx`. 에이전트는 브랜치, 커밋, push, PR 생성과 검증만 맡고 PR 본문은 올리기 전에 홍이 확인한다. 검증은 패키지 폴더에서 `npm pack --dry-run`을 돌려 README.md가 tarball에 들어가는지 본다. `files`에 README가 없어도 npm이 자동 포함하는지를 여기서 확인한다.

## SEED Design 사전 조사 (2026-08-16, `gh api`로 확인)

- 저장소 `daangn/seed-design`, 기본 브랜치 **`dev`**, Apache-2.0, ★1,048, 마지막 push 2026-08-15 — 활발하다.
- 스택: **Bun** 워크스페이스(npm/yarn 금지), React, TypeScript, bunchee·vite 빌드, Next.js + Fumadocs 문서, Storybook, **Biome** 린트/포맷, changeset.
- 파이프라인 (`TECH.md`): `[Figma] → rootage YAML(토큰) → qvism-preset(recipe) → css(vars/recipes 생성물) → react`. `packages/css/vars/`, `packages/css/recipes/`, `packages/qvism-preset/src/vars/`는 **생성물이라 직접 수정 금지** — 원천 고치고 `bun generate:all`.
- `packages/`: react, react-headless, css, design-token, stylesheet, cli, codemod, mcp, docs-mcp, figma, stackflow, tailwind3-plugin, tailwind4-theme, vite/webpack/rsbuild 플러그인, lynx-* 등 26개. `ecosystem/`: rootage, qvism, figma-extractor, postcss-*.
- 기여 가이드 (`CONTRIBUTING.md`): **오타·문서 보완·버그 픽스는 바로 PR**. 새 컴포넌트·공개 API 변경·새 패키지·외부 의존성 추가는 **이슈로 먼저 논의**. 커밋·PR 제목은 영어 Conventional Commits(`feat(button): add loading state`). 코드 주석 금지(꼭 필요하면 한국어). 유저 향 변경엔 changeset(`/changeset` 스킬).
- 셋업: `bun install → bun ecosystem:build → bun install(다시) → bun generate:all → bun packages:build`. install을 두 번 하는 이유는 ecosystem CLI 빌드 후 워크스페이스 bin 링크를 걸기 위해서 — 이 링크 없으면 `generate:all`이 조용히 다른 CLI를 써서 생성물이 갱신되지 않는다.
- 이슈·라벨: `good first issue` 같은 진입용 라벨이 **없다**(라벨은 `release:*` 3개뿐). 열린 이슈도 거의 없고 열린 PR이 65개 — 내부 팀이 PR 중심으로 움직인다. 즉 **이슈를 골라 잡는 방식이 아니라, 코드를 읽다가 발견한 문서·타입·a11y·테스트 결함을 직접 PR로 내는 방식**이어야 한다.
- 레포에 `AGENTS.md`, `CLAUDE.md`, `.claude/skills`(`create-component`, `changeset`)가 있다 — Claude Code로 작업하는 흐름을 이미 지원한다.
