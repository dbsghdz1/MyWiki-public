# 코드보다 먼저 정하는 것

**"만들고 싶다"와 "무엇을 만드는지 안다" 사이에 단계가 몇 개나 있는가**를 묻는 노트. 나는 그 사이가 한 칸인 줄 알았는데, 읽어보니 셋이었고 내가 건너뛴 것은 가운데 칸이었다.

## 핵심 정리

- **프로젝트는 기술에서 시작하지 않는다.** MDN의 표현으로 *"많은 프로젝트가 기술 부족이 아니라 목적과 전망의 부족으로 실패한다."* 음악가·화가·작가가 그러듯, 무엇을 할지 먼저 정하고 기술은 그다음에 익힌다. 기술은 수단이지 목적이 아니다.
- **가운데 칸이 제일 잘 빠진다.** ①목표를 적는 것과 ③할 일로 쪼개는 것은 누구나 한다. 빠지는 것은 ②**"이 목표에 웹사이트가 정말 필요한가"**다. 이 칸을 안 지나면 이미 있는 서비스로 되는 일을 처음부터 만들게 된다.
- **할 일로 쪼개면 대부분이 코드가 아니다.** MDN 예시에서 "사람들이 내 음악을 듣게 하기"는 ①녹음한다 ②온라인용 오디오 파일을 준비한다 ③웹사이트에서 접근하게 한다인데, 코드는 셋 중 하나다. 굿즈 판매는 다섯 단계 중 **공급·보관·결제가 웹 개발보다 앞에 있다.**
- **스펙을 안 쓰면 설계가 코드와의 타협이 된다.** Joel Spolsky: 코드를 먼저 쓰면 **이미 쓴 코드에 애착이 생겨** 더 나은 구조로 바꾸기를 거부하게 되고, 결과물은 이상적인 설계가 아니라 *"이미 작성된 코드와의 타협"*이 된다. 스펙의 가장 중요한 기능은 문서가 아니라 **설계 그 자체**다 — 글로는 설계안 여럿을 코드보다 훨씬 빠르게 바꿔볼 수 있다.

## MDN이 시키는 세 질문

원문 소제목 그대로다. 영어판 구조는 `Summary` / `Deeper dive` / `Conclusion`이고 세 질문이 양쪽에 같은 순서로 나온다.

| # | 질문 | 하는 일 | 빠뜨리면 |
|---|---|---|---|
| ① | **내가 정확히 달성하고 싶은 것은 무엇인가?** | 목표를 전부 적고 **중요도 순으로** 세운다 | 우선순위 없이 전부 하려다 아무것도 안 끝난다 |
| ② | **어떻게 웹사이트가 나를 목적지로 데려다 줄 수 있을까?** | 목표마다 **웹사이트가 실제로 필요한지** 가른다. 기존 서비스로 되는 것은 뺀다 | 이미 있는 것을 다시 만든다 |
| ③ | **내 목표를 달성하기 위해, 무엇을, 어떤 순서로 해야할까?** | 큰 목표를 실행 가능한 작은 단계로 쪼갠다. **웹과 무관한 오프라인 단계도 함께** | 코드만 쌓이고 제품이 안 된다 |

②의 예시가 좋다. 음악가의 목표 일곱 개 중 "새로운 애인 찾기"는 데이팅 앱이, "고양이 사진 출판하기"는 SNS가 이미 한다. **남는 다섯 개(음악 듣게 하기·음악 이야기·다른 음악가 만나기·굿즈·강의)만 한 웹사이트로 묶인다.** 일곱에서 다섯으로 줄이는 것이 이 단계의 산출이다.

결론도 그대로 옮겨둔다. *"모든 질문에 답하거나 모든 항목을 다 할 필요는 없다. 중요한 것은 원하는 것과 도달하는 법에 대한 명확한 비전이다."* 방법은 **큰 일을 작은 실행 단계로 쪼개고, 작은 단계를 큰 성과로 합치는 것.**

## 기록

### 2026-09-16 — 내가 건너뛴 것은 ②가 아니라 ②의 *검증*이었다

맥락: [[프로젝트/개인/약국맵/README|약국맵]]으로 `/gstack-office-hours`를 돌렸다. 그 세션이 이 글과 같은 자리를 짚어서 홍이 이 문서를 가져왔다.

**궁금했던 것**: 나는 ②를 했다고 생각했다. "약국 영업 정보는 이미 휴일지킴이약국·E-gen에 있는데 왜 새로 만드나"에 답이 있었기 때문이다. *"이건 정보가 없는 문제가 아니라 확인된 정보가 없는 문제다."* 그럼 나는 뭘 빠뜨린 건가?

**예측**: ②를 통과했으니 문제는 ③(실행 순서)에 있을 것이다.

**실제**: 틀렸다. ②의 답은 **논증이었지 관측이 아니었다.** 근거는 09-06 인터뷰 1건("주말 전화 4~5통")뿐이었고, 09-16에 실제로 세어보니 주말 하루에 **0통**이었다. 논증은 멀쩡한데 전제가 안 재져 있었다.

그리고 ③도 무너져 있었다. 실습 8칸을 올리는 동안 정작 **「지금 열림」 판정이 `Date.parse` 상수 두 개 비교로 하드코딩**돼 있었다(`server/main.js:57-59`, 항상 참). MDN 표현대로 쪼개면 「사람들이 지금 문 연 약국을 알게 하기」 = ①데이터를 가져온다 ②**지금 시각으로 열림을 판정한다** ③지도에 띄운다인데, 가운데가 통째로 비어 있었다. SSR·하이드레이션·낙관적 업데이트는 전부 ①과 ③ 주변이었다.

**배운 것 두 개.**
1. **②의 답이 문장이면 아직 안 한 것이다.** "왜 기존 것으로 안 되는가"에 답을 쓸 수는 있는데, 그 답이 참인지는 세어봐야 안다. 세는 비용이 0이었다 — 어차피 그 자리에서 일하고 있었다. **11일 동안 안 셌다.**
2. **Joel이 말한 "코드와의 타협"이 학습 프로젝트에서는 반대로 온다.** 나는 이미 쓴 코드를 지키려고 설계를 굽힌 게 아니라, **배울 것(SSR·하이드레이션)이 학습 순서를 정하게 두고 제품의 핵심 기능을 계속 뒤로 미뤘다.** 커리큘럼이 스펙 자리를 차지한 셈이다. 결과는 같다 — 만들어진 것이 설계가 아니라 지나온 경로를 닮는다.

**남은 궁금증**: 그럼 학습 프로젝트에서 ②를 어디까지 해야 하나. 수요를 다 검증하고 시작하면 배우기 전에 지치고, 안 하면 오늘 같은 일이 난다. 지금 답은 「②의 전제를 **비용 0으로 잴 수 있는 것부터** 재고, 못 재는 것은 판정에서 뺀다」인데 이게 일반화되는지는 모르겠다.

### 2026-09-22 — PRD는 「무엇을·왜」만 적는 문서다

맥락: [[프로젝트/개인/Zappy/README|Zappy]] 데스크톱 펫을 마무리한 직후([[프로젝트/개인/Zappy/Zappy 개발 기록 2026-09-22|개발 기록 09-22]]) 「PRD 문서라는 게 뭐야」를 물었다.

**PRD = Product Requirements Document(제품 요구사항 문서).** 코드를 짜기 전에 관계자가 같은 그림을 보려고 쓴다. 「어떻게 만드는가」는 여기 없다 — 그건 설계 문서 몫이다.

| 칸 | 묻는 것 |
|---|---|
| 문제 | 누가 어떤 상황에서 뭐가 불편한가 |
| 목표·성공 기준 | 뭐가 되면 성공인가 (수치로) |
| 사용자 시나리오 | 「사용자는 ~할 수 있다」 목록 |
| 범위 | 이번에 하는 것과 **안 하는 것** |
| 제약·미해결 질문 | 기한·플랫폼·아직 못 정한 것 |

위 MDN 세 질문과 겹친다 — ①이 목표 칸, ②가 문제 칸, ③이 범위 칸이다. Joel의 기능 스펙과는 층이 다르다: PRD가 「무엇을·왜」, 기능 스펙이 「화면에서 어떻게 동작하나」.

**이미 쓰고 있던 것**: 프로젝트 README의 현재 카드 5줄(특히 「하지 않을 일」)이 한 줄짜리 PRD다. 펫 브랜치의 `docs/desktop-pet-checks/README.md`(동작 규칙 + 검증 조건)는 기능 단위 미니 PRD에 가깝다 — 그 문서가 있었기 때문에 다른 세션이 남긴 미커밋 코드를 이어받아 「무엇이 완성인가」를 판단할 수 있었다. AI 에이전트에게 일을 맡길 때 PRD가 입력이 되는 이유가 이것이다.

### 2026-09-22 — 설계는 PRD와 코드 사이의 「plan」에서 일어난다

맥락: [[프로젝트/개인/약국맵/README|약국맵]] PRD v1을 쓴 직후 「PRD → spec → AI 개발이 요즘 흐름인가」, 「그럼 코드 설계는 어디서 일어나나」를 물었다.

**궁금했던 것**: PRD를 AI에게 주면 바로 코드가 나오는 것 같은데, 그럼 구조를 정하는 일은 사라진 건가?

**실제**: 사라진 게 아니라 **자리가 옮겨졌다.** 이 흐름에는 이름이 있다 — Spec-Driven Development(SDD). GitHub Spec Kit이 `constitution → specify → plan → tasks → implement`로, AWS Kiro가 `requirements.md → design.md → tasks.md`로 같은 단계를 굳혔다. 내가 「PRD → spec → 코드」로 알던 것은 가운데 **plan/design 칸이 빠진** 그림이었다.

| 단계 | 적는 것 | 누가 |
|---|---|---|
| PRD | 무엇을·왜 (위 09-22 항목) | 나 |
| spec | 기능 **하나**의 동작·수용 기준 | 나 + AI 초안 |
| **plan / design** | 데이터 모델·타입, 모듈 경계(무엇이 무엇을 모르는가), API 계약, 상태가 사는 곳, 기술 선택 이유(ADR) | **AI 초안 → 내가 경계·타입을 고쳐 확정** |
| tasks | 리뷰 가능한 크기의 조각 | AI |
| 구현 | 함수 본문 | AI |

설계 판단이 사는 곳이 하나 더 있다. **`AGENTS.md`/`CLAUDE.md`** — 「폴더 구조는 이렇게, 상태는 여기만, 이 라이브러리 금지」처럼 기능마다 반복되는 규칙은 plan에 매번 쓰지 않고 여기 박는다. Spec Kit은 이걸 `constitution`이라 부르고 프로젝트당 한 번만 세운다. 즉 **plan은 기능 단위 설계, constitution은 프로젝트 단위 설계**다.

**Joel과 이어지는 지점**: 스펙의 기능이 문서가 아니라 설계라는 말(핵심 정리 4번)이 여기서 도구가 됐다. plan 칸을 건너뛰고 AI에게 spec만 주면 파일마다 다른 구조로 짜고, 그게 「이미 작성된 코드와의 타협」의 AI 버전이다.

**폭포수는 아니다**: PRD·spec을 한 번에 완성하고 시작하지 않는다. 기능 하나만 spec → plan → 구현하고 어긋난 것을 PRD에 되먹인다. 크게 완성해 놓은 spec은 옛날 설계 문서처럼 썩는다.

**결정**: 앞으로 개발을 이 순서로 한다. 약국맵부터 — PRD v1 → 「약국 검색」 spec 하나 → plan에서 `Pharmacy` 타입·검색 API 계약·지도 컴포넌트와 데이터 레이어의 경계를 내가 확정 → 그다음 AI 구현.

**2026-09-22 저녁 정정**: 약국맵이 같은 날 보류돼 PRD v1을 닫았다(1칸 채운 상태). 순서 자체는 그대로 가고, **첫 연습 대상은 다음 새 프로젝트**로 옮긴다 — 불편 로그 한 주에서 문제가 나오면 그 문제로 PRD부터 쓴다. 이번에 확인한 것 하나: PRD의 「문제」 칸을 README에서 옮겨 적는 데 5분도 안 걸렸는데, 그 칸이 성립하는지(수요)는 다섯 달의 관찰이 정했다. **PRD는 문제를 만들어 주지 않는다, 있는 문제를 고정할 뿐이다.**

**남은 궁금증**: plan에서 내가 고칠 것과 AI에게 맡길 것의 선이 어디인가. 「타입과 경계는 나, 본문은 AI」가 지금 답인데, 경계가 잘못 그어졌다는 걸 구현 전에 어떻게 아나 — spec의 수용 기준으로 plan을 검사할 수 있는지 새 프로젝트에서 해 보면 안다(원래 약국맵이었으나 09-22 보류).
