# 에디터 단축키

내 편집 환경은 **VS Code + Vim 확장(VSCodeVim)** + **Rainy75(81키 75%)**다. 여기 단축키를 쌓는다 — 손이 기억할 때까지.

## 핵심 정리

- **두 개의 키맵이 한 창에서 겹친다.** VSCodeVim은 Vim 키 처리를 가로채고, VS Code는 원래 자기 단축키를 갖고 있다. 그래서 "안 먹는 키"는 대부분 버그가 아니라 **누가 그 키를 먹었는가**의 문제다.
- 충돌을 푸는 손잡이는 셋이다 (VSCodeVim README):
  - `vim.handleKeys` — 특정 키를 VS Code에 돌려준다. 예: `"<C-f>": false`면 `Ctrl+F`가 VS Code 찾기로 돌아간다.
  - `vim.useCtrlKeys` — Ctrl 조합 전체를 Vim이 먹을지 말지의 스위치.
  - `vim.useSystemClipboard` — yank/put의 기본 레지스터를 시스템 클립보드로.
  - `vim.leader` — 리더 키, 기본값은 `\`.
- **오른손 새끼의 기준은 「얼마나 뻗느냐」가 아니라 「어디부터 손 전체를 옮기느냐」다.** 원점은 `;`. 손을 안 움직이고 닿는 것은 `P` `0` `'` `/`, `-`·`[`까지가 한계, `=` `]` `\` `Backspace` `Enter` 오른쪽 `Shift`는 **손을 옮겨서** 친다. **`P`는 약지가 아니라 새끼다** — 여기가 어긋나면 오른손 전체가 한 칸씩 밀린다.
- **75%에서는 `Enter`와 오른쪽 `Shift`가 마지막 열이 아니다.** Rainy75는 `Del`·`Home`·`End`·`PgUp`·`PgDn` 다섯 개가 오른쪽에 열을 하나 더 만들고, `↑`가 오른쪽 `Shift` 옆에 끼어든다. 풀사이즈처럼 끝까지 뻗으면 `Enter` 대신 `PgUp`, `Shift` 대신 `↑`를 누른다 → 기준을 **「끝에서 한 칸 안쪽」**으로 잡는다(`'`에서 한 칸이 `Enter`, `/`에서 한 칸이 `Shift`).
- **Shift는 반대 손.** 오른쪽 Shift는 왼손 글자(`Q W E R T A S D F G Z X C V B`)에만 쓴다. Vim의 `:`는 **왼손 Shift + 오른 새끼 `;`** — 오른쪽 Shift로 치면 한 손이 꼬인다. `;`는 홈 키이면서 `f`/`t` 반복이라 실사용 빈도가 가장 높은 키 중 하나다.
- **창(뷰) 사이 이동은 `Cmd+Shift+<글자>` 계열이다.** 탐색기 `Cmd+Shift+E`, 검색 `Cmd+Shift+F`, 소스 제어 `Cmd+Shift+G`, 디버그 `Cmd+Shift+D`, 확장 `Cmd+Shift+X`. **편집기로 돌아오는 키는 `Cmd+1`**(첫 번째 편집기 그룹)이고, 사이드바 자체를 숨기고 여는 것은 `Cmd+B`다.
- **탐색기 안에서 `Enter`는 열기가 아니라 이름 바꾸기다** (맥 한정, 윈도우·리눅스는 `F2`). 파일을 여는 키는 `Cmd+↓`. 이동은 `↑` `↓`, 폴더 펼치기·접기는 `→` `←`.
- 이 키들은 전부 `Cmd` 조합이라 **Vim 확장이 가로채지 않는다** — 충돌 걱정 없이 쓰는 영역이다.
- VS Code 쪽 정본은 **Keyboard Shortcuts 에디터**와 `keybindings.json`이고, `when` 절이 "언제 이 키가 유효한가"를 정한다. 모드별로 다르게 걸고 싶으면 결국 `when`을 쓴다.

## 기록

### 2026-09-10 — 환경 확정: VS Code + Vim
- 맥락: 앞으로 단축키를 공부하겠다고 정하면서 편집 환경을 명시했다.
- 배운 것:
  - Vim 확장을 쓰는 순간 단축키 공부는 **Vim 키맵 + VS Code 키맵 두 축**이 된다. 한쪽만 외우면 나머지 절반에서 계속 막힌다.
  - 그래서 이 파일은 두 축을 나눠서 쌓는다 — Vim은 **모드·이동·편집·텍스트 객체**, VS Code는 **명령 팔레트·파일 이동·멀티커서·터미널**.
- 근거: 본인 확인 (2026-09-10). 설정 이름은 VSCodeVim README와 VS Code 공식 문서에서 확인.

### 2026-09-10 — 뷰 사이 이동, 그리고 맥 탐색기의 `Enter`
- 맥락: 코드 쓰다가 폴더를 고르는 창(탐색기)으로 어떻게 가느냐는 질문.
- 배운 것:
  - `Cmd+Shift+E`로 탐색기에 **포커스까지** 넘어간다(닫혀 있으면 열면서). 돌아오는 것은 `Cmd+1`, 사이드바 숨김·표시는 `Cmd+B`.
  - 탐색기에서 **파일 열기는 `Cmd+↓`, `Enter`는 이름 바꾸기**다. 목록 공통 동작(`list.select` = Enter)을 탐색기 전용 `renameFile`이 덮어서 생기는 맥 한정 함정 — 여는 키가 보조 키로 밀려난 것이다.
  - 이름을 아는 파일은 애초에 탐색기를 안 거치고 `Cmd+P`가 빠르다. 탐색기는 **구조를 훑거나 파일을 만들고 옮길 때** 가는 곳.
- 근거: VS Code 번들의 기본 키맵을 직접 확인했다 — VS Code 앱 번들의 `workbench.desktop.main.js`에서 `renameFile`이 `primary: 60(F2), mac: {primary: 3(Enter)}`, `list.select`가 `primary: 3(Enter), mac: {secondary: [2066] = Cmd+↓}`.

### 2026-09-10 — 오른손 새끼의 사정거리, 그리고 75%가 바꾸는 기준점
- 맥락: Rainy75를 쓰는데 오른쪽 새끼손가락이 어디까지 담당해야 하는지 애매하다는 질문.
- 배운 것:
  - 선은 **거리**가 아니라 **손을 옮기는가**로 긋는다. `;`가 원점이고 `P` `0` `'` `/`까지는 제자리, `Enter`·`Backspace`·오른쪽 `Shift`부터는 손 전체를 옮기는 키다. **통증은 거리가 아니라 손목을 비트는 데서 온다.**
  - 표준 배정에서 **`P`는 새끼**다(약지 아님). 이걸 약지로 치면 `O`가 중지로 밀려 오른손 전체가 한 칸 어긋난다 — 「애매함」의 흔한 원인.
  - **75% 배열이 기준점을 바꾼다**: Rainy75는 81키에 `Del`·`Home`·`End`·`PgUp`·`PgDn`이 오른쪽 열을 하나 더 만들고 `↑`가 오른쪽 `Shift` 옆에 들어온다. 풀사이즈 감각으로 「끝까지」 뻗으면 `PgUp`·`↑`를 누른다. 기준은 **끝에서 한 칸 안쪽**.
  - Vim 쪽 연결: `:`는 **왼손 Shift + 오른 새끼 `;`**. 「Shift는 반대 손」 규칙이 그대로 적용되는 자리고, `Esc`가 멀면 `Ctrl+[`가 같은 동작이다.
- 근거: 표준 터치타이핑 배정(P = 오른 새끼)은 Wikipedia Touch typing에서 확인. Rainy75 81키·5개 컨트롤 키(Del/Home/End/PgUp/PgDn) 구성은 아래 리뷰 2건.

## 학습 계획

- [ ] Vim 모드 — Normal / Insert / Visual / Visual Line, `Esc`로 돌아오는 감각

- [ ] Vim 편집 — `d c y p`, 반복 `.`, 되돌리기 `u` / `Ctrl+r`
- [ ] Vim 텍스트 객체 — `ciw` `di"` `ca(` (오퍼레이터 + 범위 조합이 진짜 힘)

- [x] VS Code — 뷰 이동 `Cmd+Shift+E/F/G/D/X`, 편집기 복귀 `Cmd+1`, 사이드바 `Cmd+B` (2026-09-10)
- [ ] VS Code — 명령 팔레트 `Cmd+Shift+P`, 파일 이동 `Cmd+P`, 심볼 `Cmd+Shift+O`
