# 키와 스키마 설계

**스키마는 DB가 집행하는 저장 규칙이고, 유일성·동시성 판정은 코드가 아니라 PK에 맡긴다.** (2026-09-16 [데이터베이스](%EB%8D%B0%EC%9D%B4%ED%84%B0%EB%B2%A0%EC%9D%B4%EC%8A%A4.md)에서 분리)

## 핵심 정리

- **스키마·DTO·Model은 다른 것이다.** 스키마 = DB가 집행하는 저장 규칙, DTO = 경계를 오가는 포장, Model = 앱이 다루는 업무 개념. Drizzle `schema.ts`는 타입이 붙은 `CREATE TABLE` 선언에 가깝다.
- **PK는 행을 유일하게 식별하고, FK는 대상 행의 존재만 검사한다.** FK 중복은 허용되므로 「사용자당 하나」는 PK+FK, 「같은 사용자의 같은 코인 하나」는 복합 PK로 막는다.
- **원화 확정액은 `bigint`, 소수 수량·단가는 `numeric`/문자열.** → [컴퓨터의 수 표현](../%EC%BB%B4%ED%93%A8%ED%84%B0%EA%B5%AC%EC%A1%B0/%EC%BB%B4%ED%93%A8%ED%84%B0%EC%9D%98%20%EC%88%98%20%ED%91%9C%ED%98%84.md)
- **「조회 → 없으면 삽입」은 동시 요청에 틈이 있다.** `INSERT ... ON CONFLICT DO NOTHING → SELECT`로 판정과 중복 방지를 DB가 원자적으로 집행하게 한다. 충돌 때 update하면 재호출마다 값이 되돌아가므로 반드시 do nothing.
- **정적 검사가 성공해도 DB 동작은 증명되지 않는다.** 두 번 호출한 뒤 행 수·값이 그대로인지 봐야 멱등성이 검증된다.
- **확인과 차감은 문장 하나로, 여러 쓰기는 트랜잭션 하나로.** `UPDATE ... WHERE cash >= cost`가 바꾼 줄이 0개면 실패다. Drizzle 트랜잭션은 콜백이 return하면 COMMIT, throw하면 ROLLBACK이라 첫 쓰기 이후의 실패는 throw로 끝낸다.

### 2026-08-28 — Drizzle로 스키마·키·정밀 숫자를 실제 DB에 내리기

- 맥락: [MyCryptoDiary](../../../../%ED%94%84%EB%A1%9C%EC%A0%9D%ED%8A%B8/%EA%B0%9C%EC%9D%B8/MyCryptoDiary/README.md) D2 Neon + Drizzle 스키마 ([작업 기록](../../../../%ED%94%84%EB%A1%9C%EC%A0%9D%ED%8A%B8/%EA%B0%9C%EC%9D%B8/MyCryptoDiary/Neon%20Drizzle%20%EC%8A%A4%ED%82%A4%EB%A7%88%202026-08-28.md)).
- 배운 것:
  - **스키마는 DB가 집행하는 저장 규칙**, DTO는 경계를 오가는 포장, Model은 앱이 다루는 업무 개념과 규칙이다. Drizzle `schema.ts`는 타입 파일이라기보다 타입이 붙은 `CREATE TABLE` 선언에 가깝다.
  - PK는 현재 테이블의 행을 유일하게 식별하고, FK는 다른 테이블에 대상 행이 존재하는지만 검사한다. FK 중복은 허용되므로 `accounts.user_id`를 PK+FK로 둬야 사용자당 계좌 하나가 된다. `holdings`는 `(user_id, market)` 조합을 복합 PK로 둬야 같은 사용자의 같은 코인 행만 중복을 막는다.
  - TypeScript의 `!`는 환경변수를 만들거나 검사하지 않는다. `DATABASE_URL`을 런타임에서 검사하고 `throw`해야 `string | undefined`가 `string`으로 좁혀진다. `return Error`는 실패가 아니라 Error 생성자를 정상 반환하는 다른 동작이다.
  - 원화 확정액은 `bigint`/TypeScript `bigint`, 소수 수량·단가·수익률은 PostgreSQL `numeric`/TypeScript 문자열로 유지한다. `10_000_000n`을 쓰려면 TS target도 ES2020 이상이어야 한다.
  - `rank_snapshots`는 원본이 아니라 계좌·보유·시세에서 재생성 가능한 파생 캐시다. 최신값만 필요해 `user_id` PK로 한 행을 upsert하고, `snapshot_at`으로 신선도를 드러낸다.

### 2026-11-21: 매수 한 번을 트랜잭션 하나로 묶기

- 맥락: [MyCryptoDiary](../../../../%ED%94%84%EB%A1%9C%EC%A0%9D%ED%8A%B8/%EA%B0%9C%EC%9D%B8/MyCryptoDiary/README.md) 새 구현의 시장가 매수. 현금 빼기, 보유 갱신, 주문 기록을 한 번에 저장해야 했다.
- 궁금했던 것: 「트랜잭션은 같이 생성하고 실패하면 같이 실패하는 거지?」, 「콜백의 tx는 뭘 받는 거야?」, 「커밋되는 순간은 언제야?」, 「cash_krw는 왜 bigint 그대로 주고받아?」
- 알게 된 것:
  - 잔고 확인과 차감은 `UPDATE accounts SET cash_krw = cash_krw - cost WHERE user_id = ? AND cash_krw >= cost` 한 문장으로 한다. 읽고 나서 JS에서 빼면 두 번 누른 요청이 둘 다 통과한다. 이 UPDATE가 계좌 줄을 COMMIT까지 잠가 같은 사람의 다음 매수가 기다린다. `returning()`이 빈 배열이면 잔액 부족이거나 계좌 줄이 아예 없는 것이다. 실제로 계좌 생성이 연결되지 않아 이 경로로 「잔액 부족」이 나왔다.
  - `tx`는 Drizzle이 BEGIN한 연결에 묶어 콜백에 넘겨주는 전용 핸들이다. 콜백 안 쿼리는 반드시 `tx`로, 반드시 `await`로 보낸다. 바깥 `db`를 쓰면 트랜잭션 밖에서 따로 실행된다.
  - 콜백이 return하면 COMMIT, throw하면 ROLLBACK이다. `return false`도 COMMIT이다. 홍이 보유 읽기 뒤에 `if (!holding) return false`를 넣었다가, 첫 구매마다 현금만 빠진 채 저장된다는 것을 보고 지웠다. 보유가 없는 것은 실패가 아니라 새 줄을 넣을 경우다.
  - 문장이 하나뿐이면 트랜잭션의 의미는 거의 없다. Postgres는 문장 하나를 원래 원자적으로 실행한다.
  - Drizzle 쿼리는 `tx.update().set().where().returning()`처럼 점으로 잇고, 조건은 `and(eq(...), gte(...))`처럼 함수 안에 함수를 넣는다(점 없음). `set` 값이 「지금 DB 값에서 빼기」면 JS 계산이 아니라 `` sql`${열} - ${값}` ``이다.
  - `gte`는 문자열에도 사전 순으로 동작한다. `market`에 쓰면 오류 없이 다른 코인 줄을 잡는다. 같은 줄을 찾을 때는 `eq`.
  - `numeric(30,8)`은 Drizzle이 문자열로, `bigint` 모드 칸은 JS `bigint`로 준다. 원 단위 정수는 `bigint`에 정확히 담기고, 소수는 JS에 정확히 담을 그릇이 없어서다. 읽자마자 1억분의 1 단위 `bigint`로 바꾸고 쓰기 직전에 문자열로 되돌린다. `amount`, `fee`처럼 원래 정수인 칸에 이 변환을 쓰면 50,000원이 0.0005원이 된다.
- 근거: MyCryptoDiary `3503c90`, `e0b62ee`, `d11df13`, `d63df2f`, `24b40a2`, `src/features/market-buy/api/placeBuyOrder.ts`. 50,000원 매수 뒤 DB 조회로 현금 9,949,975, 보유 0.00061525, 주문 amount 50000 fee 25 확인.
