# 키와 스키마 설계

**스키마는 DB가 집행하는 저장 규칙이고, 유일성·동시성 판정은 코드가 아니라 PK에 맡긴다.** (2026-09-16 [[학습/공부/CS/데이터베이스/데이터베이스|데이터베이스]]에서 분리)

## 핵심 정리

- **스키마·DTO·Model은 다른 것이다.** 스키마 = DB가 집행하는 저장 규칙, DTO = 경계를 오가는 포장, Model = 앱이 다루는 업무 개념. Drizzle `schema.ts`는 타입이 붙은 `CREATE TABLE` 선언에 가깝다.
- **PK는 행을 유일하게 식별하고, FK는 대상 행의 존재만 검사한다.** FK 중복은 허용되므로 「사용자당 하나」는 PK+FK, 「같은 사용자의 같은 코인 하나」는 복합 PK로 막는다.
- **원화 확정액은 `bigint`, 소수 수량·단가는 `numeric`/문자열.** → [[학습/공부/CS/컴퓨터구조/컴퓨터의 수 표현|컴퓨터의 수 표현]]
- **「조회 → 없으면 삽입」은 동시 요청에 틈이 있다.** `INSERT ... ON CONFLICT DO NOTHING → SELECT`로 판정과 중복 방지를 DB가 원자적으로 집행하게 한다. 충돌 때 update하면 재호출마다 값이 되돌아가므로 반드시 do nothing.
- **정적 검사가 성공해도 DB 동작은 증명되지 않는다.** 두 번 호출한 뒤 행 수·값이 그대로인지 봐야 멱등성이 검증된다.

## 기록

### 2026-08-28 — Drizzle로 스키마·키·정밀 숫자를 실제 DB에 내리기

- 맥락: [[프로젝트/개인/MyCryptoDiary/README|MyCryptoDiary]] D2 Neon + Drizzle 스키마 ([[프로젝트/개인/MyCryptoDiary/Neon Drizzle 스키마 2026-08-28|작업 기록]]).
- 배운 것:
  - **스키마는 DB가 집행하는 저장 규칙**, DTO는 경계를 오가는 포장, Model은 앱이 다루는 업무 개념과 규칙이다. Drizzle `schema.ts`는 타입 파일이라기보다 타입이 붙은 `CREATE TABLE` 선언에 가깝다.
  - PK는 현재 테이블의 행을 유일하게 식별하고, FK는 다른 테이블에 대상 행이 존재하는지만 검사한다. FK 중복은 허용되므로 `accounts.user_id`를 PK+FK로 둬야 사용자당 계좌 하나가 된다. `holdings`는 `(user_id, market)` 조합을 복합 PK로 둬야 같은 사용자의 같은 코인 행만 중복을 막는다.
  - TypeScript의 `!`는 환경변수를 만들거나 검사하지 않는다. `DATABASE_URL`을 런타임에서 검사하고 `throw`해야 `string | undefined`가 `string`으로 좁혀진다. `return Error`는 실패가 아니라 Error 생성자를 정상 반환하는 다른 동작이다.
  - 원화 확정액은 `bigint`/TypeScript `bigint`, 소수 수량·단가·수익률은 PostgreSQL `numeric`/TypeScript 문자열로 유지한다. `10_000_000n`을 쓰려면 TS target도 ES2020 이상이어야 한다.
  - `rank_snapshots`는 원본이 아니라 계좌·보유·시세에서 재생성 가능한 파생 캐시다. 최신값만 필요해 `user_id` PK로 한 행을 upsert하고, `snapshot_at`으로 신선도를 드러낸다.
- 근거: MyCryptoDiary 커밋 `1cfe07c`·`8eadff3`·`f7ccda4`, PR #5. Neon에 6테이블을 반영하고 seed 최초·재실행 및 Studio 읽기를 확인했다.

### 2026-08-29 — 계좌 lazy create의 동시성을 PK에 맡기기

- 맥락: [[프로젝트/개인/MyCryptoDiary/README|CoinPilot]] D3 Clerk 인증 ([[프로젝트/개인/MyCryptoDiary/Clerk 인증 D3 2026-08-29|작업 기록]]).
- 배운 것:
  - "계좌가 있는지 조회 → 없으면 삽입"은 두 요청이 동시에 조회하면 둘 다 없다고 판단하는 틈이 있다. `accounts.user_id` PK가 중복을 막게 하고 `INSERT ... ON CONFLICT DO NOTHING → SELECT`로 만들면 판정과 중복 방지를 DB가 원자적으로 집행한다.
  - `users`와 `accounts`는 FK 순서로 같은 트랜잭션에 넣어야 둘 중 하나만 남는 상태를 막는다. 기존 계좌 충돌 때 update하면 페이지 재호출마다 잔액을 1,000만원으로 되돌릴 수 있으므로 반드시 do nothing이다.
  - 정적 검사가 성공해도 DB 동작은 증명되지 않는다. 로그인 홈을 두 번 호출한 뒤 Neon Studio에서 행 수와 잔액이 그대로인지 확인해야 멱등성이 검증된다.
- 근거: MyCryptoDiary 커밋 `ffcb94c`, PR #7. `src/entities/account/api/getOrCreateAccount.ts`; Neon에서 최초 생성과 재호출을 확인했다.
