# 네트워크

인터넷이 실제로 어떻게 동작하는가 — 응용(HTTP·DNS·TLS), 전송(TCP·UDP), 네트워크(IP) 계층을 위에서 아래로. [[학습/공부/CS/OSI 7계층|OSI 7계층]] 다음 단계이며, 소마 백엔드 API와 앱의 통신 문제를 계층으로 설명할 수 있는 것이 목표.

## 핵심 정리

### 계층 모델과 오류 검출 (44강까지)

- **계층의 진짜 차이는 "얼마나 멀리 책임지나"다.** 이게 4계층을 관통하는 열쇠다 — 애플리케이션은 프로그램↔프로그램(무슨 내용), 전송은 프로세스↔프로세스(어느 프로그램·다 왔나), 인터넷은 컴퓨터↔컴퓨터 **끝까지**(어느 길로), 링크는 **바로 옆 장비까지 한 구간**(다음 한 칸은 누구). 주소가 4번 바뀌는 것도 담당 거리가 4가지라서다.
- **그래서 IP는 경로 내내 안 바뀌고, MAC은 홉마다 매번 갈아끼워진다.** 인터넷 계층은 끝까지를, 링크 계층은 한 칸만 책임지기 때문이다. 송장의 최종 주소(IP)는 그대로고 "지금 이 물건을 실은 기사가 다음에 들를 물류센터"(MAC)만 계속 바뀌는 것. **면접 단골 "IP와 MAC이 왜 둘 다 필요한가"의 답이 이것.**
- **계층 = 주소가 갈아끼워지는 지점이다.** 기능 4개가 아니라 주소 체계가 4번 바뀌는 것으로 보면 잡힌다 — URL(애플리케이션) → 포트(전송) → IP(인터넷) → MAC(링크). 위에서 아래로 "사람이 읽는 주소 → 기계가 읽는 주소"로 내려가고, **캡슐화는 이 주소들을 겉에 하나씩 더 붙이는 일**이다. 다음 한 구간을 옮기는 장비는 맨 바깥 라벨만 보면 된다.
- **계층을 나눈 실질적 이득은 "갈아끼울 수 있다"는 것.** 와이파이 → 테더링으로 바꾸면 MAC·게이트웨이·경로가 전부 바뀌지만 애플리케이션의 `fetch()` 코드는 한 글자도 안 바뀐다. 링크 계층만 통째로 교체됐는데 위층이 그걸 모른다는 게 계층화의 값이다.
- **TCP와 IP가 짝인 이유는 정확히 반대 일을 해서다.** IP는 길만 정하고 던진다(도착·순서 보장 없음) = 배달, TCP는 그 위에서 순서 번호·재전송·도착 확인을 한다 = 등기. IP 없이는 갈 곳을 모르고, TCP 없이는 믿을 수 없다.
- **TCP/IP 4계층 = 애플리케이션 / 전송 / 인터넷 / 링크.** 계층을 나누는 이유는 각 계층이 자기 관심사만 보게 하려는 것이다 — TCP는 신뢰성만, IP는 라우팅만. **캡슐화가 그 분리를 물리적으로 구현한다.**
- **캡슐화 = 내려가면서 헤더를 두르는 것**, 비캡슐화는 수신 측에서 역순으로 벗는 것. 메시지 → (TCP 헤더) 세그먼트 → (IP 헤더) 패킷 → (프레임 헤더 + FCS 트레일러) 프레임 → 비트.
- **각 계층은 원본을 열어보지 않는다 — 앞에 자기 헤더만 붙인다.** IP는 안에 TCP가 들었든 UDP가 들었든 "그냥 짐"으로 본다. 이 무관심이 계층이 독립일 수 있는 이유다.
- **헤더가 앞에 붙는 이유는 받는 쪽이 앞에서부터 읽기 때문**이고, **FCS만 뒤에 붙는 이유는 앞의 내용을 전부 읽어야 계산되는 값이기 때문**이다(시험지 다 풀고 맨 아래 검산). 위치가 자의적이지 않다.
- **장비가 어디까지 벗기는지가 곧 그 장비의 정체다.** 스위치는 프레임 헤더까지(2계층) → **IP를 모른다**. 라우터는 IP 헤더까지(3계층) → 원칙적으로 **포트를 모른다**. 서버는 끝까지 벗겨 HTTP를 읽는다. (예외: 가정용 공유기는 NAT 때문에 포트까지 본다 → 58강)
- **"다 패킷"은 대충 맞고 정확하진 않다** — 계층마다 PDU 이름이 따로 있다(메시지 / 세그먼트·데이터그램 / 패킷 / 프레임 / 비트). 이름을 정확히 부르면 "어느 헤더를 열어봐야 하는가"가 바로 정해진다.
- **세그먼트·패킷·프레임은 서로 다른 물건이 아니라 같은 데이터의 껍질 겹수다.**

  ```
  "BTC 시세 줘"                        ← 메시지
  [TCP헤더|"BTC 시세 줘"]                ← 세그먼트 (포트가 붙음)
  [IP헤더|TCP헤더|"BTC 시세 줘"]          ← 패킷    (IP가 붙음)
  [프레임헤더|IP헤더|TCP헤더|"..."|FCS]    ← 프레임   (MAC이 붙고 뒤에 검사값)
  ```
- **PDU 이름을 구분하는 실익 = 계층마다 "한 덩어리"의 크기가 다르다는 것.** 100KB JSON 하나는 메시지 1개지만 세그먼트 수십 개, 프레임 수십 개가 된다. **프레임 하나는 최대 1500바이트(MTU)** 까지라서 TCP가 애초에 그보다 작게 잘라야 한다 → `MTU 1500 − IP헤더 20 − TCP헤더 20 = MSS 1460`. "세그먼트가 크면 프레임에 안 들어간다"는 문장은 이름을 구분해야만 쓸 수 있다. (45강 MTU·MSS·PMTUD의 전제)
- **트레일러가 붙는 계층은 링크 계층뿐**이다. 나머지는 헤더만 붙는다.
- **OSI 7계층은 TCP/IP 4계층을 쪼갠 것**이고 차이는 세 가지뿐이다 — 애플리케이션을 셋으로, 링크를 둘로 쪼개고, 인터넷 계층을 네트워크 계층이라 부른다. 대응표는 [[학습/공부/CS/OSI 7계층|OSI 7계층]] `## 핵심 정리`.
- **오류 검출 알고리즘은 계층마다 다르다.** IPv4 헤더·TCP/UDP 헤더는 **1의 보수합**, 이더넷 FCS는 **CRC-32**. 1의 보수합은 16비트씩 더하되 넘친 캐리를 하위로 되더하고(순환 캐리) 마지막에 비트 반전 → 수신 측은 `데이터 + 체크섬 == 0xFFFF`로 판정. CRC는 XOR 이진 나눗셈의 나머지 → 나머지 0이면 정상.

### 계층화를 왜 하는가 (44강)

- **한 문장: 곱셈을 덧셈으로 바꾸려고 나눴다.** 링크 L가지 × 앱 A가지를 계층 없이 짜면 L×A개, 계층이 있으면 L+A개. 새 기술이 들어올 때 차이가 난다 — 6G가 나와도 링크 구현 1개만 추가하면 위의 앱 전부가 그대로 올라탄다.
- **디버깅에서 계층은 좌표계다.** `ping`(2·3계층) → `nslookup`(DNS) → `curl -v`(4·7계층)로 고장 범위를 이분 탐색. 계층이 없으면 "안 된다"만 남고 좁힐 축이 없다.
- **대가 3가지 (면접 "계층화의 단점은?" 답).**
  1. **헤더 오버헤드** — 이더넷 14 + IP 20 + TCP 20 = **54바이트가 순수 포장지**(1500 대비 3.6%). 짧은 메시지일수록 나빠진다.
  2. **기능 중복** — 오류 검사가 링크(CRC-32)·인터넷(1의 보수합)·전송(TCP 체크섬)에 **세 번** 돈다. 각 계층이 서로를 못 믿게 설계돼서다.
  3. **정보 은닉의 대가** — 무선 유실의 원인은 보통 전파 간섭인데 TCP는 링크 사정을 모르니 **"혼잡"으로 오해해 속도를 줄인다.** 줄여도 간섭은 안 없어진다. **계층 독립성을 만든 그 무관심이 여기선 손해로 돌아온다.** ← 셋 중 이게 핵심
- 설계 근거(모래시계·변화 속도·계층 위반)는 → `## 더 알아보면 좋은 것`

(TCP 3-way handshake·흐름/혼잡 제어, HTTP/1.1 vs 2 vs 3, DNS 조회 흐름, TLS 핸드셰이크는 해당 강의를 들으면서 여기에 이어 채운다)

## 더 알아보면 좋은 것

지금 안 외워도 되지만 버리기 아까운 것. **선반이지 숙제가 아니다** — 안 봐도 진도에 아무 문제 없다.

### 계층화의 설계 근거 (2026-08-22, 44강에서 파고든 것)

- **조합 폭발의 숫자판** — 링크 기술 L가지 × 앱 프로토콜 A가지를 계층 없이 짜면 조합 L×A개를 각각 구현해야 한다(예: 10×20 = 200). 계층이 있으면 L+A = 30개다. 진짜 차이는 **새 기술이 들어올 때** — 6G가 나오면 계층 없는 세계는 앱 20개를 다 다시 짜고, 있는 세계는 링크 구현 1개만 추가하면 기존 20개가 그대로 올라탄다.
- **그래서 인터넷은 모래시계(hourglass) 모양이다 — "IP over everything, everything over IP".** 위(앱 프로토콜)도 아래(링크 기술)도 계속 넓어지는데 **허리는 IP 하나로 좁혀** 놓았다. RFC 1958이 이걸 명시한다: *"there should be one, and only one, protocol at the Internet level."* 허리가 하나뿐이라 위아래가 서로를 몰라도 되고, 그래서 각자 마음대로 늘어날 수 있다. 허리가 둘이었다면 위의 모든 앱이 "어느 허리로 갈지"를 알아야 했다.
- **자를 곳을 정한 기준은 기능이 아니라 「변화 속도」다.** 애플리케이션=매년 새로 생김(gRPC·WebRTC) / 전송=수십 년에 한 번(TCP 1974 → QUIC 2021) / 인터넷=거의 안 바뀜(IPv4 1981년부터, IPv6 전환 30년째) / 링크=카페 옮길 때마다. **자주 바뀌는 것과 안 바뀌는 것을 한 덩어리에 두면 안 바뀌어도 될 것이 끌려서 다시 짜인다.** 경계는 변화 속도가 꺾이는 지점에 놓는다 — [[학습/공부/JS/Feature-Sliced Design|Feature-Sliced Design]]의 `shared ← entities ← features ← pages`도 정확히 같은 논리다.
- **계약이 고정되니 양쪽이 따로 진화한다.** 계층 간 계약은 "IP한테 주면 저쪽 컴퓨터까지 가져다 놓는다(순서·도착은 보장 안 함)" 뿐이다. 이 계약 덕에 HTTP/1.1→2→3, 와이파이4→6E, TLS 1.2→1.3이 **서로의 코드를 한 줄도 안 건드리고** 각각 일어났다.
- **그래서 현실에는 계층 위반이 흔하다** — 공유기 NAT는 3계층 장비인데 4계층 포트를 보고(→58강), L7 로드밸런서는 HTTP 경로까지 연다. 깔끔한 모델이 성능·기능 앞에서 타협되는 지점.
- 원문: [RFC 1958](https://www.rfc-editor.org/rfc/rfc1958) §2·§3 (모래시계 허리), [RFC 3439](https://www.rfc-editor.org/rfc/rfc3439) §3 「Layering Considered Harmful」 (대가)

> [!important] 세션 운영 (2026-08-25 도입 — 44강에서 5일 멈춘 뒤)
> - **정리는 세션 마지막 10분, 타이머.** 거친 불릿 3~5개면 끝. 볼드·근거 줄·링크 확인·위키링크는 **안 한다** — 그건 일요일 정리 세션 몫이다.
> - **한 강의 최대 2세션.** 넘으면 `## 막힌 것`에 질문으로 내리고 진도를 뺀다.
> - **일요일은 정리 세션, 진도 0.** 화~토 5세션은 강의 그대로 두고 일요일 하나를 정리에 쓴다. 그 주 `## 기록`의 거친 불릿 중 한 주 지나도 중요한 것만 골라 `## 핵심 정리`로 승격시키며 지금 밀도로 다시 쓴다. `## 막힌 것`의 답도 여기서 찾는다. **뭐가 중요한지는 세션 중엔 모르고 한 주 지나야 보인다 — 이 선별이 곧 "내가 모르는 것"을 드러내는 장치다.**

### 2026-08-18 — 포트·localhost·사설 IP (강의 전에 프로젝트에서 먼저 만남)

- 맥락: [[프로젝트/개인/MyCryptoDiary/README|MyCryptoDiary]] D1에서 `npm run dev`로 띄운 서버가 왜 `localhost:3000`으로 보이는지 물으며 ([[프로젝트/개인/MyCryptoDiary/모의투자 전환 D1 2026-08-16|작업 기록]]). W1 강의(38강~) 시작 전에 실물로 먼저 부딪힌 내용이라 여기 남긴다.
- 배운 것:
  - **서버 = 특별한 하드웨어가 아니라 포트를 잡고 LISTEN 하고 있는 프로그램.** `lsof -nP -iTCP:3000 -sTCP:LISTEN`으로 `node ... TCP *:3000 (LISTEN)` 확인. 끄면 서버가 사라진다.
  - **포트 = 한 컴퓨터 안에서 어느 프로그램인지 구분하는 번호**(0~65535). IP는 "어느 컴퓨터"까지만 알려준다. 80=HTTP, 443=HTTPS, 5432=Postgres. **3000번은 아무 의미 없고 Node 생태계 관습**일 뿐 — `-p 4000`이면 그대로 동작한다.
  - **`localhost` = `127.0.0.1` = 루프백.** 요청이 랜카드로 나갔다 오지 않고 OS 안에서 되돌아온다. 랜선을 뽑아도 동작한다.
  - **"나만 볼 수 있다"는 절반만 맞다.** LISTEN 주소가 `127.0.0.1:3000`이면 정말 나만 보지만, `*:3000`이면 모든 인터페이스에서 듣는 것이라 **같은 와이파이의 다른 기기는 `192.168.x.x:3000`으로 접속 가능**하다(핸드폰 테스트에 씀). 다만 `192.168.x.x`는 사설 IP라 공유기 밖 인터넷에서는 찾아올 수 없다. 즉 정확히는 "인터넷에 공개되지 않았다".
  - 왜 브라우저가 외부 API를 직접 부르면 안 되는가 → **CORS**. 우리 서버에 same-origin 창구(route handler)를 두는 이유. 자세한 건 [[학습/공부/JS/Next.js 서버와 캐싱|Next.js 서버와 캐싱]], CORS 자체는 W3-4 94강에서.
- 근거: 로컬 `lsof` 출력, `ipconfig getifaddr en0` → `192.168.35.199`


### 2026-08-21 — TCP/IP 4계층: 캡슐화·PDU·OSI 대응·체크섬 (44강)

- 맥락: [CS 지식의 정석] 네트워크 **W1-2 = 44강 「TCP/IP 4계층 #1. 캡슐화, 비캡슐화, PDU, OSI 7계층」** 수강. 전날 08-20에 W1-1(38~43강 — 기초·토폴로지·병목·유니/멀티/브로드캐스트·LAN/MAN/WAN)을 끝낸 다음 순서다. 계획보다 이틀 밀려 시작했으므로 W1은 08-22~08-24에 W1-3~W1-5를 붙여야 따라잡는다.
- 배운 것:
  - **애플리케이션 계층 ≠ 애플리케이션.** 브라우저·메일 클라이언트 같은 UI 프로그램이 아니라, **그 프로그램이 네트워크와 말할 수 있게 해주는 프로토콜들의 집합**(HTTP·SMTP·FTP·SSH)이 그 계층이다. 강의가 따로 짚을 만큼 헷갈리는 지점.
  - **캡슐화는 계층화를 실제로 성립시키는 장치다.** 상위 계층 데이터를 하위 계층이 헤더로 감싸기 때문에 각 계층이 자기 일만 하면 된다(TCP=신뢰성, IP=라우팅). "계층으로 나눴다"가 구호가 아니라 데이터 구조로 드러나는 지점.
  - **PDU 이름이 계층마다 다르다** — 메시지 / 세그먼트(TCP, 연결형)·데이터그램(UDP, 비연결형) / 패킷 / 프레임 / 비트.
  - **트레일러는 링크 계층에만 붙는다.** 이더넷 프레임은 앞에 헤더(Dest MAC · Src MAC · EtherType), 뒤에 FCS 트레일러(CRC 값). 상위 계층은 헤더만 붙인다.
  - **OSI 7계층은 TCP/IP 4계층의 세분화판**이라는 게 대응의 전부다 — 애플리케이션 → 애플리케이션·프레젠테이션(인코딩/디코딩·암호화)·세션(세션 관리), 링크 → 데이터링크·물리, 인터넷 계층은 이름만 네트워크 계층. → 표는 [[학습/공부/CS/OSI 7계층|OSI 7계층]]에 작성했다.
  - **체크섬은 하나가 아니라 계층별로 다른 알고리즘**이다: IPv4 헤더·TCP/UDP 헤더 = 1의 보수합, 이더넷 FCS = CRC-32.
  - **1의 보수합의 핵심은 순환 캐리(end-around carry)** — 16비트를 넘긴 캐리를 버리지 않고 하위로 되더한다(`0xFFFF + 0x0001 = 0x10000` → `0x0000 + 0x0001 = 0x0001`). 합의 비트를 반전한 값이 체크섬이고, 수신 측은 `데이터 + 체크섬`의 합이 `0xFFFF`인지로 손상을 판정한다.
  - **CRC는 XOR 기반 이진 나눗셈의 나머지.** 원본 뒤에 다항식 차수만큼 0을 붙여 나누고, 나머지를 데이터 뒤에 붙여 보낸다 → 수신 측이 같은 방식으로 나눠 나머지가 0이면 오류 없음.
- 근거: 교안 「CS - 네트워크」(version.25.09.26) pp.34~42 — PDU 목록 p.37, 이더넷 프레임 헤더/트레일러 p.38, 체크섬 알고리즘 표 p.39, 순환 캐리·1의 보수합 파이썬 예시 pp.40~41, CRC p.42


### 2026-08-21 — 44강이 어려웠던 이유와, 계층을 내 맥에서 눈으로 확인하기

- 맥락: 위 44강 정리 직후 "TCP/IP가 너무 어렵다"고 느껴서 다시 붙잡은 것. 교안 43/225쪽까지 진행(44강 끝, 45강 시작 지점).
- 배운 것:
  - **왜 어려웠는지가 먼저다: 44강은 강의에서 처음으로 "눈에 안 보이는 것"만 나오는 구간이다.** 38~43강(토폴로지·LAN/MAN/WAN)은 그림으로 그려졌는데 44강부터는 헤더·PDU·계층처럼 실체가 안 잡히는 단어뿐이라, 외우려 들면 안 외워진다. **실물을 하나씩 붙여야 잡힌다.**
  - **계층은 "기능 4개"가 아니라 "주소가 4번 갈아끼워지는 지점"이다.** 이 프레임으로 보니 캡슐화가 자동으로 따라왔다 — 주소를 겉에 하나씩 더 붙이는 것이 곧 캡슐화다.
  - **각 계층을 맥에서 명령어 하나로 실물 확인할 수 있다** (실제로 해봄, 아래 근거):

    | 계층 | 주소 | 확인 명령어 |
    |---|---|---|
    | 애플리케이션 | URL | `curl -v <url>` |
    | 전송 | 포트 | `lsof -nP -iTCP -sTCP:ESTABLISHED` |
    | 인터넷 | IP·경로 | `route get default` / `netstat -rn` |
    | 링크 | MAC | `arp -a` / `ifconfig en0 \| grep ether` |

    → 08-18에 [[프로젝트/개인/MyCryptoDiary/README|MyCryptoDiary]]에서 `lsof`로 포트를 봤던 게 사실 **전송 계층을 본 것**이었다. 그때는 계층 언어가 없어서 그렇게 부르지 못했다.
  - **계층화의 값은 "갈아끼울 수 있다"는 것.** 와이파이 → 테더링이면 MAC·게이트웨이·경로가 전부 바뀌는데 `fetch()` 코드는 안 바뀐다. 교안의 "TCP는 신뢰성만, IP는 라우팅만"이 추상적으로 들렸던 게 이 얘기였다.
  - **TCP와 IP가 붙어 다니는 이유 = 정확히 반대 일을 해서.** IP는 길만 정하고 던진다(배달), TCP는 그 위에서 순서·재전송·확인을 한다(등기).
  - **지금 안 외워도 되는 것을 정한 것도 소득이다.** 1의 보수합·CRC를 손으로 계산할 필요는 없다. 면접에서 나오는 건 "왜 계층마다 또 검사하나" 수준이고, `IP·TCP 헤더 = 1의 보수합 / 이더넷 프레임 = CRC-32` 한 줄이면 된다. **어려운 구간에서는 외울 것과 넘길 것을 나누는 게 진도보다 중요하다.**
- 근거: 내 맥 실측 — `route get default` → `gateway 192.168.35.1`, `interface en0`, **`mtu 1500`** / `arp -a` → `192.168.35.1 at 0:23:aa:d8:aa:d9` / `ifconfig en0` → `ether c0:c7:db:21:24:78` / `ipconfig getifaddr en0` → `192.168.35.199`
- 다음: `route get default`에 이미 찍힌 **`mtu 1500`이 45강(MTU·MSS·PMTUD)의 주제**다. 1500 − IP헤더 20 − TCP헤더 20 = MSS 1460을 강의에서 확인할 것. 44강과 달리 45강은 숫자로 바로 검증되는 구간이라 실측과 함께 볼 것.


### 2026-08-22 — 44강 다시 설명받으며 잡은 것: 계층 = 책임지는 거리

- 맥락: 44강(교안 pp.34~42)을 들은 뒤에도 안 잡혀서 캡슐화·비캡슐화·PDU·OSI 7계층을 처음부터 다시 설명받은 것. 08-21의 "주소가 4번 바뀐다" 프레임에서 한 겹 더 들어갔다.
- 배운 것:
  - **계층의 차이는 기능이 아니라 "책임지는 거리"다.** 애플리케이션=프로그램↔프로그램, 전송=프로세스↔프로세스, 인터넷=컴퓨터↔컴퓨터 **끝까지**, 링크=**바로 옆 장비 한 구간**. 주소가 4가지인 것도 담당 거리가 4가지라서다 — 이 순서로 봐야 캡슐화가 "왜 필요한지"까지 따라온다.
  - **IP는 경로 내내 그대로고 MAC은 홉마다 바뀐다.** 인터넷 계층은 끝까지를, 링크 계층은 한 칸만 책임지니까. 교안이 이 대비를 명시하지 않는데, **"IP와 MAC이 왜 둘 다 필요한가"라는 면접 단골 질문의 답이 정확히 이것**이다.
  - **각 계층은 안에 든 것을 열어보지 않는다.** IP 입장에서 TCP 세그먼트는 그냥 짐이다. 이 무관심이 계층 독립성의 실체 — "각 계층이 자기 일만 한다"가 구호가 아닌 이유.
  - **헤더 위치가 자의적이지 않다.** 헤더가 앞인 건 받는 쪽이 앞에서부터 읽어야 해서고, **FCS만 뒤인 건 앞 내용을 다 읽어야 계산되는 값**이라서다.
  - **장비가 어디까지 벗기는지가 그 장비의 정체다** — 스위치는 2계층까지(IP를 모름), 라우터는 3계층까지(원칙적으로 포트를 모름), 서버는 끝까지. 단 가정용 공유기는 NAT 때문에 포트까지 본다(→ 58강에서 확인할 것).
  - **PDU 이름을 나누는 실익은 계층마다 한 덩어리 크기가 다르기 때문**이다. 프레임 하나는 1500바이트(MTU)가 한계라 TCP가 미리 그보다 작게 자른다(MSS 1460). "세그먼트가 크면 프레임에 안 들어간다"는 말은 이름을 구분해야 성립한다.
  - **OSI가 왜 따로 있는지는 역사로 풀린다.** TCP/IP는 1970년대에 개발돼 1983년 ARPANET이 전면 전환한 실물, OSI는 1984년 ISO 7498(= ITU-T X.200)로 나온 국제 표준안. 표준 경쟁에서 TCP/IP가 이겼고 **OSI는 "말하기 위한 언어"로만 남았다.** 실제 코드에 OSI 5계층 같은 건 없다.
  - **프레젠테이션·세션은 TCP/IP에 대응 계층이 없는 빈 칸이다.** 인코딩·암호화·세션 관리는 실제로 애플리케이션 프로토콜(UTF-8·TLS·쿠키·keep-alive)이 알아서 한다. "실무에선 어디 있나요"에 이렇게 답하면 된다.
  - 암기법: **P**lease **D**o **N**ot **T**hrow **S**ausage **P**izza **A**way (물리→애플리케이션 순).
- 근거: 교안 「CS - 네트워크」 pp.34~42, 08-21 실측(`route get default` → `mtu 1500`, `arp -a` → 게이트웨이 MAC). 면접 답변 형태로 정리한 5문항은 [[학습/공부/CS/OSI 7계층|OSI 7계층]] `## 핵심 정리`와 이 파일 핵심 정리에 반영.
- 다음: 45강에서 MSS 1460을 강의로 확인. **44강처럼 안 잡히는 구간이 또 오면 "진도를 더 빼지 말고 프레임을 바꿔 다시 설명받기"가 실제로 먹혔다는 것**을 기억할 것.


### 2026-08-22 — 계층화를 「왜」 하는가: 조합 폭발·모래시계·변화 속도, 그리고 그 대가

- 맥락: 같은 날 44강을 "계층 = 책임지는 거리"로 다시 잡은 직후, **"계층화를 왜 이렇게 해야 하나"** 를 물어서 설계 근거까지 내려간 것. 앞선 기록들이 *무엇이 어떻게 나뉘는가*였다면 이번은 *왜 나눠야만 했는가*다.
- 배운 것:
  - **계층화의 목적은 정리정돈이 아니라 조합 폭발 차단이다.** 링크 L가지 × 앱 A가지 = L×A를 L+A로 줄이는 것. 새 링크 기술이 들어올 때 위층 전부를 다시 짜지 않아도 되는 것이 실질 이득이다. 08-21에 적은 "와이파이→테더링에도 `fetch`가 안 바뀐다"가 이 원리의 1인칭 버전이었다.
  - **모래시계 모형(hourglass)** — 위도 아래도 넓은데 허리는 IP 하나. **"IP over everything, everything over IP."** RFC 1958이 *"one, and only one, protocol at the Internet level"* 로 못 박아 놓았다. 허리를 하나로 좁힌 것이 위아래의 자유를 만든다.
  - **경계를 어디에 그을지의 기준은 「변화 속도」다.** 앱=매년, 전송=수십 년, IP=거의 불변, 링크=수시로. 속도가 다른 것을 한 덩어리에 넣으면 안 바뀌어도 될 것이 끌려간다. **이건 네트워크 고유 원리가 아니라 모듈 경계의 일반 원칙** — MyCryptoDiary에 쓴 [[학습/공부/JS/Feature-Sliced Design|FSD]] 계층이 같은 논리로 잘려 있다는 걸 이번에 연결했다.
  - **계층은 디버깅의 좌표계다.** `ping` → `nslookup` → `curl -v`로 고장 범위를 이분 탐색. 계층 언어가 없으면 "안 된다"만 남는다.
  - **대가를 정확히 아는 것이 면접 답이 된다** — 헤더 54바이트(3.6%) 오버헤드 / 오류 검사 3중 중복 / **무선 손실을 TCP가 혼잡으로 오해**하는 정보 은닉의 손해. 마지막 것이 핵심: **계층 독립성을 만든 그 무관심이 여기선 성능 손해로 되돌아온다.** RFC 3439 §3 제목이 아예 「Layering Considered Harmful」이다.
  - **그래서 NAT·L7 로드밸런서 같은 계층 위반이 현실엔 흔하다.** 모델이 절대 규칙이 아니라 **대부분의 경우에 이득이 큰 트레이드오프**라는 것.
- 근거: [RFC 1958](https://www.rfc-editor.org/rfc/rfc1958) §2·§3(단일 인터넷 계층·end-to-end), [RFC 3439](https://www.rfc-editor.org/rfc/rfc3439) §3 Layering Considered Harmful(중복 기능·정보 은닉 비용), 08-21 실측 `route get default` → `mtu 1500`. 헤더 크기는 이더넷 14 + IPv4 20 + TCP 20 = 54바이트(옵션 없을 때).
- 다음: 45강 MTU/MSS에서 **오버헤드 54바이트가 MSS 1460이라는 숫자로 그대로 드러난다** — 이번 항목의 (1)번 대가를 강의에서 숫자로 확인할 것.
