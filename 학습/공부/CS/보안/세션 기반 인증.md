# 세션 기반 인증

**로그인 상태는 서버가 기억하고, 브라우저에는 그 기억을 찾을 번호표(세션 ID)만 준다.** 쿠키는 브라우저에, 세션은 서버에 있고, 그 번호가 통하는지는 서버가 정한다.

## 핵심 정리

### 왜 필요한가

HTTP는 요청끼리 서로를 모른다(stateless). 로그인 요청 다음에 온 요청이 같은 사람인지 서버가 알려면, 요청마다 붙어 오는 표시가 있어야 한다.

### 흐름 네 단계

1. **로그인**: 브라우저가 아이디와 비밀번호를 보낸다
2. **세션 생성**: 서버가 확인한 뒤 랜덤 세션 ID를 만들고, 자기 저장소에 「이 번호는 hong」이라고 적는다
3. **쿠키 발급**: 응답의 `Set-Cookie: sid=<번호>`로 번호만 내려준다
4. **이후 요청**: 브라우저가 `Cookie: sid=<번호>`를 자동으로 붙이고, 서버는 그 번호로 저장소를 찾아 누구인지 안다

로그아웃은 서버 저장소에서 그 번호를 지우는 것이다.

### 어디에 무엇이 있나

| | 위치 | 들어 있는 것 |
|---|---|---|
| 쿠키 | 브라우저 | 의미 없는 랜덤 번호 하나 |
| 세션 | 서버 저장소 | 누구인지, 언제 로그인했는지 |

- **세션 ID는 의미가 없고 추측할 수 없어야 한다.** 사용자 정보를 넣지 않고, OWASP 기준 엔트로피 64비트 이상이다. 아래 실험의 `crypto.randomBytes(16)`은 128비트(16진수 32자)다
- **판정은 서버가 한다.** 쿠키가 브라우저에 남아 있어도 서버가 세션을 지우면 그 번호는 더 이상 통하지 않는다. 그래서 로그아웃, 강제 로그아웃이 즉시 반영된다
- **서버 저장소가 사라지면 로그인도 사라진다.** 세션을 프로세스 메모리에 두면 재시작할 때 전원이 로그아웃된다. 실무에서 Redis 같은 프로세스 밖 저장소에 두는 이유다

### 쿠키 속성은 보안 장치다

- `HttpOnly`: 페이지의 JS(`document.cookie`)가 읽지 못한다. XSS가 들어와도 세션 ID를 훔쳐 가기 어렵다. 서버가 `Set-Cookie`로 내려줄 때만 붙일 수 있다
- `SameSite=Lax`: 다른 사이트에서 시작된 POST 요청에는 쿠키를 붙이지 않는다. CSRF를 막는 장치다
- `Max-Age`: 브라우저가 쿠키를 버릴 때까지의 초. 로그아웃 응답의 `Max-Age=0`은 「지금 버려」라는 뜻이다

### 「쿠키는 서버에 두는 게 안전하다」는 말

쿠키는 정의상 항상 브라우저에 저장된다. 서버에 두는 쿠키는 없다. 이 말은 줄면서 뜻이 섞인 것이고, 맞는 말은 아래 둘이다.

- **서버가 `Set-Cookie`로 `HttpOnly`를 붙여 내려준 쿠키**가 JS로 만든 쿠키보다 안전하다
- **중요한 상태는 서버 세션에 두고**, 쿠키에는 번호만 넣는다

토큰 저장 위치로 「localStorage보다 HttpOnly 쿠키」를 권하는 말도 같은 이유다. 둘 다 브라우저 안이고, 차이는 페이지 JS가 읽을 수 있느냐다.

## 기록

### 2026-10-17 — 로그인 상태를 서버는 어떻게 기억하나

- 궁금했던 것: [네트워크 학습 계획](../%EB%84%A4%ED%8A%B8%EC%9B%8C%ED%81%AC/%ED%95%99%EC%8A%B5%20%EA%B3%84%ED%9A%8D.md) N8(70~73강 세션 기반 인증)의 개념을 강의 전에 손으로 먼저 잡고 싶었다
- 파고든 길: Node 기본 `http`만으로 서버를 만들고, curl의 `-c jar.txt`(쿠키 저장)와 `-b jar.txt`(쿠키 전송)로 브라우저를 흉내 냈다. 핵심 코드:

```js
const sessions = new Map();        // 세션 저장소: sid -> { user, createdAt }

// POST /login 성공 시
const newSid = crypto.randomBytes(16).toString("hex");
sessions.set(newSid, { user: id, createdAt: Date.now() });
res.writeHead(200, { "Set-Cookie": `sid=${newSid}; HttpOnly; SameSite=Lax; Path=/; Max-Age=3600` });

// GET /me
const session = sessions.get(sid);   // 쿠키로 받은 sid로 저장소를 찾는다
if (!session) { res.writeHead(401); return res.end("누구세요?\n"); }

// POST /logout
sessions.delete(sid);
```

| 순서 | 요청 | 응답 |
|---|---|---|
| 1 | 로그인 전 `/me` | 누구세요? |
| 2 | 로그인 | `Set-Cookie: sid=0138b5f8…; HttpOnly; SameSite=Lax; Path=/; Max-Age=3600` |
| 3 | 쿠키 들고 `/me` | 안녕하세요 hong |
| 4 | 쿠키 없이 `/me` | 누구세요? |
| 5 | 로그아웃 | 서버 로그에 `세션 저장소: {}` |
| 6 | **옛 쿠키 그대로** `/me` | **누구세요?** 쿠키는 왔는데 거절 |

- 예측: 로그인 → 서버 재시작 → 같은 쿠키로 `/me`면 「세션이 만료됐고, 쿠키가 서버에 없어서 거절」. **결과(거절)는 맞았고 이유 둘은 틀렸다**
  - 만료가 아니라 **삭제**였다. 실험은 몇 초였고 `Max-Age=3600` 안이었다. 메모리 `Map`이 프로세스와 함께 사라지고 새 프로세스는 빈 `new Map()`으로 시작했다
  - 쿠키는 원래 서버에 없다. 재시작 뒤에도 jar.txt에 쿠키가 남아 있었고 요청에도 실렸다. 서버가 그 sid로 **세션**을 못 찾았을 뿐이다
- 알게 된 것:
  - 쿠키는 번호표, 세션은 서버의 기록. 둘을 섞어 말하면 틀린다
  - 6번처럼 판정은 서버가 하므로 서버가 지우면 즉시 끝난다
  - 저장소가 프로세스 메모리면 재시작이 곧 전원 로그아웃이다
- 근거: 로컬 재현(위 표), [MDN Using HTTP cookies](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies)의 HttpOnly 절, [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)의 세션 ID 길이와 로그아웃 절
- 새로 생긴 궁금증: 서버가 아무것도 기억하지 않는 토큰 방식은 무엇으로 「이 사람은 hong」을 믿게 하나 → N8 후반, [토큰 인증과 키 관리](%ED%86%A0%ED%81%B0%20%EC%9D%B8%EC%A6%9D%EA%B3%BC%20%ED%82%A4%20%EA%B4%80%EB%A6%AC.md)

## 더 알아보면 좋은 것

- 서버를 두 대 띄우고 요청을 번갈아 보내면, 각자 메모리 `Map`을 들고 있어서 로그인이 요청마다 됐다 풀렸다 한다(2026-10-17 실험). 해법은 한 서버에 고정(sticky session)하거나 세션을 공유 저장소(Redis)에 두는 것

## 참고 자료

- [MDN: Using HTTP cookies](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies) — 쿠키의 첫 용도로 세션 관리를 들고, *"A cookie with the `HttpOnly` attribute can't be accessed by JavaScript … Cookies that persist user sessions for example should have the `HttpOnly` attribute set"* (2026-10-17 확인)
- [OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) — 세션 ID는 *"must be meaningless"*, *"at least 64 bits of entropy"*, 로그아웃 때 *"must invalidate the session at least on server side"* (2026-10-17 확인)
- [RFC 6265: HTTP State Management Mechanism](https://www.rfc-editor.org/rfc/rfc6265) — `Set-Cookie`와 `Cookie` 헤더의 원문 명세. HttpOnly는 쿠키를 HTTP 요청으로만 한정하고 스크립트 API에서 뺀다 (2026-10-17 확인)
