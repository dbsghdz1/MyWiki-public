# 가상머신과 컨테이너

가상머신은 **커널까지 새로 부팅**하고, 컨테이너는 **호스트 커널을 빌려 쓰면서 프로세스만 칸막이**한다 — 그래서 다른 OS 버전을 시험하려면 가상머신이어야 한다.

## 핵심 정리

| | 가상머신 (UTM, Parallels) | 컨테이너 (Docker) |
|---|---|---|
| 흉내 내는 것 | 컴퓨터 한 대 — CPU·메모리·디스크·화면 | 프로세스 하나가 사는 칸막이 |
| 커널 | 게스트가 **자기 커널**을 부팅 | 호스트 커널을 **공유** |
| 격리 장치 | 하이퍼바이저(CPU의 가상화 기능) | 리눅스 커널의 namespace·cgroup |
| 무게 | 수십 초 부팅, 수십 GB | 1초 안팎, 수십~수백 MB |
| 안에서 도는 것 | macOS·Windows·Linux 통째로 | 리눅스 프로그램(서버·DB 등) |

- **namespace**는 PID·네트워크·마운트 같은 전역 자원을 "나만의 사본"처럼 보이게 감싸는 커널 기능이다. 컨테이너 = namespace로 시야를 가리고 cgroup으로 자원을 묶은 **평범한 프로세스**.
- 그래서 컨테이너는 **호스트와 같은 종류의 커널**에서만 돈다. macOS 커널에는 이 기능이 없어서 macOS 컨테이너는 없다.
- 맥에서 Docker Desktop을 켜면 **보이지 않는 리눅스 가상머신**을 하나 띄우고, 컨테이너는 그 안의 리눅스 커널 위에서 돈다. 결국 맥의 Docker = 가상머신 + 컨테이너 두 겹.

## 기록

### 2026-09-30 — macOS 27에서 앱을 시험하려면 왜 Docker가 아니라 UTM인가
- 궁금했던 것: [BarStack](../../../../%ED%94%84%EB%A1%9C%EC%A0%9D%ED%8A%B8/%EA%B0%9C%EC%9D%B8/BarStack/README.md)이 macOS 27에서 안 된다는 얘기를 듣고 시험 환경으로 UTM이 나왔는데, 격리된 환경이면 Docker도 되지 않나 싶었다.
- 파고든 길: 두 방식이 어디까지 새로 만드는지를 비교했다.
- 알게 된 것:
  - 확인하고 싶은 건 **macOS 27의 새 window server가 메뉴바를 어떻게 그리는지**다. 이건 커널·시스템 서비스 수준의 동작이라, 호스트 커널(26.5.1)을 빌려 쓰는 컨테이너로는 절대 볼 수 없다.
  - UTM은 Apple Virtualization framework 위에서 macOS 게스트를 통째로 부팅하므로 다른 버전을 볼 수 있다. 다만 호스트보다 새 게스트는 안 뜰 수도 있다.
- 근거: 결국 가상머신 없이 Hidden Bar·Thaw의 macOS 27 실측을 근거로 고쳤다 — BarStack 1.1.3.
- 새로 생긴 궁금증: 하이퍼바이저는 게스트의 특권 명령을 어떻게 가로채나? (Apple silicon의 EL2)

## 더 알아보면 좋은 것
- cgroup이 CPU·메모리 한도를 거는 방식, `docker run --memory`가 실제로 무엇을 쓰는지.
