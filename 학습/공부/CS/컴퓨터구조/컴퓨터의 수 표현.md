# 컴퓨터의 수 표현

돈 계산에서 float을 쓰면 안 되는 이유와, 그 대신 쓰는 방법.

## 핵심 정리

### 왜 `0.1 + 0.2 !== 0.3`인가

십진법에서 `1/3`을 정확히 못 쓰는 것과 같은 일이다. `0.333…`으로 무한히 이어지니 어딘가에서 끊어야 하고, 끊으면 오차가 남는다.

**컴퓨터는 이진법을 쓰는데, 이진법에서는 `0.1`이 무한소수다.**

```
0.1(십진)  →  이진으로는 0.0(0011) — 괄호 안 네 자리가 무한 반복
0.2(십진)  →  이진으로는 0.(0011) — 같은 마디가 반복
```

> 반복 마디를 괄호로 표기했다. 0과 1을 길게 나열해 적으면 퍼블리시 차단 패턴(휴대폰·카드번호)에 오탐으로 걸린다 — 이진 전개는 그런 번호와 생김새가 같기 때문이다.

메모리는 유한하니 잘라낸다. 그래서 저장된 값이 정확히 0.1이 아니다.

```js
0.1 + 0.2          // 0.30000000000000004
0.1 + 0.2 === 0.3  // false
```

**버그가 아니라 구조적 한계다.** JS만이 아니라 Python·Java·C 전부 같다 — 다들 IEEE 754라는 같은 표준을 쓴다.

**정확히 표현되는 소수의 조건**: 분모가 2의 거듭제곱인 분수만 된다. `0.5`(1/2)·`0.25`(1/4)·`0.125`(1/8)는 정확하고, `0.1`(1/10)·`0.3`은 안 된다. 10 = 2 × 5인데 **5가 2의 거듭제곱이 아니기 때문**이다. (십진법에서 분모에 2·5 외의 소인수가 있으면 무한소수인 것과 같은 원리다.)

### 정수는 왜 괜찮나

정수는 이진법으로 **정확히** 표현된다. `5` = `101`, `100` = `1100100`. 끊을 자리가 없다.

단 **크기 한계가 있다.** JS `number`(배정밀도)는 가수부가 53비트라 **2⁵³까지만** 정확하다.

```js
Number.MAX_SAFE_INTEGER + 2   // 9007199254740992  (정답은 …93)
```

`bigint`는 이 한계가 없다 — 메모리가 허락하는 만큼 커진다.

### 해법은 "소수를 안 쓰는" 게 아니라 "단위를 바꾸는" 것 — 고정소수점

키를 `1.75m` 대신 `175cm`로 재면 소수점이 사라진다. **같은 값인데 단위를 잘게 만든 것**뿐이다.

비트코인이 실제로 이렇게 한다. 내부적으로 BTC가 아니라 **사토시**(1억분의 1 BTC) 단위 정수로 다룬다.

```
0.001 BTC  =  100,000 사토시
```

소수점 아래 n자리를 살리려면 **10ⁿ을 곱한다**. 8자리면 10⁸ = 1억. 이렇게 "정수 + 정해진 배율"로 표현하는 방식을 **고정소수점(fixed-point)**이라 하고, 금융 시스템이 float 대신 쓰는 표준 방법이다.

**곱셈은 배율이 곱해지고, 나눗셈은 나뉜다.** 그래서 스케일된 값끼리 곱하면 배율을 한 번 되돌려야 한다.

```
가격 × 수량 ÷ 10⁸
106,954,000 × 100,000 = 10,695,400,000,000
                ÷ 1억 = 106,954원
```

검산: `106,954,000 × 0.001 = 106,954`. **중간이 전부 정수라 오차가 낄 자리가 없다.** 마지막 나눗셈에서만 나머지가 생기고, 거기에 올림·내림 정책을 적용한다.

### ⚠️ 스케일링을 float으로 하면 안 된다

`0.001 * 1e8`이 정확히 `100000`이 나와서 "그냥 곱해도 되네" 싶은데, **운이 좋았던 것**이다. 실측:

| 값 × 1e8 | 결과 |
|---|---|
| `0.001` | `100000` ✅ |
| `0.07` | `7000000.000000001` ❌ |
| `0.29` | `28999999.999999996` ❌ |
| `0.145` | `14499999.999999998` ❌ |
| `0.00000003` | `2.9999999999999996` ❌ (3 사토시가 안 나온다) |

**9개 중 5개가 정수가 아니었다.** 소수를 없애려고 하는 계산인데 중간에 소수를 거치니 소용이 없다. 그래서 스케일링은 **문자열을 조작해서** 한다 — 소수점을 옮기는 건 결국 문자를 옮기는 일이다.

```
"0.001"  →  "0" 과 "001"  →  소수부를 8자리로 "00100000"  →  "0"+"00100000"  →  BigInt  →  100000n
```

### JS의 두 숫자 타입 — 섞이지 않는다

```js
1n + 1          // TypeError: Cannot mix BigInt and other types
Math.abs(1n)    // TypeError: Cannot convert a BigInt value to a number
1n < 2          // true  ← 비교만 예외적으로 허용
```

**JavaScript 자체의 규칙**이라 `as`로 우회해도 런타임에 던진다. 섞으면 결과가 뭐가 되어야 할지 정해지지 않기 때문이다 — `bigint`로 만들자니 상대가 소수일 수 있고, `number`로 만들자니 2⁵³ 넘는 값이 뭉개진다. **조용히 틀리느니 막은 것**이다.

`BigInt()`의 실패는 입력에 따라 종류가 다르다(실측):

```js
BigInt(0.5)      // RangeError: 정수가 아니라서
BigInt("0.5")    // SyntaxError: 정수 리터럴로 파싱 실패
```

### 어느 값에 무엇을 쓸까

기준은 하나다 — **이 값으로 돈을 깎는가, 화면에 그리기만 하는가.**

| | 타입 |
|---|---|
| 잔고·주문금액·수수료·가격 | `bigint` (1원도 틀리면 안 됨) |
| 코인 수량 | `bigint` (10⁸ 곱해 정수화) |
| 24h 거래대금·등락률 | `number` (표시 전용) |

**왜 돈에서 유독 문제인가**: 거래 한 번에 0.0000001원 틀리는 건 아무도 모른다. 그런데 수만 번 쌓이면 잔고가 실제와 어긋난다. 게다가 오차 방향이 일정하면(항상 내림 등) 한쪽으로만 쌓인다 → [[프로젝트/개인/MyCryptoDiary/README|반올림 규칙]]을 정해두는 이유.

### 다른 언어는

- **Java** — `BigDecimal` (십진 고정소수점 클래스)
- **Python** — `decimal.Decimal`, 정수는 애초에 무한 정밀도
- **PostgreSQL** — `numeric`/`decimal` 타입. **JS 드라이버는 이걸 문자열로 돌려준다**(`number`로 바꾸면 정밀도가 깨지므로)
- **JS** — `bigint`(정수만) 또는 라이브러리(decimal.js 등)

## 기록

### 2026-09-03 — 매수 금액 계산 (MyCryptoDiary D4)

맥락: [[프로젝트/개인/MyCryptoDiary/거래 엔진 D4 2026-09-02|D4]] 매수 엔진에서 `가격 × 수량`을 원 단위 정수로 만드는 함수. 수량이 소수(0.001 BTC)라 그대로는 `bigint`에 못 담는다.

계기는 질문이었다 — *"왜 소수를 안 쓴다고 했지? 컴퓨터가 계산을 못 해서?"* 반은 맞다. 못 하는 게 아니라 **이진법으로 십진 소수를 정확히 담을 수 없어서**다.

`0.001 * 1e8`이 정확히 나오길래 "float으로 스케일링해도 되나" 싶어 9개 값을 실측했더니 **5개가 깨졌다**(`0.07`·`0.29`·`0.145`·`0.00000003` 등). 특히 `0.00000003 × 1e8 = 2.9999999999999996`이라 3 사토시가 안 나온다. **된 케이스만 보고 판단하면 안 된다는 실증.**

그리고 이 주제에서 **`tsc` 통과가 검증이 아니라는 걸 여러 번 겪었다** — 수수료가 20원으로 나온 것, 15억이 "150000000억"으로 나온 것, 응답 타입을 `bigint`로 선언해 컴파일러를 속인 것. 전부 타입은 완벽했다. **숫자는 손계산이 검증한다.**
