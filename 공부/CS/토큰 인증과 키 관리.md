# 토큰 인증과 키 관리

**키는 "누가 검증하느냐"로 갈린다.** 남이 검증하면 받아오는 값이고, 내가 검증하면 지어내는 값이다. 이 구분이 "어떻게 얻나 · 공유해도 되나 · 어디에 둬야 하나"를 전부 결정한다.

## 핵심 정리

### 두 종류의 키

| | 발급 | 검증 | 지어낼 수 있나 |
| --- | --- | --- | --- |
| 제공자 식별자 (OAuth client id, API key) | 남 | **남** | ❌ 남이 알아봐야 한다 |
| 자체 서명 키 (HMAC secret) | 나 | **나** | ✅ **난수면 충분하다** |

앞은 카카오·애플이 우리를 알아보는 이름표다. 뒤는 우리가 발급한 토큰을 우리가 되읽을 때만 쓰므로 바깥의 누구도 알 필요가 없다. **"어디서 받아오지?"라고 묻게 되면 대체로 앞을, "아무거나 넣어도 되나?"라고 묻게 되면 뒤를 다루고 있는 것이다.**

### HS256이 대칭키라서 생기는 것들

같은 키로 서명하고 같은 키로 검증한다. 여기서 실무 규칙이 전부 따라 나온다.

- **한 환경의 서버 인스턴스는 같은 값을 써야 한다.** 다르면 A가 발급한 토큰을 B가 위조로 판정해 로그인이 랜덤하게 풀린다. 스케일아웃하는 순간 드러난다
- **환경 간에는 반드시 달라야 한다.** dev와 prod가 같으면 **dev 키 유출이 곧 prod 세션 위조**다. dev는 접근·로그가 느슨해서 실제 위험이다
- **개발자 각자의 로컬은 서로 달라도 된다.** 내 기계가 발급한 토큰을 남의 기계가 검증할 일이 없다
- **회전 비용이 크다.** 바꾸면 그 환경의 발급된 토큰이 전부 무효다. refresh TTL이 30일이면 운영에서 전원 로그아웃이 된다
- 비대칭(RS256)이면 공개키만 뿌리면 되므로 이 고민이 줄지만, **발급처가 하나뿐이면 대칭키로 충분하다**

키 길이는 알고리즘이 정한다 — HS256은 **256비트(32바이트) 이상**이고, RFC 7518이 "해시 출력 이상의 키"를 요구한다. `openssl rand -base64 48` 같은 CSPRNG 출력을 쓴다. 사람이 지어낸 문장은 길어도 엔트로피가 없다.

### 공유해야 하는 것은 서버끼리지 사람끼리가 아니다

"팀원과 키를 공유해야 하나"의 답은 **아니오**다. 같아야 하는 주체는 그 환경의 **서버 인스턴스**이지 사람이 아니다. 그래서 잘 만든 배포는 사람 손을 아예 안 거치게 한다 — 비밀 저장소(Parameter Store 등)에 두고 **머신이 자기 권한으로 직접 꺼내 쓰게** 한다. 그러면 저장소·CI 로그·GitHub 어디에도 값이 남지 않는다.

### 제3자에게 "이 앱이 맞다"를 증명하는 식별자는 또 다른 축이다

앞의 두 종류(제공자 식별자·자체 서명 키) 말고 **플랫폼이 앱 자체를 알아보는 값**이 있다. 소셜 로그인 SDK가 요구하는 것이 이쪽이다.

| 값 | 무엇을 증명 | 어디서 나오나 |
| --- | --- | --- |
| iOS **번들 ID** | 이 앱이 등록된 그 앱이다 | 프로젝트 설정 |
| Android **패키지명** | 위와 같음 | `applicationId` |
| Android **키 해시** | 이 APK가 **그 키로 서명**됐다 | `base64(SHA-1(서명 인증서))` |

**키 해시는 서명 키마다 다르다.** 그래서 같은 앱이라도 최소 셋을 등록해야 한다 — 디버그 키(개발자마다 다르다) · 릴리스 업로드 키 · **스토어가 재서명한 키**. 마지막을 빠뜨리는 것이 전형적인 사고다: 내 기기에선 되는데 **스토어에서 받은 앱만 로그인이 안 된다.**

**등록이 빠지면 "실패"가 아니라 "다른 경로로 성공"처럼 보인다.** 네이티브 앱 로그인이 거부되면 SDK가 웹 로그인으로 폴백하도록 짜여 있는 경우가 많고, 그러면 **동의 화면을 두 번 지나는 것**이 유일한 단서가 된다. 완전히 실패하지 않아서 더 오래 걸린다.

### 설정 누락은 부팅이 아니라 첫 요청에서 드러난다

비밀을 환경변수로 받으면 **비어 있어도 부팅은 된다.** 값을 실제로 쓰는 첫 요청에서야 터지고, 그동안 헬스체크는 계속 초록이다. 의도한 설계일 수 있지만(다른 기능은 살린다), **"헬스체크가 초록이니 정상"이라는 판단이 틀리는 구간**이 생긴다는 것을 알고 있어야 한다.

### 상태코드가 원인을 가른다

같은 가짜 토큰을 던졌을 때 **401과 500은 다른 고장을 가리킨다.**

- **401** — 설정을 읽었고 토큰만 틀렸다 → 서버는 정상
- **500** — 검증기를 만들지도 못했다 → **설정이 비었다**

토큰을 파싱하기 전에 죽으므로 토큰 모양과 무관하게 500이 난다. **가짜 토큰 한 방으로 "값이 도달했는가"를 판정할 수 있다** — 실기기도 실제 계정도 필요 없다.

## 기록

### 2026-08-25 — dev만 로그인이 안 되는 이유를 500 하나로 좁혔다

- 맥락: 소프트웨어마에스트로 보험찾개냥에서, 앱 코드가 다 끝났는데 dev 서버 소셜 로그인이 실패했다 (SSH-388)
- 배운 것:
  - **`.env`가 하나가 아니었다.** 로컬 파일과 배포 서버의 파일은 다른 물건이고, 배포 워크플로가 후자를 만들지 않으면 "로컬엔 있는데 서버엔 없는" 상태가 조용히 유지된다
  - **비밀을 넣어도 도달하지 못하는 층이 있다.** 비밀 저장소에 값을 넣는 것과, 그 값이 컨테이너까지 전달되는 것은 별개다. compose의 `environment:`에 없으면 앱은 끝내 못 본다
  - **인증 기능을 추가할 때 배포 경로를 같이 안 고치면 이 구멍이 난다.** 로컬은 셸에 직접 올리는 절차라 안 걸리고, 그래서 개발 중엔 아무도 모른다
  - 401 vs 500으로 "코드 문제인가 값 문제인가"를 실기기 없이 갈랐다
- 근거:
  - `OidcSocialTokenVerifier.kt:94` — `require(issuer.isNotBlank() && jwksUri.isNotBlank() && audiences.isNotEmpty())`. 앞의 둘은 설정 파일에 박힌 공개값이라 빌 수 없으므로 비는 것은 `audiences`뿐
  - 실측 — 같은 코드에 값만 다른데 dev는 500 `SOCIAL_PROVIDER_UNAVAILABLE`, 로컬은 401 `SOCIAL_TOKEN_INVALID` (카카오·애플 모두)
  - `Server/deploy/docker-compose.yaml`의 `environment:`에 인증 키가 하나도 없었다. 배포 문서의 `.env` 생성 루프도 마찬가지
  - `server-deploy.yml:166` — 배포는 `/opt/app/.env`의 `APP_IMAGE_TAG` 한 줄만 `sed`한다. **비밀 저장소에 값을 넣어도 그 파일을 다시 만들지 않으면 반영되지 않는다**
  - 스펙: `docs/spec/SSH-388/spec.md` (PR #77)

### 2026-08-25 — 등록 누락은 실패가 아니라 "우회 성공"으로 나타난다

- 맥락: 소프트웨어마에스트로 보험찾개냥. 서버 키를 다 채워 dev가 401을 주는 것까지 확인한 뒤, 실기기에서 카카오 로그인이 여전히 실패했다 (SSH-388)
- 배운 것:
  - **증상이 "두 번 동의"였다.** 카카오톡 앱에서 동의 → 다시 웹뷰에서 동의 → 실패. 코드상 앱 로그인이 성공하면 웹뷰가 안 뜨므로, **앱 로그인이 이미 실패하고 폴백한 것**이 드러난다. 콘솔에 iOS 번들 ID가 없으면 나는 모양이다
  - **키 해시는 `base64(SHA-1(서명 인증서))`이고 서명 키마다 다르다.** 디버그·릴리스·스토어 재서명 셋을 각각 등록해야 한다
  - **최신 APK는 v1(JAR) 서명이 없다.** `keytool -printcert -jarfile`이 "서명된 jar 파일이 아닙니다"로 끝난다 — v2/v3 전용이라 `apksigner`나 keystore에서 직접 뽑아야 한다
  - **`debug.keystore`가 `(로컬 경로)`에 없을 수 있다.** SDK를 별도 경로에 두면 그쪽으로 따라간다(`local.properties`의 `sdk.dir`). 그 디렉터리를 다시 만들면 **키가 바뀌어 등록해 둔 키 해시가 무효가 된다**
- 근거: `kakao_login_service.dart`의 `_login()` 폴백 분기, 빌드 산출물 `app-debug.apk`(v1 서명 없음), `flutter-env/.android/debug.keystore`, [카카오 로그인 iOS 문서](http://developers.kakao.com/docs/ko/kakaologin/ios)
