# 테스트 코드

**통과하는 테스트가 무엇을 보증하는가**를 의심하는 노트. 지금까지 배운 것은 거의 전부 "초록인데 아무것도 안 지키고 있던" 경우였다.

## 핵심 정리

- 테스트를 쓰고 나서 **"이 단언이 거짓이 되는 상황이 실제로 있는가"**를 한 번 되묻는다. 없으면 그 줄은 장식이다.
- 통합 테스트에서 **컨테이너·DB 같은 외부 자원의 생명주기**는 프레임워크가 정한 기본값을 그대로 믿으면 안 된다. 테스트 클래스가 하나일 때만 맞는 기본값이 많다.

## 기록

### 2026-08-16 — Testcontainers `@Container`는 클래스가 끝나면 컨테이너를 멈춘다

- 맥락: 보험찾개냥 SSH-310. 통합 테스트 클래스가 **둘이 되자** 로컬에서 간헐적으로, CI에선 매번 `Connection refused`가 났다(14건 실패, 9분 12초).
- 배운 것:
  - `@Testcontainers` + `@Container`를 **static 필드**에 쓰면 "테스트 메서드 사이에는 공유하되 **마지막 테스트 메서드가 끝나면 stop**"이다. 문서 표현 그대로 클래스 단위 수명이다. 그래서 **두 번째 테스트 클래스는 이미 멈춘 컨테이너에 붙으려 한다.**
  - 클래스가 하나뿐일 땐 이 결함이 절대 드러나지 않는다. **테스트가 하나일 때만 맞는 설정**이었던 것이다.
  - 해결은 **싱글턴 컨테이너 패턴** — 애노테이션을 빼고 공통 부모에서 `MySQLContainer(...).apply { start() }`로 직접 띄우고 **stop을 부르지 않는다.** 정리는 Testcontainers가 띄우는 Ryuk 컨테이너가 스위트 종료 때 해준다.
  - Spring Boot에선 `@JvmStatic @field:ServiceConnection`을 붙여 접속 정보를 컨텍스트에 넘긴다.
- 근거: 커밋 `5481911`. 고친 뒤 CI가 9분 12초 실패 → 1분 50초 통과로 바뀌었다.

### 2026-08-18 — 항상 참인 단언, 그리고 너무 넓은 예외 단언

- 맥락: 같은 프로젝트 SSH-293 AI 리뷰. 내가 쓴 테스트 세 개가 서로 다른 방식으로 아무것도 검증하지 않고 있었다.
- 배운 것 — **초록이지만 비어 있는 단언의 유형들**:
  - **타입이 이미 보장하는 것을 단언한다.** `assertTrue(items.all { it.providedBy in ProvidedBy.entries })` — `providedBy`가 그 enum 타입이므로 **항상 참**이다. 의도는 "세 분류가 다 나오는가"였으니 집합 비교로 바꿔야 했다.
  - **예외가 났다는 사실만 본다.** `runCatching { ... }.isFailure`는 **DB가 꺼져 있어도 통과한다.** 검증하려던 제약 위반이 아니라 연결 실패로 통과하는 것이다.
  - **예외 타입을 너무 넓게 잡는다.** 상위 타입(`DataAccessException`)으로 받으면 FK·UNIQUE 등 **다른 제약에 걸려도 통과**한다. 정작 검증 대상인 CHECK 제약이 빠져도 초록이 된다. → 원인 메시지에 **제약 이름**이 있는지까지 확인했다.
  - 공통점은 전부 **"실패시켜 보지 않았다"**는 것이다. 검증 대상을 일부러 지우거나 망가뜨렸을 때 빨간불이 나는지 확인하면 셋 다 그 자리에서 드러난다.
- 근거: 커밋 `bf81ab6`, `0cdeacf`. 예외 타입 쪽 배경은 [[공부/백엔드/JPA와 Spring Data|JPA와 Spring Data]].

### 2026-08-18 — 정렬이 정해지지 않은 결과를 테스트가 잡아내려면

- 맥락: 같은 PR. 여러 룰의 서류를 합치는 코드가 `distinctBy { it.code }`로 첫 행을 남겼는데, `ORDER BY sort_order`가 동점을 깨지 못해 **어느 행이 남을지는 DB가 정하고 있었다.** 테스트는 통과하고 있었다.
- 배운 것:
  - **비결정성은 단언이 약해서가 아니라 입력이 한 가지라서 안 잡힌다.** 픽스처가 늘 같은 순서로 들어오면 코드가 순서에 의존해도 초록이다.
  - 그래서 **입력 순서를 뒤집은 케이스를 따로 만든다.** "DB 반환 순서를 뒤집어도 결과가 같은가"를 테스트 이름으로 박아두면 의도가 남는다.
  - 그리고 **정렬은 DB가 아니라 코드에서 완결한다.** 동점을 깨는 2차 키(`id`, `code`)까지 지정해야 "정렬했다"고 할 수 있다.
- 근거: 커밋 `e9bb4a1`. 실측으로 같은 조회를 3회 돌려 응답 해시가 동일한지도 확인했다.

### 2026-08-20 — mock과 stub의 차이, 그리고 "가짜로 바꾸는 선"이 테스트의 성격을 정한다

용어부터. **stub**은 손으로 만든 가짜 클래스("묻지 말고 늘 이 답을 줘"), **mock**은 라이브러리가 만들어 주고 테스트마다 반환을 지정하는 가짜다. mockk·Mockito는 mock을 만드는 라이브러리 이름이고 하는 일은 같다.

더 중요한 건 **어디에 가위를 대느냐**다. 소마 서버에 두 방식이 공존하고 있었다.

```
방식 A   [Controller] → [Service] ─✂─ [가짜 외부API · 가짜 저장소]
방식 B   [Controller] ─✂─ [가짜 Service]        + 서비스 단위 테스트를 따로
```

- **A(경계에서 자르기)** — Controller와 Service를 한 번에 검증한다. 서비스 예외가 공통 핸들러까지 가서 계약대로 변환되는지가 함께 잡힌다. 대신 서비스 분기를 촘촘히 보려면 테스트가 뚱뚱해진다
- **B(서비스 앞에서 자르기)** — Controller의 바인딩·검증·직렬화만 좁게 본다. **서비스 단위 테스트가 짝으로 있어야 성립한다**

어느 쪽이 옳다기보다 **서비스에 분기가 있느냐**로 갈린다. 위임만 하는 얇은 서비스는 A가 낫고, 조건 판정이 여럿인 서비스는 B로 나누는 게 맞다. 판정 기준을 하나 두면 편하다 — **"이 서비스에 단위 테스트를 쓰면 케이스가 3개 이상 나오는가."**

규칙 없이 두면 사람마다 다르게 쓰고, 세 번째 방식이 또 생긴다.

### 2026-08-21 — Docker에 의존하는 테스트는 커밋 게이트에 넣을 수 없다

커밋 직전에 자동으로 돌릴 검사를 고르면서 실측했다(소마 서버, macOS, Gradle 데몬 웜).

| 명령 | 시간 | Docker |
| --- | --- | --- |
| `ktlintCheck` | 1.4s (콜드 11s) | 불필요 |
| `compileKotlin` | 7.4s | 불필요 |
| `test` (DB 불필요분) | 3.1s | 불필요 |
| `test` 전체 · `build` | — | **필요** |

CI가 쓰는 `./gradlew build`를 그대로 커밋 게이트로 쓰려다 막혔다. **Testcontainers 통합 테스트가 Docker를 요구해서, Docker를 안 켠 날에는 커밋 자체가 불가능해진다.** 실제로 Docker를 끄고 돌려 `DockerClientProviderStrategy` 예외로 죽는 것을 확인했다.

그래서 게이트에는 **Docker 없이 도는 것만** 넣고 테스트는 CI에 남겼다. 일반화하면 —

> **로컬 게이트는 CI의 부분집합이어야 한다.** 로컬을 통과한 것이 CI에서 깨지는 건 괜찮지만(로컬이 더 느슨하므로) 그 반대는 안 된다. 로컬이 더 엄격하면 사람은 코드가 아니라 도구를 의심하게 된다.

**속도도 설계 변수다.** 콜드 11초는 하루 첫 커밋에서만 겪지만, 느린 게이트는 결국 꺼진다. **꺼진 게이트는 없는 것보다 나쁘다** — 있다고 믿게 만들기 때문이다.
