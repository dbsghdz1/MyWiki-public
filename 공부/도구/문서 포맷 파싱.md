# 문서 포맷 파싱

발표 자료·문서에서 텍스트를 뽑아내는 법. 대부분의 오피스 포맷은 **zip 컨테이너 + 안쪽 마크업**이라 전용 앱 없이 열 수 있고, 예외는 애플의 iWork(Keynote·Pages·Numbers)다.

## 핵심 정리

| 포맷 | 실체 | 추출법 | 앱 필요 |
|---|---|---|---|
| `.pptx` / `.docx` / `.xlsx` | zip + OOXML | `ppt/slides/slideN.xml`에서 `<a:t>` 텍스트 런 추출 | X |
| `.pdf` | 객체 스트림 | PyMuPDF(`fitz`) `page.get_text()` | X |
| `.key` / `.pages` / `.numbers` | zip + **IWA**(snappy로 압축된 protobuf) | 청크 헤더를 읽어 snappy 블록을 풀고 UTF-8 런 스캔 | X (직접 디코드하면) |

## 기록

### 2026-08-26 — 업로드 파일 포맷은 선언이 아니라 매직 바이트로 판정한다

- 맥락: 소프트웨어 마에스트로 SSH-402 — 영수증 업로드 허용 포맷을 JPEG·PNG에서 WEBP·HEIC·HEIF까지 넓히면서, 서버 판정 근거를 `Content-Type`에서 파일 앞부분 바이트로 바꿨다.
- 배운 것:
  1. **멀티파트의 contentType은 클라이언트 선언이지 사실이 아니다.** 실제로 어긋나는 예 — Flutter `image_picker` 안드로이드 구현(`ImageResizer`)은 `imageQuality < 100`이면 JPEG로 재인코딩하는데 **저장 파일명은 원본(`.heic`)을 그대로 쓴다.** Dio는 contentType을 안 주면 확장자에서 추론하므로, JPEG 내용을 `image/heic`이라고 선언해 보낸다. 서버가 선언을 믿으면 저장 확장자도, 다음 소비자(우리 경우 Gemini)에 넘기는 mimeType도 같이 틀린다.
  2. 매직 바이트 판정표: JPEG `FF D8 FF` · PNG `89 50 4E 47 0D 0A 1A 0A` · WEBP는 `RIFF` + **8바이트 뒤** `WEBP` — RIFF는 WAV·AVI도 쓰는 컨테이너라 앞 4바이트만 보면 오디오가 이미지로 통과한다 · HEIC/HEIF는 4바이트 뒤 `ftyp` + 브랜드 4바이트(`heic`·`heix`→HEIC, `mif1`·`msf1`→HEIF). **avif도 ftyp 컨테이너다** — 브랜드까지 봐야 화이트리스트가 유지된다.
  3. **안드로이드 `image_picker`는 옵션을 하나도 안 주면 변환 자체를 안 돈다** — `shouldScale`이 `maxWidth`·`maxHeight`·`imageQuality` 중 하나라도 있어야 참이다. iOS는 옵션과 무관하게 첫 바이트로 포맷을 판정해 JPEG/PNG/GIF 외에는 JPEG로 재인코딩한다(`FLTImagePickerMetaDataUtil`).
  4. Flutter `Image` 위젯이 디코드하는 것은 JPEG·PNG·GIF·WebP·BMP·WBMP뿐 — **HEIC는 못 그린다.** 서버가 HEIC를 그대로 저장하면 "분석은 성공했는데 썸네일만 안 뜨는", 원인 추적이 오래 걸리는 증상이 된다.
- 근거: `ASMSSH/Boheomgaenyang` PR #79 — `ImageFormat.kt` 판정기 + 단위 테스트(`.heic` 이름 + JPEG 내용 → JPEG 판정을 컨트롤러 테스트로 고정).

### 2026-08-19 — Keynote `.key`는 protobuf라 Keynote 앱 없이도 읽을 수 있다

- 맥락: 발표 자료 6건(`.pptx` 1, `.key` 1, `.pdf` 4)을 위키로 옮기면서 텍스트를 뽑아야 했다. 이 맥이 Keynote 미설치라 "앱으로 PDF export" 경로가 막혀 있었다.
- 배운 것:
  1. **`.key`는 zip이고 안에 `Index/*.iwa`가 있다.** `Data/`(이미지)·`Metadata/`·`preview.jpg`와 함께 들어 있으며, 슬라이드 하나가 `Index/Slide-<id>.iwa` 하나에 대응한다.
  2. **IWA = 4바이트 청크 헤더 + snappy(raw block) 압축 protobuf**의 반복이다. 헤더는 `[타입 1바이트][길이 3바이트 little-endian]`이고, 뒤의 길이만큼이 snappy 블록이다.
  3. snappy raw block 디코더는 **의존성 없이 40줄이면 짠다** — 앞에 varint로 원본 길이, 이후 태그 바이트 하위 2비트로 literal(0)/1바이트 오프셋 copy(1)/2바이트(2)/4바이트(3)를 구분한다. `python-snappy`가 없어도 된다.
  4. protobuf 스키마를 파싱하지 않고 **디코드된 바이트에서 UTF-8 런만 긁어도** 슬라이드 텍스트가 거의 다 나온다. 노이즈(`Google Shape;NN;...`, `Transition`, 파일명)는 필터로 걷어내고, 실제 텍스트 런은 끝에 `*`(0x2A, 다음 필드 태그)가 붙는 경향이 있어 이걸로 골라내면 정확도가 올라간다.
  5. **한계**: 순서·레이아웃·표 구조는 복원되지 않고 문장이 조각날 수 있다. 이미지는 `Data/`에 원본이 그대로 있으니 필요하면 따로 꺼낸다.
- `.pptx`는 훨씬 단순하다 — `unzip` 후 `ppt/slides/slideN.xml`에서 `<a:t>...</a:t>`만 정규식으로 긁고 XML 엔티티만 되돌리면 된다. 슬라이드 순서는 파일명의 숫자로 정렬(문자열 정렬하면 `slide10`이 `slide2`보다 앞에 온다).
- **PDF 메타데이터가 날짜 근거가 된다**: `fitz.open(p).metadata`의 `creationDate`/`author`/`title`. 슬라이드에 날짜 표기가 없던 자료 2건의 시점을 여기서 추정했다(추정임을 문서에 명시). 반대로 메타데이터가 비어 있으면(`producer` 없음 등) 날짜를 지어내지 않는다.
- 근거: 커밋 `8c33ea5`. `.key` 37장·`.pptx` 66장·PDF 4건에서 실제로 텍스트를 뽑아 보존했다.
