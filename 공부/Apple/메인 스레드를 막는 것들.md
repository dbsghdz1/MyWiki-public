# 메인 스레드를 막는 것들

Fadeo 실기기 검증에서 "셔터를 누르면 걸린다 → 고쳤는데 또 걸린다 → 콜드 스타트도 걸린다"를 세 라운드에 걸쳐 잡으며 확인한 목록. **전부 API 이름만 봐서는 비싼 줄 모르는 것들이다.**

## 실측으로 확인된 블로커

| API | 비용 | 함정 |
|---|---|---|
| `AVAudioSession.setActive(true)` | 수십~수백 ms (미디어 서버와 **동기 IPC**) | 재생 함수 안에 넣으면 소리 낼 때마다 낸다. **세션은 시작 때 한 번만, 전용 큐에서** 활성화. `AVAudioPlayer`는 메인을 요구하지 않는다 |
| `CHHapticEngine.start()` | 동기 | `isAutoShutdownEnabled = true`면 쉬던 엔진을 **재생 때마다 다시 깨운다** — 절전 옵션이 매번의 블록으로 돌아온다. 패턴 생성·시작을 전용 큐로 |
| `Data.write(options: .atomic)` | 1~2MB에 수십 ms | 셔터 콜백처럼 "즉시 반응해야 하는 자리" 바로 뒤에 오면 체감상 버튼이 걸린 것으로 읽힌다. 인코딩(메모리)과 쓰기(IO 큐)를 나눈다 |
| `AVCaptureSession` 구성 (`beginConfiguration`~`commit`) | **100~300ms** (렌즈 탐색+포맷 선택 포함) | 콜드 스타트 최대범. Apple 권고대로 **세션 전용 큐**에서 구성하고 `@Published`만 메인에서 갱신 |
| `CIContext(mtlDevice:)` 생성 | 수십 ms | 첫 프리뷰가 붙는 순간 청구된다. `static let`으로 묶어 **앱 시작 때 백그라운드에서 선생성** (static let 초기화는 스레드 안전) |
| lazy 초기화 전반 (텍스처 생성 등) | 각각은 작아도 합산 | "미리 데우기"를 메인 `.task`에서 하면 **데우기가 콜드 스타트를 늘린다.** `Task.detached`로 — 단 스레드 안전한 것만 |

## 순서 있는 파일 쓰기는 직렬 IO 큐 하나로

`DispatchQueue(label:, qos: .utility)` 직렬 큐면 쓰기 순서가 호출 순서 그대로 보존된다. 인덱스 저장처럼 "마지막 쓰기가 이기면 되는" 것에 정확히 맞는다.

## 블록을 없애면 드러나는 2차 버그 ★

**메인이 한가해지면 타이밍에 기대던 코드가 깨진다.** Fadeo에서는 화면 삽입 직후 `.task`의 `withAnimation`이 삽입과 같은 트랜잭션에 합쳐지며 애니메이션이 통째로 사라졌다 — 전에 움직였던 것은 오디오 블록이 두 트랜잭션 사이에 시간을 벌어준 **우연**이었다. 해법은 [[공부/Apple/SwiftUI|SwiftUI]] 2026-08-27 항목(시계 기반 이동).

**규칙: 성능을 고치면 "그동안 우연히 되던 것"이 무엇이었는지 의심하라.**

## 진단 요령

증상별 용의자: **특정 버튼 순간** → 그 핸들러의 동기 호출(오디오·햅틱·디스크). **첫 실행** → 세션·컨텍스트 생성과 lazy. **화면 전환 순간** → 새 화면의 초기화. 재현이 실기기뿐이면 추측 반복 대신 Instruments Time Profiler로 가는 편이 빠르다 — Fadeo는 세 라운드 추측으로 잡았지만 운이 좋았다.
